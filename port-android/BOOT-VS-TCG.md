# 为什么同样是软件 MMU，启动差 5.1 倍（完整启动差 7.4 倍）

结论先说：**"都是软件 MMU"这个前提不成立 —— 启动的主要成本根本不在 MMU 上。**
把成本拆开量下来，差距几乎全部来自**控制流**（块转移、`ret` / `br` 这类间接跳转），
而 MMU 那一块两者只差 1.5 倍。

下面是拆解过程，每一格都是这台设备（vivo V2156FA / 天玑 700 / Cortex-A76 @2.2 GHz）
上实测的，不是估算。

---

## 1. 先看一个反直觉的事实：本移植翻译出的代码**更多**

用 QEMU 的 `-d in_asm` / `-d out_asm` 抓同一次 `fastboot=1` 启动的全部翻译，
和引擎的 `HV_SUM=1 --stats` 对照（脚本：`tools/analyze_tcg_log.py`）：

| 指标 | QEMU TCG | 本移植 |
|---|---|---|
| 翻译块数 | 81 306 | 78 729 |
| 客机指令数 | 407 344 | 396 222 |
| **平均每块客机指令** | **5.01** | **5.03** |
| 块大小分布 | 中位 4，p90 10，最大 235 | 中位 4，p90 10 |
| 宿主指令 / 客机指令 | **12.62** | **15.88** |

两点值得注意：

- **块粒度几乎一样**（5.01 vs 5.03）。所以"TCG 的块切得太碎"不是原因。
  早期我说过"TCG 单个 TB 最多 8 条指令、平均 4.9" —— 那是日志解析被截断导致
  **看错了**，正确数字就是上表：平均 5.01、最大 235。
- **本移植的翻译放大比反而更高**（15.88 > 12.62 条宿主指令/条客机指令）。
  也就是说它不是靠"生成更少代码"赢的。

静态体积既不能解释 5 倍差距，那就只能是**动态**：同样的代码，跑起来每块的进出代价不一样。

---

## 2. 把"每块进出一次要花多少"单独量出来

微基准 `work/loops.c`（客户机侧同一份在 `tests/bench_extra.S`）：
三种循环，**工作指令总数完全相同（2^28 条）**，只有每块的指令数不同：

| 版本 | 块内容 | 每块工作指令 |
|---|---|---|
| `u1` | `sub` + `subs` + `b.ne` | 1 |
| `u8` | 8×`sub` + `subs` + `b.ne` | 8 |
| `u32` | 32×`sub` + `subs` + `b.ne` | 32 |

三条路各跑一遍，绑 cpu7、冷态、取最小值（`output/scripts/run-bench.sh loops`）：

单位 ns / 工作指令，越小越快。

| 版本 | 原生 | QEMU TCG | 本移植 | **TCG vs 原生** | **本移植 vs 原生** |
|---|---|---|---|---|---|
| `u1`（3 条/块） | 0.4550 | 5.1335 | 1.3839 | **11.3× 慢** | **3.04× 慢** |
| `u8`（10 条/块） | 0.4551 | 0.6939 | 0.4616 | 1.52× 慢 | **1.01×（持平）** |
| `u32`（34 条/块） | 0.4550 | 0.5090 | 0.4610 | 1.12× 慢 | **1.01×（持平）** |

（原生三行相等是自洽性校验：工作指令总数一样，原生就该一样。
最初 `u1` 报出 122 ms / 372 ms 两个差 3 倍的值，原因是循环入口没对齐 ——
`.p2align 4` 之后才稳定，这一步不做这条实验就是废的。）

读法：

- **块一大，本移植就跟原生一模一样**（1.01×）。这说明它的"翻译 + 派发"机器
  在正经块尺寸下是零成本的，`HV_INSN_COPY` 那条路确实是一进一出。
- **TCG 在大块下还有 1.1–1.5 倍**，这一层是它的指令展开与寄存器重分配。
- **块一小到 3 条，TCG 塌到 8.9% 原生**，本移植还保住 33%。

用 `c(U) = a + (2a+b)/U` 拟合 `u8`/`u32` 两点（`a` 每条指令成本、`b` 每次块转移成本）：

| | a（每条指令） | b（每次块转移） |
|---|---|---|
| 原生 | ≈0.455 ns（1 周期） | ≈0（分支预测掉了） |
| QEMU TCG | 0.447 ns | **≈1.08 ns ≈ 2.4 周期** |
| 本移植 | ≈0.46 ns | **≈0** |

TCG 每转移一次基本块要付约 2.4 个周期，本移植约 0。
真实内核代码平均 5 条指令一块（上表第 1 节的 5.01），
所以每 5 条指令就要付一次这个钱 —— 这就是那 5.1 倍的主要来源。

### 另一条独立证据：268 435 456 次块转移，1 次派发

`test_bench`（不经 Linux 客户机，直接跑引擎 JIT）跑 `bench_u1`：

```
bench_u1   native 123.0 ms   jit 367.8 ms   dispatches 1   chained ...
```

`dispatches` 是引擎主派发器的进入次数。2.68 亿次块转移里，
**派发器只被进入 1 次** —— 之后块与块之间是一条 `B` 直跳（块链）。
客户机里跑同一段（`HVB=u1`）得到 371.8 ms，和宿主侧 367.8 ms 对得上。

## 3. 那 MMU 呢？

访存微基准（`bench3 mem`，8 KB 工作集 load+store）：

| | 原生 | TCG | 本移植 | TCG vs 原生 | 本移植 vs 原生 |
|---|---|---|---|---|---|
| `mem` | 5.51 | 13.83 | 9.14 | 2.51× | 1.66× |

**两边都是软件 MMU，代价都在 1.5–2.5 倍这个量级，跟 5.1 倍不是一个数量级。**
所以"同样是软件 MMU，凭什么差这么多"这个问法本身指向了错误的部件。
真正的重灾区是下面这张表里的 `call` 和 `real`：

| 负载 | 原生 | TCG | 本移植 | TCG vs 原生 | 本移植 vs 原生 |
|---|---|---|---|---|---|
| `alu`（纯寄存器） | 5.93 | 9.98 | 6.00 | 1.68× | 1.01× |
| `mem`（访存） | 5.51 | 13.83 | 9.14 | 2.51× | 1.66× |
| `call`（4 亿次 noinline 调用） | 2.73 | 36.66 | 5.14 | **13.4×** | 1.88× |
| `branch`（数据相关分支） | 2.70 | 8.25 | 3.31 | 3.06× | 1.23× |
| `real`（qsort + 指针追逐 + 哈希） | 2.90 ms | 125.3 ms | 10.2 ms | **43.2×** | 3.5× |

`call` 一项 TCG 慢 13.4 倍：`bl` 是直接调用（可静态链接），但 **`ret` 是间接跳转**，
TCG 必须退出 TB → 回到 `cpu_exec` 主循环 → 哈希查表找下一个 TB → 再跳进去。
本移植用间接跳转缓存（IJC）在 JIT 里就地解析，不出去。

内核和 systemd 是什么形态？**满地的 `bl`/`ret`、函数指针、`switch` 跳表。**
这就是为什么：

- 纯启动路径（内核 + 挂根，`fastboot=1`）：**2.36 s vs 11.94 s = 5.1×**
  —— 以访存和顺序代码为主，介于 `mem`(1.5×) 和 `call`(13.4×) 之间。
- 到 systemd 完全就绪：**17.1 s vs 126.5 s = 7.4×**（在另一台设备上重测，
  见末尾"更正"）—— fork/exec 每一步都是新地址空间 + 海量调用 + 超时轮询，
  正好踩在 `call` / `real` 那一档。

还有一层放大：**超时等待本身也要执行指令**。
这个 LXC 镜像带 `incus-growpart`、`apt-daily.timer` 这类注定失败的单元，
systemd 要陪它们把超时走完。在 TCG 上这些"空等"的循环被放大成真实时间。

## 4. 一句话总结

| 部件 | TCG 相对原生 | 本移植相对原生 | 是 5.1× 的主因吗 |
|---|---|---|---|
| 静态代码体积 | 12.62 条/客机指令 | 15.88 条/客机指令（更差） | 否 |
| 块粒度 | 5.01 条/块 | 5.03 条/块 | 否 |
| 纯 ALU | 1.68× | 1.01× | 否 |
| 软件 MMU / 访存 | 2.51× | 1.66× | 否 |
| **块转移开销** | **≈2.4 周期/次** | **≈0（块链，一条 `B`）** | **是** |
| **间接跳转（`ret`/`br`）** | 退出 TB + 哈希查表 | IJC 就地解析 | **是（更主要）** |

直通翻译器的价值不在"少翻译几条指令"，而在**块之间不需要回主循环**：
同 ISA 下一条 `B` 就能进下一块，间接跳转也有缓存兜住。
TCG 的通用设计必须假设"下一个块可能还没翻译、可能在任何架构上"，
每一步都要回主循环确认一次 —— 这个代价摊到 5 条指令一个块的内核代码上，就是 5 倍。

## 更正：这里的"≥34×"曾经是错的

本文早前写过"完整启动 25.5 s vs >15 min ⇒ ≥34×"。**那个数字不成立。**

后来换到一台有 root + KVM 的设备（OPPO PDYT20）上，用同一份 Debian 镜像、
同一套脚本重测，并把测量方法的所有漏洞修干净之后：

| | 加速器 | TCG | 比值 |
|---|---|---|---|
| `fastboot`（挂根） | 2162 ms | 9033 ms | 4.18× |
| 完整启动 | 17059 ms | 126546 ms | **7.42×** |

TCG 三次 127.0 / 125.5 / 126.5 s，波动 1.2% —— 它**能跑完**，只是慢 7.4 倍。

当初"永远不就绪"的真因是：`boot-efi.mount` 依赖失败后掉进 **`sulogin`
维护模式等键盘输入**，永远等不到人。不是慢，是卡住。**配置问题伪装成了性能问题。**

这次踩到的两个测量陷阱（都写进了 KVM-VS-ENGINE.md）：

1. **宿主侧 `timeout` 只杀 adb**，设备上的 QEMU 变成孤儿继续吃满一个核，
   污染后面所有测量。我因此一度测出 17→22→28 s 单调上升、然后又 60→35→31 s
   的荒唐数据。修法：超时放设备侧 + 每次前后 `pkill`。
2. **`timeout` 不认环境变量前缀**（把 `LD_LIBRARY_PATH=...` 当成程序名），
   必须 `timeout N env VAR=... cmd`。

教训：**"跑不完"和"慢"是两件事，必须看 guest 自己的 uptime 和启动进度**，
不能只看宿主墙钟。这一条比任何数字都重要。
