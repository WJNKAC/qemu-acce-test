# 第一步 + 第二步的实测结果

针对"先读码确认四个未知、再建测量"这份计划，这里是实际做完的结果。

**一句话结论：五个候选优化里有两个（#1 inline、#2 hoisting）引擎已经做完了，
第三个（#3 大页 bank）确实缺但取决于计数器；而 knee 曲线在 64 MB 处
量出一个 30× 的断崖 —— 那才是真正值得动手的地方。另外"60% 原生"可以销案了。**

---

## 0. 先纠正一个前提：迭代成本不是半小时

计划里写"每次改 core/ 要 macOS 构建 → devicectl → LLDB bless 384 MiB TXM，单轮半小时"。
**这里不成立。** 我们跑的是 Android/Linux 移植：

| | 这个项目 | WindowsiOS |
|---|---|---|
| 构建 | NDK clang，**`make` 约 15 秒** | Xcode 全量 |
| 部署 | `adb push` 300 KB，1 秒 | devicectl |
| JIT 内存 | `mmap(PROT_EXEC)` 直接用 | TXM 页签名，LLDB bless 384 MiB |
| 单轮迭代 | **约 20 秒** | 半小时起 |

所以"先读再改、别用试错"这条纪律在这里**不必要**。实测也确实如此：
这一轮的 knee 基准从写代码到出曲线，总共改了 4 次、重建 3 次 Image，
加起来不到十分钟。**该做的实验就该直接做，不用为了省迭代成本而保守。**

（代价是另一个：设备侧测量容易被污染——孤儿进程、DVFS、瞬时频率。
见第 5 节。真正的纪律在这里。）

## 1. 四个未知，全部读码确认

| # | 未知 | 结论 | 证据 |
|---|---|---|---|
| 1 | 访存 TLB 探测是内联还是 BL callout | **内联**，慢路径是行外 `ool` | `translate_excl_pair`：`put_tlb_slot` → `ldr` tag → `sub` → `sub ADJ` → `ubfm` 比较 → `cbnz` 跳行外 |
| 2 | 一个块里多次访存是否逐次探测 | **不逐次 —— 已经做了分组 hoisting** | `Emit.grp[]` / `plan_groups` / `cpu->gaddend[4]` |
| 3 | 慢路径有没有读 PDE 大页位 | **读了，但只用于校验 + Bloom，没有大页 bank** | `tlb_fill`：`w->block_size` 参与判断，填充仍是 4 KB 粒度 |
| 4 | HvTlbStash 是逐槽拷贝还是 ASID 分 bank | **逐槽拷贝** | `stash_drop` / `hv_tlb_switch_user`：`s->ent[k++] = *e` 逐条复制 |

### 未知 1：内联，没有 callout

快路径实测指令序列（来自 `put_tlb_slot` + `translate_mem_impl`）：

```
ubfm  T, va, #12, #25      取页号
add   T, x28, T, lsl #5    (表-主序) 定位到 HvTlbEntry
ldr   15, [T, #tag_off]    读 read_tag / write_tag
sub   15, va, 15
sub   15, 15, #15          (HV_TLB_ADJ)
ubfm  15, 15, ...          检查落在本页内
cbnz  15 -> 行外 slow     失败才出去
add   15, va, addend       客机地址 -> 宿主地址
<原访存指令>
```

**约 6–8 条，和计划里估的"inline 只要 ~6-8 条 host 指令"完全一致。**
计划担心的"callout 每次多付 20–40 周期"在这里不存在，**#1 不用做**。

### 未知 2：分组 hoisting 已经实现了，而且比计划更完整

`core/translate.c:55` 的 `Group` 注释和实现：

| 参数 | 值 | 含义 |
|---|---|---|
| `MAX_GROUPS` | 8 | 一个块最多 8 组 |
| `GROUP_SLOTS` | 4 | `cpu->gaddend[4]` 个 addend 缓存槽 |
| `GROUP_SPAN` | 2048 | 一组最多覆盖 2 KB（严格小于 4 KB − `HV_TLB_ADJ`） |
| `GROUP_INSNS` | 48 | 一组最多 48 条指令 |

机制：**同基址**的多次访存，第一条探测整个覆盖范围、把该页宿主 addend 存进
`gaddend[slot]`；后续几条直接用，**不再探测**。探测失败时走 `copy_at` ——
从组的第一条到 `end` 用逐条普通翻译重跑一遍再回来。

计划里写的"发射一次探测 + 一个运行时 guard，整块共享 addend"，就是这套东西。
而且它比计划多一层保护：`GROUP_SPAN` 卡在 2048 是因为快路径要求访问不落在
页尾 `HV_TLB_ADJ` 字节内，超过 2 KB 的范围就可能跨这个禁区。
**#2 不用做。**

### 未知 3：真是缺口 —— 读了大页位，但没有大页 bank

```c
static void tlb_fill(HvCpu *cpu, uint64_t va, int el, const HvWalk *w) {
    if (w->block_size < (1ull << HV_TLB_PAGE_BITS)) return;   /* 小页只管慢路径 */
    ...
    uint64_t page_pa = w->pa & ~PAGE_MASK;      /* ← 仍然按 4 KB 切 */
    uint64_t page_va = va & ~PAGE_MASK;
    ...
    if ((cpu->sctlr_el1 & 1) && w->block_size > (1ull << HV_TLB_PAGE_BITS) && cpu->pc_state) {
        if (w->block_size <= (1ull << 21)) {     /* ← 大页只用来喂 Bloom */
            uint32_t h = hv_large_2m_bit(page_va);
            __atomic_or_fetch(&cpu->pc_state->large_2m_bloom[h >> 6], 1ull << (h & 63), ...);
        } else { ... large_big_bloom ... }
    }
}
```

所以：**大页被识别了，但只用于范围 TLBI 的安全性判断（Bloom filter），
映射仍然是"一个 2 MB 块 = 512 个独立 4 KB 表项"**。

这是计划里唯一一个"确实没做"的项。但它的收益**不是每次访问更便宜**
（每次访问照样 1 次探测），而是：

- **TLB 容量**：一个 2 MB 区域占 512 个槽，占 16384 槽 TLB 的 1/32
- **填充次数**：整段 2 MB 要 512 次 `tlb_fill`，每次一次软件走查

所以它的价值取决于"2 MB 块占多少比例"——**正好是计划里说的那个计数桶**。
这个桶现在**不存在**（`tlb_miss_kind[4]` 只分 EL0/EL1 × empty/conflict），
要做得加一个计数。见第 3 节的判断。

### 未知 4：逐槽拷贝已确认

```c
if (s) { s->slot[k] = code; s->ent[k++] = *e; }   /* 每槽 32 字节，逐条复制 */
memset(e, 0x80, sizeof *e);                        /* 逐条清 */
...
for (uint32_t j = 0; j < r->n; j++) {              /* 恢复也是逐条 */
    *e = r->ent[j];
    ... write_guard(...)                           /* 还要逐条重新校验可写性 */
}
```

参数：`HV_STASHES = 8` 个 bank、`HV_STASH_CAP = 1024` 槽/bank、
`HV_USER_FILLS = 2048`（超过就退化成全表扫描）、bank 键是 **`ttbr0` 不是 ASID**。

`ttbr0` 做键这一点值得注意：计划担心"ASID 会被回收复用，bank 键必须区分代际"。
**用 `ttbr0` 做键天然避开了这个问题** —— 不同进程的 TTBR0 值不同，
复用 ASID 也不会撞上旧 TTBR0。所以 stash 已经躲开了计划里列的那个正确性坑。

## 2. 已有测量：比计划想的更全

上游 `dispatch.c` 的 `--stats` 已经输出这些分类计数（我们只是之前用 `HV_SUM` 没印）：

| 输出项 | 对应的计划需求 |
|---|---|
| `tlb misses K/s: el0 empty / el0 conflict / el1 empty / el1 conflict` | 计划的"miss 按原因分桶"（粒度略粗，但 ASID/tag 冲突已分开） |
| `slow mem causes K/s: mmio / code-page write / page end / tlb miss / other / entry-but-tag` | 慢路径原因 |
| `process switches: N/s saved, M/s restored (K entries each)` | stash 的实际槽数 |
| `inline words per insn %.2f: copy X%xY branch-reg ...` | **按指令类别统计的放大比** —— 等价于我从 JIT dump 手算的那张表 |
| `misses at: RET / BR-BLR / B-BL / conditional / MSR / other` | 间接跳转 miss 分桶 |

**唯一缺的就是"大页"桶。** 需要时加一个 `large_fills` 计数器即可（`tlb_fill` 里
`block_size > 4 KB` 时递增），一处改动、一个字段。

用法：`hv-linux ... --stats`（`HV_SUM` 只印 6 项汇总，分类要看 `--stats`）。
注意 `stats_interval` 是门控：只给 `HV_SUM=1` 不加 `--stats`，所有计数器都是 0 —— 踩过。

## 3. knee 曲线：64 MB 处有一个 30× 的断崖

新写的基准 `work/knee.c`：**每 4 KB 页只放一个 64 字节节点，随机环遍历**。
这样每次访问必然换页、但只碰 4 MB 的 cache line —— 把 cache 影响压到最低，
测到的差异基本就是 TLB。步数固定 2^24，三个变体跑同一个二进制。

单位 ns/access（越低越好），绑 cpu6/7、`performance`、2.0 GHz：

| 工作集 | 页数 | 原生 | KVM | **加速器** | 加速器/原生 |
|---|---|---|---|---|---|
| 64 KB | 16 | 2.01 | 2.01 | 7.13 | 3.5× |
| 128 KB | 32 | 2.02 | 2.03 | 8.01 | 4.0× |
| 256 KB | 64 | 2.91 | 2.88 | 7.31 | 2.5× |
| 512 KB | 128 | 4.42 | 4.42 | 7.68 | **1.7×** |
| 1 MB | 256 | 6.79 | 6.34 | 16.57 | 2.4× |
| 2 MB | 512 | 10.86 | 13.61 | 29.63 | 2.7× |
| 4 MB | 1024 | 15.03 | 15.82 | 35.42 | 2.4× |
| 8 MB | 2048 | 13.73 | 15.94 | 37.39 | 2.7× |
| 16 MB | 4096 | 13.90 | 14.36 | 38.21 | 2.8× |
| 32 MB | 8192 | 14.92 | 14.75 | 40.55 | 2.7× |
| **64 MB** | **16384** | 15.81 | 16.00 | **42.01** | 2.7× |
| **128 MB** | **32768** | 16.99 | 17.59 | **506.59** | **29.8×** |
| **256 MB** | **65536** | 19.48 | 20.43 | **566.96** | **29.1×** |

### 怎么读

1. **原生与 KVM 两条线基本重合，一路平到 256 MB。** KVM 的 stage-2 嵌套分页
   在这里几乎不要钱（128 MB：17.6 vs 17.0）。

2. **加速器在 64 MB 以内是 1.7–4.0×**，和微基准 `mem`（1.87×）同量级。
   最好的一档是 512 KB（1.74×）—— 工作集小到 TLB 命中率 100%，
   剩下的就只是那 6–8 条指令。

3. **64 MB → 128 MB 之间跳了 12 倍**（42.0 → 506.6）。
   拐点位置和源码里的注释精确对上：

   > `#define HV_TLB_BITS 14 /* 16384 entries per EL: 64 MB of 4 KB pages */`

   16384 页正好 = 64 MB。到 128 MB（32768 页）就是 **2× 超订**，
   直接映射的表 → 命中率崩到 ~0，**每次访问都走软件页表走查**。

4. `--stats` 佐证了这个机制：整轮（13 档 × 2^24 步 = 2.18 亿次访问）
   报 **`tlb_refills = 33,903,157`**。其中 128 MB 与 256 MB 两档各 1677 万次
   ≈ 3350 万，**基本就是这两档贡献的**。反推每次 refill ≈ **500 ns**。

### 这个数字为什么重要

计划里担心的是"每次访存多付 20–40 周期的 callout"。实际情况相反：
**常态访存只多 6–8 条指令，但一旦工作集越过 TLB 覆盖半径，每次访问要付 500 ns**
（软件走查，~1000 周期）。

也就是说：**这个引擎的性能风险不在稳态，而在容量。**
跑微基准（8 KB 工作集）永远看不到它。

## 4. "60% 原生"可以销案了

这个数字之前没有出处。现在有实测（同一台设备、同一批二进制、四方对比）：

| 负载 | 加速器 / 原生 |
|---|---|
| `alu` | 1.00× |
| `mem`（8 KB 工作集） | 1.87× |
| `call` | 1.85× |
| `branch` | 1.50× |
| `real` | 4.92× |
| **几何平均** | **1.91× = 52% 原生** |

所以"52%"是对的，"60%"接近但不准。而且**这个数字高度依赖工作集**：
knee 曲线里从 1.74×（512 KB）到 29.8×（128 MB）都有。
**引用单个百分比没有意义，必须带工作集。**

## 5. 测量的坑（这轮踩到的，比计划里列的更要命）

### 5.1 频率读数是会变的，不能只读一次
`scaling_max_freq` 我先读到 **1274000**，据此在所有文档里写了"大核被限在 1.274 GHz"。
后来再读变成 **2000000**，而依赖加法链标定给出 **1.996 GHz**。
那个 1274 是瞬时状态（某个 power hint 打开了）。**结论：频率必须实测标定，不能读一次 sysfs 就当常数。**

副作用：我此前用 1.274 GHz 做的周期换算全部要重算。
`call` 的 4.01 ns 差额在 2.0 GHz 下是 **8 个周期**，而 17 条宿主指令 ÷ 4 宽发 ≈ 4.25 周期 ——
**只解释了一半**。剩下约 3.75 周期不在指令发射上（可能在块退出/链填/分支预测上）。
这不改变"指令条数是主因"的量级判断，但也不能再声称"完全对上"。

### 5.2 孤儿进程与设备侧超时（上一轮已记，仍然有效）
宿主 `timeout` 只杀 adb；设备侧必须 `timeout` + 前后 `pkill`。

### 5.3 `timeout` 不认环境变量前缀
必须 `timeout N env VAR=... cmd`。

### 5.4 `HV_SUM` 不带 `--stats` 时所有分类计数器为 0
因为每个计数器都被 `if (m->stats_interval)` 门控。第一次跑出一排 0，白跑一轮。

## 6. 修正后的优先级

计划里的五项，按实测重排：

| 计划项 | 结论 | 动作 |
|---|---|---|
| #1 inline 探测 | **已经内联**，6–8 条 | ~~做~~ |
| #2 same-page hoisting | **已经实现**，还带 2 KB 跨页保护 + `copy_at` 回退 | ~~做~~ |
| #3 大页 fast path | 真缺，但收益只在"填充次数 + TLB 容量"，不在每次访问 | **先加 `large_fills` 计数桶再定** |
| #4 TLB 容量 | **knee 曲线直接给了答案：拐点在 64 MB** | **升级为第一优先级** |
| #5 stash bank 化 | 逐槽拷贝确认，但 `ttbr0` 做键已避开 ASID 复用坑；切换只 1/s（这台设备） | 观察，暂不动 |

**新的第一优先级应该是 #4（TLB 容量）**，理由是它由曲线直接支撑，而且代价可算：

- `HV_TLB_BITS` 14 → 15：16384 → 32768 槽/表，覆盖 64 MB → **128 MB**
- 内存代价：`HvTlbEntry` 32 字节 × 32768 × 4 张表 = **4 MB**（现在 2 MB）
- 预期：128 MB 档从 507 ns 回到 ~42 ns 量级

但先别急着改：**要确认目标负载真的会越过 64 MB**。
Linux 启动和 `bench3` 都在里面；能越过的只有"大堆 + 随机访问"这一种形态。
判断方法：跑一次真实负载的 `--stats`，看 `tlb_refills` 速率。

### 关于 #3 的判定方法（如果要做）
加一个计数器就够了：`tlb_fill` 里 `block_size > 4 KB` 时递增 `large_fills`。
- 若 `large_fills` 相对总填充数很小 → Linux 客户机没在用大页 → **跳过 #3**
- 若很大 → 一个 2 MB 区占 512 槽，值得上第二级 bank

注意这跟 Windows 的预期不同：ARM64 Linux 内核文本通常用 4 KB 页映射，
只有 THP（用户态匿名大页）才给 2 MB 块。所以**在 Linux 客户机上 #3 的价值
大概率低于 Windows 场景** —— 这需要计数确认，不能照搬。

# 第二轮：BITS 14→16、PMD bank、以及两条负结果

## 1. BITS 14→16：断崖从 64 MB 右移到 256 MB

改一个常量做不到 —— 有三处必须一起改，否则要么编译失败、要么静默出错：

| 依赖点 | 为什么 | 改法 |
|---|---|---|
| `HV_CPU_RET_TAB` | 硬编码 0x201000（"紧跟 TLB、4 KB 对齐"）。TLB 从 2 MB 变 8 MB 后 `ret_pad` 算出负数 | 按 TLB 末尾向上对齐到 4 KB：0x801000 |
| `user_fills[]` / `kernel_fills[]` / `HvTlbStash.slot[]` | 是 **uint16_t**，存 `hv_tlb_code()` = `table<<BITS \| slot`。BITS=14 时最大 65535 正好放满；BITS=16 时最大 262143，**静默截断 → 往错表项写 → 随机内存错误** | 升到 uint32_t |
| `HvCpu` 大小 | 4.3 MB → 10.3 MB，`static HvCpu cpus[8]` 的 BSS 从 34 MB 到 82 MB | 接受（8 GB 设备） |

实测（`work/knee.c` 扩到 1 GB 上限，每 4 KB 页一个节点、随机环、2^24 步、2.0 GHz 锁频）：

| 工作集 | 原生 | **BITS=14** | **BITS=16** | 14 的比值 | 16 的比值 |
|---|---|---|---|---|---|
| 4 MB | 29.8* | 35.4 | 29.8 | 1.19× | 1.00× |
| 8 MB | 32.5* | 37.4 | 32.5 | 1.15× | 1.00× |
| 64 MB (16384 页) | 15.8 | 42.0 | 41.7 | 2.66× | 2.64× |
| **128 MB (32768 页)** | 17.0 | **506.6** | **59.7** | **29.8×** | **3.5×** |
| **256 MB (65536 页)** | 17.6 | **567.0** | **77.2** | **32.2×** | **4.4×** |

*4/8 MB 是同一批 BITS=16 运行的相邻档，无 BITS=14 对应值。

`tlb_refills` 从 **33,903,157** 降到 **170,736**（198 倍）。

**断崖位置精确等于 `HV_TLB_SIZE × 4 KB`**：BITS=14 → 64 MB；BITS=16 → 256 MB。
这一条把"knee 拐点 = 槽数 × 页大小"从推测变成了实测。

### BITS=16 对真实启动没有帮助

同一 Debian 12、2 vCPU、锁频 2.0 GHz、干净构建：

| | BITS=14 | BITS=16 |
|---|---|---|
| `SYSTEM_READY` uptime | 11.25 s | 11.38 / 11.47 / 11.46 / 11.33 s |

**持平。** 启动的工作集远小于 64 MB，本来就命中。所以这项优化的受益者是
"大堆 + 随机访问"的负载，不是启动。**不要用启动测 TLB 容量。**

## 2. PMD bank：桶计数了，结论是"不值得"

按计划先加桶、再决定。实现是在慢路径前挂一个 512 项直接映射缓存（epoch 失效），
`PMD_BANK=2` 只计数、`PMD_BANK=1` 启用。

### 桶读数：2 MB 块占 77% 的 refill

```
[sum] tlb_refills=136718
[sum] pmd: lookups=0 hits=0 fills=104680  (large_fills=104680)
```

**104,680 / 136,718 = 77% 的页表走查来自 2 MB block。**
这比预期高得多 —— ARM64 Linux 内核文本常用 4 KB 映射，但这里 THP 和内核
线性映射的大页占了绝对多数。

### 但启用后一点没快

| 工作集 | 无 PMD | PMD=1（命中率 64%） |
|---|---|---|
| 64 MB | 41.7 | 38.5 |
| 128 MB | 59.7 | 63.0 |
| 256 MB | 77.2 | 80.9 |
| 512 MB | 477.6 | — |

**差异全在噪声内，256 MB 还略差。**

### 为什么

PMD 命中省掉的只是 `hv_mmu_walk` 里 4 次 `read_desc`（每次一个 acquire 原子 load），
约 20–40 周期。而 refill 的真实成本在别处 —— 500 ns ≈ 1000 周期里，
走查只占一小部分。剩下的在：

- `tlb_fill` 里的 `write_guard`：**每次填可写项都要 `__atomic_thread_fence(SEQ_CST)`**
- 逐个 `memset(e, 0x80, sizeof *e)` 和 tag 计算
- 以及 refill 之后回到翻译代码的重入开销

**结论：桶里 77% 看着很诱人，但它度量的不是瓶颈。**
"大页占比高" ≠ "页表走查是成本"。这就是为什么要先做最小改动再量，
而不是看到高占比就直接上第二级 bank。

### 顺带修掉一个自己引入的正确性问题

第一版 PMD 命中时把权限硬编码成 `w.r = w.w = w.x = 1`。后果有两个：
1. 只读页也会调 `write_guard`（含 SEQ_CST 全屏障）→ `slow_accesses` 涨 76%
2. **写只读页不再被拦住** → 正确性 bug

改成缓存并取回真实 `r/w/x` 后才对齐。**任何"重建一个 HvWalk"的做法都必须带权限位**，
否则省下的时间是拿正确性换的。

PMD 代码保留在 `PMD_BANK=1/2` 分支里作为可复现的证据，**默认不启用**。

## 3. 负结果：BITS≥17 被 ADD 的 imm12 编码挡住了

想覆盖更大的工作集（目标 8 GB guest），自然想 BITS=17（512 MB）或 18（1 GB）。
实测 BITS=17 **一跑就 JIT fault**：

```
guest_pc=0xffff8d599ab8 el=0    ← EL0 的 PC 变成了内核地址
table 0: tag=0xffff4a855ff1 addend=0xffff00744d236000 -> ...  ← addend 被写坏
```

根因在 `put_call` / `put_return` 定位返回地址表的这一条：

```c
put(e, 0x91400000u | (off >> 12) << 10 | 28 << 5 | 7);   /* add x7, x28, #imm12, lsl #12 */
```

`off = HV_CPU_RET_TAB + (flags & 15) * 0x20000 + hash * 16`，而 **imm12 最大 4095**：

| BITS | ret_tab 基址 | off 最大值 | `off>>12` | 结果 |
|---|---|---|---|---|
| 14 | 0x201000 | 0x3EFFC0 | 0x3EF = 1007 | ✓ |
| 16 | 0x801000 | 0x9EFFC0 | 0x9EF = 2543 | ✓ |
| **17** | **0x1001000** | **0x1200FC0** | **0x1200 = 4608** | **✗ 溢出到指令其他字段** |

编码溢出后 `x7` 算出的不是 ret_tab，写进去的是野地址；下一次 `ret` 就跳到那里。
**这就是 PC 变成内核地址的原因。**

### 修法（没做，留给下一步）

盘一下：`tlb` 的寻址是 `add x7, x28, xT, lsl #5`（寄存器移位，无限制），
table 偏移是 `table × (HV_TLB_SIZE×32/4096)` = table×1024（BITS=17 时 ≤2048，安全）。
**只有 ret_tab 这条 ADD 受限**，因为它在 16 MB 之外。

方案：把 `ret_tab` 挪到 `tlb` **前面**（`HV_CPU_RET_TAB = 0x1000`，
`HV_CPU_TLB = 0x201000`）。这样 ret_tab 的 `off>>12` 最大 0x201 = 513，安全；
而 tlb 的寻址不受 imm12 约束。

代价：交换 HvCpu 里两个大字段的顺序，所有 `HV_CPU_*` 偏移常量和静态断言要跟着调。
**在动 BITS≥17 之前必须先做这个**，否则一定 fault。

自己所在目录**，永远命中原版。必须用 `-include build/core/cpu.h` 抢先展开

# 第三轮：拆 refill 的 1000 周期 —— 假设被推翻，我找错了对象

## 0. 先说结论

| 我原本的怀疑 | 实测 | 判断 |
|---|---|---|
| `write_guard` 的 SEQ_CST 全屏障 | 删掉 fence：**0 收益** | ❌ 不是 |
| `write_guard` 的原子 RMW | bloom 改非原子：**0 收益** | ❌ 不是 |
| `write_guard` 整体 | 整个跳过：**-30%（475→334 ns）** | ✅ **是，但原因不是屏障** |
| `code_pages[pg]` | 不读：**0 收益** | ❌ 不是 |
| **`whint` 数组** | 彻底不碰（load+store 都跳）：**-28%（475→341 ns）** | ✅ **真凶** |
| 直接映射 TLB 的冲突形状 | 索引折一位高位：**-28%（475→341 ns）** | ✅ 叠加因素 |

用户判断"证据指向 write_guard"——**方向对了一半**：`write_guard` 确实是 30%，
但**原因不是屏障，是 `whint` 数组的 cache miss**。删屏障、改原子，一分钱不省。

## 1. 先证明分桶这条路走不通（这是必要的第一步）

`cntfrq = 13 MHz`，1 tick = **77 ns ≈ 154 周期**。而单段只有 10–270 ns。

埋 8 个点、累加 3400 万次 refill 后得到：

```
[prof] refills=34667520  ticks/refill=4.64
[prof]   A walk                    3.50 tick   269.4 ns   75.5%
[prof]   D1 fill-pre               0.19 tick    14.7 ns    4.1%
[prof]   C entry-write             0.19 tick    14.3 ns    4.0%
[prof]   B1 write_guard/whint      0.21 tick    15.8 ns    4.4%
[prof]   B2 write_guard/fence      0.19 tick    14.3 ns    4.0%
[prof]   D3 bloom+ret              0.19 tick    14.2 ns    4.0%
[prof]   call overhead             0.18 tick    14.1 ns    4.0%
```

**但这个结果自相矛盾**：它说 walk 占 269 ns，可是把 walk 整个跳过
（PMD cache，命中率 99.4%）之后，512 MB 档**反而从 518 ns 变慢到 756 ns**。

如果 walk 真值 269 ns，跳过它不可能更慢。**所以 A 段的 269 ns 是伪影。**

伪影来源：`mrs cntvct_el0` 在这台设备上的读延迟远大于 1 tick，
而且不加 `isb` 时会被 OoO 重排。8 个点里每段都继承一份这个延迟。
基线校准（连续两次 `hv_prof_now()` 相减）读出 **0.00 tick** —— 因为两次读间隔
小于 1 个计数器周期。**校准自己也测不出来，这条路就废了。**

教训：**13 MHz 的计数器不适合测量 10–500 ns 的分段**。要么用 PMU
（`PMCCNTR_EL0` + `PMCR_EL0` 分频，或 `PMU` 事件计数），要么改用消融。

## 2. 改用消融：直接删一段，看端到端差多少

消融没有分辨率问题（差异是几十上百 ns），而且是**因果**证据。
`ABL=n` 生成不同变体（`tools/build_variant.sh 16 0 0 n`），同一档 512 MB、各 2 次：

| 变体 | 做了什么 | 512 MB knee (ns/access) |
|---|---|---|
| ABL=0 | 基线 | 474.1 / 476.0 |
| ABL=2 | 删 `write_guard` 里的 `SEQ_CST` fence | 473.2 / 475.9 |
| ABL=3 | `large_*_bloom` 原子 OR → 普通 RMW | 473.0 / 477.5 |
| ABL=4 | 上面两个一起 | 473.6 / 473.2 |
| **ABL=5** | **完全不碰 `whint`（load + store 都跳）** | **341.8 / 341.0** |
| ABL=6 | 不读 `code_pages[pg]` | 475.5 / 474.7 |
| **ABL=1** | **整个 `write_guard` 不调用** | **334.5 / 333.5** |

读法：

- **fence 是免费的**（-0.2%，噪声内）。单核下 `dmb ish` 本来就只有十几周期，
  不是 600 周期的大头。**用户的这个假设可以彻底划掉。**
- **原子 bloom 也是免费的**（A76 有 LSE，`ldset` 一条指令）。
- **`code_pages` 免费** —— 512 KB 数组，热点集中，命中率高。
- **`whint` 是 133 ns（28%）**，且占了 `write_guard` 总量（140 ns）的 95%。

`whint` 是什么：`ram->whint[pg * HV_MAX_CPUS + cpu->index]`。
2 GB guest = 524288 页 × 8 CPU × 8 字节 = **32 MB 数组**，
按页号随机索引，每次填充必然 miss。

它的用途只有一个：当某页**变成代码**时，知道该丢哪个 TLB 表项。
在 Linux 客户机里（W^X，可写页通常不会变成代码），这几乎从不发生，
但每次可写填充都要付一次 32 MB 数组的 cache miss。

> 消融自身也踩了一个坑：ABL=5 第一版只把 `old` 置 0，块里的
> `__atomic_store_n(hint, ...)` 仍在执行 —— **store 要 RFO 拿 cache line，
> 一样 miss**，所以第一版测出"0 收益"。必须连 store 一起跳才看得出来。

## 3. 断崖的真正形状：不是容量不够，是确定性互踢

索引是 `(va >> 12) & (2^BITS - 1)` —— 纯低位直接映射。

knee 走的是**随机环**（每条边恰好一次，零复用）。这种模式下：

- 工作集 ≤ 槽数（256 MB = 65536 页 = 65536 槽）→ 整环装得下 → 命中率 ≈ 100%
- 工作集 = 2× 槽数（512 MB）→ 第 p 页与第 p+65536 页**永远落在同一槽**，
  随机访问下必然互踢 → 命中率 **≈ 0**（不是容量决定的 50%）

**这就是"断崖"而不是"缓坡"的原因。** 容量不足本该是线性退化，但确定性冲突让它变成悬崖。

验证：把索引折一位高位（`HASH=1`，热路径 +2 条指令）：

| 工作集 | 基线 | HASH=1 | 变化 |
|---|---|---|---|
| 128 MB | 62.4 | 61.6 | -1% |
| 256 MB | 77.2 | 74.2 | -4% |
| **512 MB** | **474.7** | **340.7** | **-28%** |

折一位就把命中率从 ~0 拉回"容量决定的 50%"。**但只有 50%** —— 因为容量确实是 2 倍超订。

## 4. 所以我判断错了方向，而且改法也是错的

- **BITS 14→16 是"传统 VMM 思路"**：把每条目 4 KB 的软件 TLB 做大，
  BSS 从 34 MB 涨到 82 MB，断崖只右移一倍，还撞上 `ret_tab` 的 imm12 墙。
- 对 2–5 GB 的客户机，这条路**无论如何走不到头**：
  要覆盖 2 GB 需要 BITS=20，即每 CPU 128 MB × 8 = 1 GB BSS。不可行。

真正该做的，是让**一项 TLB 覆盖多个页**：

- 2 MB 大页在 TLB 里按 1 项记（而不是 512 项）→ 等效覆盖 ×512，
  256 MB 工作集只需要 128 项。这才是数量级的解。
- 这正是之前做的 `PMD_BANK`，但我**测错了**：当时（a）knee 上限只有 256 MB、
  没测到 512 MB 档；（b）`whint` 的 133 ns 掩盖了收益。

### 但 PMD 现在有个未解的异常，不能直接采信

用 1 GB knee 重测 PMD=1（BITS=16，无 HASH）：

| 工作集 | 无 PMD | PMD=1 |
|---|---|---|
| 128 MB | 59.7 | 63.3 |
| 256 MB | 77.2 | 76.3 |
| **512 MB** | **518.6** | **756.1** |

命中率 **99.4%**（`hits=34.2M / (hits+lookups)`），却比不命中还慢 46%。
说明 PMD 实现里有 bug，我怀疑是：

`pmd` 只缓存了 `r/w/x` 一份，而**同一个 2 MB 块里不同页权限可以不同**
（THP 里只读页与可写页并存）。命中后拿到错权限 → 走慢路径 → 反而更慢。

正确做法：pmd 只缓存**页表走查的前 3 级结果**（L0/L1/L2 的基址），
第 4 级 PTE 仍然读 —— 权限和存在性保持按页精确，只省掉 3 次 descriptor 读。
这个改动很小，但我没做（本轮时间到了）。

## 5. 这一轮的净结论

1. **屏障、原子操作不是瓶颈**，可以彻底从怀疑列表划掉。
2. **`whint` 值得优化**（30%）：32 MB 的 per-page×per-CPU 数组，为一件
   "可写页变成代码"这种 Linux 下几乎不发生的事，每次填充付一次 cache miss。
   方向：合并成每页一个字节（CPU 用位掩码），或按"是否可能出现代码页"分档。
3. **断崖是确定性冲突，不是纯容量**；折一位高位（+2 指令）能省 28%，
   256 MB 以下无损。这个改动便宜且安全，可以考虑合并。
4. **真正的数量级解是让一项覆盖多页**（2 MB 大页 → 1 项），
   而不是继续加 BITS。但现有 PMD 实现有权限 bug，要先修。
5. **分桶测量在这台设备上不可用**（13 MHz 计数器），除非改用 PMU。

# 第四轮：THP 前提、whint 落地、以及"容量不是解"的第三次确认

## 0. 先接受一条更正

我上一轮说"做完 whint + PMD 前 3 级就能重回巅峰"是错的，而且错得自相矛盾：
**我自己写过"descriptor 全程在 cache 里"，那就同时判了"缓存前 3 级 descriptor"死刑**——
它要省的正是这几次 cache 命中的读取。这条降级为"不做"。

## 1. THP 前提：先确认再测量（这条决定后面全部结论）

之前所有 knee 测量都**没有** `MADV_HUGEPAGE`，也没有 2 MB 对齐，拿到的可能是 4 KB 页。
现在 `knee.c` 改成：

- `mmap` + 手工对齐到 2 MB（`aligned_alloc(PAGE,...)` 只有 4 KB 对齐，fault 时内核不给大页）
- `madvise(MADV_HUGEPAGE)`
- 打印 `/proc/meminfo` 的 `AnonHugePages` 与 THP 模式

客户机内核是 `CONFIG_TRANSPARENT_HUGEPAGE_ALWAYS=y`。实测：

```
[thp] before    AnonHugePages=0 kB (0.0 MB)        MemTotal=2966 MB
[thp] enabled = [always] madvise never
[thp] after     AnonHugePages=2097152 kB (2048.0 MB)   ← 100% 覆盖
```

**2 GB 缓冲全部落在大页上。** 前提成立，后面测的才是大页路径。

## 2. whint：真正的收益是"数组变小"，但**没有免费**

`whint` 是 `pages × HV_MAX_CPUS` 个 uint64：2 GB 客机 = **32 MB**，按页号随机索引。
消融实测它占 refill 的 28%。

改成**每页 1 字节的 CPU 位图**（2 GB → 512 KB，能进 L2）：

| 工作集 | 基线 | WHINT 位图 | 变化 |
|---|---|---|---|
| 256 MB | 74.7 | 78.1 | +4.6%（噪声） |
| 512 MB | 477.1 | **355.5** | **-25.5%** |
| 1 GB | 496.8 | **382.4** | **-23.0%** |
| 2 GB | 508.4 | **432.2** | **-15.0%** |

**同时修掉一个我自己引入的正确性漏洞**：`whint` 用 16 位字段存 `hv_tlb_code()`，
而 BITS=16 时编码是 `table<<16|slot`（最大 196607，需 18 位）→ **静默截断成 0**
→ 被当空槽跳过 → 代码页的陈旧可写表项永不失效。

### 代价：protect 时退化成整表扫描

位图只记"这个 CPU 写过这页"，不记"是哪个表项"，所以页变成代码时要扫
`HV_TLB_SIZE × 3` 项。实测 Debian 启动 `one entry 466/s` 这类调用会退化成扫描：

| | BITS=16 基线 | BITS=16 + WHINT 位图 |
|---|---|---|
| Debian 启动 uptime | 11.43 / 11.61 s | **12.90 / 12.90 s（+11%）** |

### 试图"只修 bug 不提速"的版本反而更慢，暴露了一件事

字段 16 位 → 20 位（3×20=60 位，仍装进 uint64），逻辑不变、不引入扫描：

| 512 MB | 613 ns |

**比"有 bug 的基线"（477）还慢。** 因为截断让编码恒为 0，`!c` 短路掉了
`maps_writable()` —— 那是**一次 TLB 表项解引用（8 MB 数组里的随机读）**。
所以那个"基线"是**靠 bug 白赚了一次 cache miss**。位图版把整个 `maps_writable` 也去掉了，
既正确又快，唯一代价是扫描。这也是选位图而不是加宽字段的理由。

## 3. 大页 bank：先把"2 MB 步长"这个病态暴露出来

给 knee 加 `STRIDE` 参数后，2 GB 工作集两种粒度：

| 步长 | 节点数 | 基线 | +WHINT |
|---|---|---|---|
| 4 KB（52.4 万页） | 524288 | 511.0 | 430.5 |
| **2 MB（1024 页）** | 1024 | **749.4** | **576.6** |

**2 MB 步长更慢**，而且只碰 1024 页（本该 ~100% 命中）。原因不是大页，是：

```
slot = (va >> 12) & 65535
2 MB 步长 → va>>12 每次 +512 → & 65535 每 128 个节点就绕回
1024 个节点只落到 8 个不同槽位 → 128 路冲突 → 命中率 ≈ 0
```

**4 KB 直接映射 TLB 在 2 MB 粒度的访问模式下是病态的。** 这反过来证明：
大页粒度的负载必须有按大页索引的 TLB，用 4 KB TLB 硬扛是没救的。

### 但 PMD bank 现在这版不行，原因量出来了

`PMD` 是 512 项直接映射（`(va>>21) & 511`）：

| 场景 | pmd 命中率 | 结果 |
|---|---|---|
| 2 MB 步长（1024 个大页） | **3.2%**（560562 / 17353015） | 592 → 601（更慢） |
| 4 KB 步长（2048 个大页） | 反而不升 | 426 → 584（更慢） |

**1024 个 key 打进 512 个槽 → 又是完美 2 路互踢，命中率≈0。** 同一个病。
而且即使命中，它也只省掉 walk（消融已证明 walk 只值 3%），还带着
`memset(&w, 0, sizeof w)` 的开销 —— 所以命中率 99% 那次也是更慢（518 → 756）。

**结论：bank 要成立必须（a）容量 ≥ 大页块数，（b）命中发生在快路径而不是 refill。**
两条都不满足时，它连"配菜"都不如。

## 4. 顺带：BITS=16 不能交付

| | BITS=14 | BITS=16 |
|---|---|---|
| 自测 `test_mmu` | **76 checks, 0 failures** | **段错误** |
| BSS（8 CPU） | 34 MB | 82 MB |
| knee 512 MB（+WHINT） | 352.4 | 355.5 |
| knee 2 GB（+WHINT） | 433.0 | 432.2 |

**BITS=16 性能与 14 完全相同，却多占 48 MB 并且让 `test_mmu` 崩溃。** 
这已经是第三次从不同角度确认：**加容量不是解**。已回退。

## 5. 现在的账（目标 2 GB，THP 100%）

| | 512 MB | 2 GB |
|---|---|---|
| 原生 | 31.0 | 104.0 |
| 引擎（BITS=14 基线） | 477.1 | 508.4 |
| **引擎（+WHINT 位图）** | **355.5** | **432.2** |
| 抬升倍数 | 11.5× | 4.2× |

原生自己也在涨（31 → 104，硬件 TLB 同样会 miss）。引擎几乎不涨（477 → 508），
说明它的单价在 miss 率 97% 时已经饱和 —— 这正是"容量决定 miss 率、单价决定每次 miss"的
分工。WHINT 砍掉了单价的 25%，平均访问只从 508 降到 432，因为每 8 次访问仍有 7.75 次在 miss。

## 6. 修正后的顺序

1. **~~whint 压缩~~** ✅ 已做（-25% @512 MB / -15% @2 GB）。**已知代价：启动 +11%**，
   需要下一步把它降到可接受（见 7）。
2. **大页 bank，但必须重做**：容量 ≥ 大页块数（2 GB → 至少 2048 项），
   且命中要在**快路径**。现有 512 项直接映射版命中率 3%，不能用。
3. **linear map fast path**：EL1 常数偏移。这条对启动/内核态有效，
   对 knee（EL0 指针追逐）零收益 —— 两条要分开量。
4. PMD 前 3 级 descriptor：**不做**（自证伪）。

## 7. 下一轮必须先解决的两件事

- **whint 的扫描代价**：现在是"每页一个 bit + 全表扫描"。折中方案是
  "位图 + 每页记 1 个表项编号"（uint32/页 = 2 GB → 2 MB），单表项精确失效，
  多表项才扫描。这样启动的 +11% 应该能吃掉大半。
- **bank 的索引**：不要再用 4 KB 低位的形状。按 `(va>>21)` 索引、容量 ≥ 块数，
  并且要考虑"快路径怎么在一次比较里判断命中大页"—— 这才是决定 2 GB 能不能到
  ~70 ns 的关键，而它需要改快路径的指令序列，必须重新量热路径开销。

# 第五轮：P₀ 锚点 + bank 落地（性能达标，正确性差一项）

## 1. P₀：快路径的价格标签

64 MB 全命中（THP 100%）、2.0 GHz 锁频、各 3 次：

| | native | engine | 差值 |
|---|---|---|---|
| 64 MB | 16.0–17.6 | **44.2–46.5** | **≈28 ns ≈ 56 周期** |

这 56 周期 = TLB 探测（`ubfm/add/ldr/sub/ubfm/cbnz` + `ldr addend`）+ 内联原子 + 寄存器压力。
**后面每次改热路径都用这个锚点做回归防线。**

## 2. bank：2 GB 439 → 114 ns（验收达标）

`HV_BANK_SIZE=2048`（2 GB→1024 块，×2 余量），16 B/项 = 32 KB，
放在 `HV_CPU_BANK = HV_CPU_RET_TAB + HV_IJC_TABLES*HV_RET_TAB_BYTES`
（**4 KB 对齐，且在那之前没有 C-only 字段**，所以不动任何已有偏移），
探针内联在 4 KB 探测**之前**：

```
lsr   T, addr, #21                    块号
and   T, T, #0x7ff                    索引（N=2048）
add   T, x28, T, lsl #4               16B/项
add   T, T, #0x401, lsl #12           bank 基址
ldr   U, [T]                          tag
sub   U, addr, U
ubfm  U, U, #21, #63                  与 4 KB 表项同款检查，粒度 2 MB
cbnz  U, 4k                           miss → 落回原 4 KB 探测
ldr   U, [T, #8]                      addend
b     after
```

结果：

| 工作集 | 基线 | **BANK** | |
|---|---|---|---|
| 64 MB（全命中） | 43.9 | **43.4** | **−1%（不退化，守住 P₀）** |
| 512 MB | 355.8 | **73.8** | **−79%** |
| **2 GB** | 439.3 | **114.3** | **−74%（验收 ≤150 ✓）** |

对照 native：512 MB 31.0 / 2 GB 104.0 —— **2 GB 档已经接近原生天花板（114 vs 104）**。

### 三个 bug，都是"静默错"类型

1. **`and` 立即数编码错**：写成 `(64-11)<<16 | 63<<10`（immr=53/imms=63），
   实际编成 `and x7,x7,#0xFFFFFFFFFFE00000`，索引变野值 → JIT SIGILL。
   正确是 `N=1, immr=0, imms=log2N-1`。
2. **`lsr` 源寄存器写成 T 而非 addr**：探测读的是未初始化的寄存器，
   症状是"fill 正常（18.4 M 次）、refill 一点没少"——最费时间的一个。
   靠 dump JIT 逐条解码才看出来（`d35584e7` 的 rn=7 而不是 6）。
3. **fill 的对齐检查要求 pa/va 都 2 MB 对齐**：那只允许块首页入 bank，覆盖 1/512。
   正确是"两者块内偏移相等"（块描述符保证 addend 全块恒定）。

## 3. 但有一个正确性洞没堵住：自修改代码

`test_exc` 的 `p_smc_nomaint` 失败（`1 then 2 after patching = 2, expected 3`）：

对代码页的**写**被 bank 直接放行 → 绕过 whint → 翻译没被作废 → 旧指令继续执行。

我加了两道防线，都**没能堵住**：

- fill 时要求"整块无代码页"（`ram->ncode == 0` 时跳过扫描，否则扫 512 字节）
- `protect_code_page` → `bank_drop_host_page`（按 host 地址反查覆盖它的块）

仍然失败，说明还有一条路径让带代码页的块进了 bank，或者 drop 的时序不对。
**这一项没查清之前不能交付**，交付版已回退到 WHINT-only（自测 53/0）。

（对照实验已确认：WHINT-only 的 `test_exc` 是 53/0，纯基线也是 53/0，
所以这个失败确实由 bank 引入，不是 WHINT。）

## 4. bank 版启动退化（未解决）

Debian 启动：基线 11.4–12.9 s → bank 版 **19.5 / 21.7 s**。
第一版是 30.8 s（每页 TLBI 都 32 KB memset），改成精确失效后降到 19.5 s，
仍然慢 50%。原因待查：可能是 8 条探测指令 × 每次访问 + bank 在启动工作集上
命中率低（启动的页多为 4 KB 且频繁被 TLBI 打掉）。

## 5. 结论与交接

| 项 | 状态 |
|---|---|
| P₀ 锚点 | ✅ 44.2 ns（64 MB） |
| bank 性能 | ✅ 2 GB 114 ns（≤150），512 MB 73.8 ns，64 MB 不退化 |
| bank 正确性 | ❌ SMC 一项失败，必须修完才能上 |
| bank 启动 | ❌ +50%，需查 |

**下一步（按优先级）**
1. 堵 SMC 洞：最可能的原因是"写入后填充"的时序 —— 建议在 `tlb_fill` 里
   **同时检查将要写入的那个页**是否 `code_pages`，并且把
   `bank_drop_host_page` 从 protect 时刻改成"每次 translate 一个块时"
   都做一次（代价小，块翻译本来就少）。
2. 启动退化：先量 bank 命中率（加一个 hist 计数器），若启动期命中率 <20%
   就考虑按"是否发生过 protect"动态启停 bank。
3. whint-hint（位图 + 每页一个表项号）留到 bank 落地后重估 ——
   理由与用户一致：bank 命中不走 fill，whint 的价值面被压缩。

# 第六轮：bank 落地（四个洞、一个必须交代的代价）

第五轮结束时 bank 性能达标但正确性差一项、启动慢 50%。这一轮正确性归零，
启动的 **memset/扫描那一半** 也归零，但同时量出一个之前没见过的、**真实存在的**
代价（每次访问都付探测税）。最终交付的是"只读 bank"。

## 1. 结果（同一会话、交错 A/B）

设备 A55、`performance`/2.0 GHz、THP 100%（`AnonHugePages=2097152 kB`）、
guest `--ram 2560 --cpus 1`、`KNEE` = 64 MB / 512 MB / 2 GB：

| 工作集 | 原生 | 基线（BITS=14+WHINT） | **bank（只读）** | 变化 |
|---|---|---|---|---|
| 64 MB | 17.3 | 47.5 | **43.5** | −8% |
| 512 MB | — | 353.1 | **76.2** | **−78%** |
| 2 GB | — | 440.4 | **117.8** | **−73%** |

启动（Debian 12 → `multi-user.target`，`hvrun=boot`，RAM=2048，两个二进制交错跑）：

| 核数 | 基线 | bank | 代价 |
|---|---|---|---|
| 2 | 25.48 / 28.67 | 31.81 / 32.12 | **+21%**（每档仅 2 样本） |
| 4 | 33.76 / 35.38 | 40.00 / 43.13 | **+18%**（每档仅 2 样本） |

> **这两个数是 2 样本，第七轮已用 5 样本重测并修正，见文末第七轮 §2b。**

**这是真实的代价，不是噪声**（同一时间窗交错，两个核数都复现）。
原因在 §5，处置建议也在那儿 —— 这一版**没有**把它消掉，只是搞清楚了它是什么。

自测（交付配置）：`test_classify` 43/0、`test_operands` 36/0、`test_mmu` 76/0、
`test_exc` **53/0**（第五轮挂的 `p_smc_nomaint` 已过）、`test_jit_region` ok。

## 2. 根因一：写被 2 MB 块整块放行（SMC 洞）

第五轮的两道防线（"整块无代码页"+"protect 时按 host 页反查"）都没堵住，因为
**洞在快路径，不在慢路径**：bank 探测读的是表项偏移 0 的 `read_tag`，
而 4 KB 路径是 `tlb + (op.store ? 8 : 0)` 分开的。于是：

```
store → 命中 bank 的 read_tag → 直接拿 addend 写宿主内存
      → 不填 4 KB 表项 → 不碰 whint → memop 看不到这次写 → 翻译不作废
```

`p_smc_nomaint` 期望 `1+2=3`，实际 `1+1=2`：第二次 `bl 3f` 跑的还是旧 `mov x0,#1`。

**先做实验再改设计**：把探测限制在 `!op.store`（`BANK_RD=1`），`test_exc` 立刻 53/0。
一个变量、一次构建（8 s），把"猜测"变成"结论"。

## 3. 顺手挖出的另外三个洞

### 3.1 bank 里没有地址空间键 → 跨进程读到别人的内存

`hv_tlb_switch_user` 按 `ttbr0` 收起/恢复 4 KB 表项（stash），bank 完全没有这一层：
进程切换后旧进程的块翻译对新进程是**错的 addend**。`test_mem` 一开始就崩在这里。
修法：切换时 `bank_invalidate`。代价是每次进程切换擦一次 —— 这也是 §5 的一部分。

### 3.2 全零的 tag = "从 VA 0 开始的块"

探测判据是 `addr - tag < 2 MB`：`tag = 0` 恰好等价于"该块从 VA 0 起"且 `addend = 0`，
于是 **VA < 2 MB 的访问全部假命中，直接读宿主地址 0**（tombstone: `fault addr 0x10000`）。
来源有两处：`hv_cpu_reset_index` 把整个 `HvCpu` memset 成 0；以及**任何没走过 reset
的 CPU**（静态 BSS 里的 `cpus[]`、测试里的 `static HvCpu`）。
所以修法不能只补 reset，得让它"自证干净"：

- `hv_bank_reset()`：复位末尾整表擦成 0x80（合法 tag 低 21 位恒为 `2MB-15`，0x80 不匹配）；
- `bank_ready` 标志：`bank_invalidate` 第一次被调用时若未就绪，退回整表擦，之后才走 live 表。

**这个洞只在自测里暴露**：生产 guest（Debian / QEMU）几乎不碰 2 MB 以下 VA。

### 3.3 一次 `pkill -f hv-` 把自己杀了

运行脚本 `work/rk.sh` 里写了 `pkill -f hv-`，而脚本自己的命令行里含 `hv-bank`：
症状是 exit 143、零输出。改成 `pkill -x <进程名>`。

### 3.4 启动的 +50% 里，有一半是"每次 fill 扫 512 页"

第五轮为"写也走 bank"加了"整块无代码页"检查，`ram->ncode != 0` 时每 **fill** 扫 512 页。
18 M 次 fill × 512 次读 = 几千万次无谓访存。只读 bank 不需要这个条件（读不改内存），
删掉后：19.5 s → 与基线持平（这一项已归零）。**剩下的是 §5 那 20%，与它无关。**

## 4. 结构性结论：为什么最终是"只读 bank"

引擎的**写撤销是页粒度的**（`code_pages` + `whint` 记 3 个表项号 + `page_gen`），
bank 是块粒度的授权。让块粒度缓存承载页粒度撤销，只能靠"时快照"条件
（"填充那一刻整块没有代码页"），而页面**随时**会变成代码页，于是必须再挂一条
"代码页出现 → 作废整块"的逆向通知 —— 这条通知又依赖 `code_pages` 的 0→1 边沿
（`dispatch.c` 只在第一次置位时调 protect）。这条链每一环都能被绕过（§2 就是第一环）。

所以最终设计选择**不参与**：

> **bank 只授权读，写永远走 4 KB 权威表。**
> 读没有撤销语义，bank 的正确性只依赖"映射变了就失效"这 8 条 flush 路径 + 进程切换，
> 不依赖任何时快照条件。

代价是写侧不加速。**实测这个代价 ≈ 0**：knee（读主导）2 GB 117.8 vs 读写版 113–114；
512 MB 76.2 vs 73.8。读写两开只多赚几 ns，却要买下整条易碎的撤销链 —— 不值。

## 5. 那 20% 是什么：快路径上的探测税

bank 探测放在 4 KB 探测**之前**，于是**每一次数据访问**（含 4 KB 映射、bank 永远
命中不了的那些）都要付 7 条指令 + 一次对 32 KB 数组的额外 load：

- 启动期的工作集以 **4 KB 映射**为主（slab、页表、用户页），`w->block_size < 2 MB`
  → 这些页永远进不了 bank → 探测 100% 是白付；
- 32 KB/CPU 的额外热足迹（4 核 = 128 KB）还会把这些行本该占的位置挤掉。

两条都随核数放大，正好解释"2 核 +21%、4 核 +18%（同一量级）"。

**下一步的最优解不是调参，是换位置**：把探测放进 `emit_ool` 的 refill 分支 ——
只有 4 KB 探测已经失败、正要走 ~500 ns refill 时才付出这 7 条指令；
命中就直接跳到"U = addend"的续点（`to_after`，本轮已经算好了）。
预估：启动税归零，大工作集的收益保留（那里本来就每次都在 refill）。
两个要量清楚的副作用：（a）每条访存指令的 OOL 会长 8–9 个字 → JIT 体积/局部性；
（b）OOL 命中后的返回目标要用 `patch_branch` 回填成一个**后向**分支，路径本身很短。
在这次交付里**没有做**，因为它要动 `emit_ool` 的形状，风险与本轮的收益不成比例。

临时处置：`BANK=0` 编一份基线（启动优先），`BANK=1 BANK_RD=1` 是交付配置（大内存优先）。

## 6. 顺带修的两个测量设施问题

1. **`test_mem` 走不到第 6 个用例**：`atomics` 用 `ldapur / stlur / ldapursb`
   （FEAT_LRCPC2，ARMv8.4），设备是 A55，**原生对照跑就 SIGILL**，进程死在那里，
   后面 12 用例 × 3 模式全不跑。裸汇编三行已在设备上复现（`exit=132`）。
   → `tools/patch_tests.py` 给测试加 `HV_SKIP=` 开关（上游源码保持只读）。
2. **`test_mem` 的 `main` 栈帧 ~8.6 MB**（harness 内联），设备默认栈 8 MB，
   bank 每 CPU 多 32 KB 就把它顶破。症状是"零输出 + SIGSEGV"，
   tombstone 写得很清楚：`stack pointer is in a non-existent map`。
   → 跑测试必须 `ulimit -s 65536`（此前几轮也踩过，这次记进文档与脚本）。

## 7. 已知未解（与本轮改动无关，已对照确认）

`test_mem` 的 mode 2（MMU on）10 项失败：`dispatcher returned 9 at pc 200
(insn 00000000) esr 86000005 far 200 elr 200`。
`0x200` 是 AArch64 向量表里"来自低 EL 的同步异常"槽位 —— guest 在新页表下先发生了
同步异常，然后跑到 `VBAR=0` 的空向量页上取指失败。
**基线（无 bank）逐项一致**，历史上这个移植也从未记录过 mode 2 通过。
要拿它做回归，得先查这个同步异常的第一现场。

# 第七轮：把四个悬案结清（其中两个推翻了上一轮的预设）

上一轮交付状态是"性能达标、两条正确性悬案未关、+20% 归因缺分桶证据"。
这一轮只做补证，不改快路径。结论里有两处**推翻了上一轮的判断**，先说那两处。

## 0. 两个被推翻的预设

**预设一（我上一轮写的）："慢路径是 knee 曲线的第二支柱"。**
→ **不成立。** bank 版 knee 的 TLB miss 只有 **3.5%**，慢路径份额 ≈ 12 ns（占 16%），
不是支柱。详见 §2。

**预设二（沿用很久的）："knee 曲线测的是 TLB 覆盖半径"。**
→ **在 bank 版下它已经不测 TLB 了。** bank 版三档的 `tlb_refills` 是
587.5K / 587.7K / 589.1K（64MB / 512MB / 2GB）—— **几乎完全一样**。
refill 数与工作集无关，说明 knee 本身的访问已经全部被 bank 接住，
剩下那 3.5% 是启动/printf 之类的固定开销。曲线现在测的是**宿主内存层级**（见 §2 表）。

## 1. ① 76.2 ns 的分解（三桶，用差值法）

为什么不用 JIT 插桩：试过了，撞墙。bank 在 `x28+0x401000`（4 MB 外），计数桶紧跟其后
（+38920），而 `LDR_X` 的 imm12 只覆盖 `4095*8 = 32760` —— 38920/8=4865 溢出到 Rn 位，
整个指令编码错乱，计数写进野地址。症状是"`fills` 正常但 `hits` 恒为 0"，
和当初 `lsr` 写错寄存器一模一样。要修得两步寻址 + 第 4 个寄存器（此时 T 是表项指针、
U 是 addend，都不能动），代价 6 条指令，不值得。

改用**差值法**（零插桩、零污染）：

```
bank_hit = refills(BANK=0) - refills(BANK=1)     ← bank 接住的那部分
N        = knee 的 STEPS = 16,777,216（固定）
miss 率  = refills(BANK=1) / N
```

三档实测（同会话、交错、各 3 次取中位；THP 100%；2.0 GHz）：

| 工作集 | native | base（BANK=0） | **bank** | refills(base) | refills(bank) |
|---|---|---|---|---|---|
| 64 MB | 17.3 | 44.65 | **44.84** | 644,840 | 587,500 |
| 512 MB | 31.0 | 359.70 | **75.04** | 17,632,476 | 587,665 |
| 2 GB | 104.0 | 438.91 | **115.79** | 18,419,496 | 589,118 |

**注意 base 的 refills 在 512 MB 就达到 17.6M ≈ 105% × N** —— 4 KB 直接映射 TLB
（16384 槽 × 4 KB = 64 MB 覆盖）在 512 MB 工作集上几乎每次访问都 miss，这解释了
359.7 ns：它就是"全 miss 时的单价"。

于是慢路径单价 `t_miss ≈ 342 ns`（359.7 去掉 3.8% 命中的修正），分解：

| | 512 MB | 2 GB |
|---|---|---|
| 实测 ns/access | **75.04** | **115.79** |
| 慢路径份额（3.5% × t_miss） | 11.97（**16%**） | 15.36（13%） |
| 快路径份额（含宿主访存） | **63.1（84%）** | **100.4（87%）** |
| 其中 native 自己就要花 | 31.0 | 104.0 |
| **引擎的额外开销** | **32.1** | **−3.6** |

**2 GB 那格的 −3.6 不是笔误。** bank 版快路径 100.4 ns，native 104.0 ns —— 引擎
不但没更慢，还略快一点点（在噪声内）。原因是宿主 DRAM 延迟（~100 ns）把 TLB 探测
完全掩盖了：CPU 在等内存的时候，那 8 条指令被乱序执行吃掉了。

**这个发现的实用含义**：探测税不是恒定的，它取决于"这次访问本来要等多久"。
- 数据全在 LLC（64 MB 档，实际数据只有 1 MB）→ 税全额可见（27.5 ns）
- 数据在 DRAM（2 GB 档，实际数据 32 MB）→ 税被完全掩盖
- 中间态（512 MB 档，实际数据 8 MB，正卡在 LLC 边缘）→ **税最贵（32 ns）**

> ⚠️ 注意"工作集"和"实际数据量"的区别：knee 每 4 KB 页只放一个 64 B 节点，
> 所以 64 MB/512 MB/2 GB 的**实际触碰字节**是 1 MB / 8 MB / 32 MB。
> 这解释了为什么 native 是 17.3 → 31.0 → 104.0（跨过 L2、L3 两级）。

## 2. ② 启动期的税基：bank 只覆盖 8%

Debian 启动到 multi-user（RAM=2048, CPUS=2），带 `HV_SUM`：

| | base | bank |
|---|---|---|
| `tlb_refills` | 2,851,858 | **3,092,935** |
| `slow_accesses` | 423,883 | 304,858 |
| `bank fills` | — | **244,307** |
| `switch_user` | — | **41,317** |

**`bank fills / tlb_refills = 244,307 / 3,092,935 = 7.9%`。**

启动期的页绝大多数是 4 KB 映射（slab、页表、用户态小对象），`w->block_size < 2 MB`
→ 永远进不了 bank。所以那 8 条探测指令在启动期 **92% 是纯税**。

**这正好证实了上一轮那个"未验证的隐含假设"**，而且方向是对的：
启动期的主流状态就是"4 KB 能命中/要 refill + bank 必然未命中"，
探测顺序造成的代价**不是**"把税从访存挪到 miss"，而是实打实的每次访存白付。
→ **修法应当是"挪进 refill 分支"（消除纯税），而不是调容量或动态启停。**

副产物：`refills(bank) 3.09M > refills(base) 2.85M` —— bank 版启动的 refill 反而多了 8%。
原因未完全定论，最可能是 bank 命中后 `tlb_fill` 不再被调用、于是 `user_fills[]` 里
少了这批项、进程切换时 stash 行为改变，导致额外的 cold fill。这条记作**待查**，
不影响主结论（税基来自探测而不是 refill）。

## 3. ④' switch_user 失效对账：比预估小 50 倍

上一轮担心的是 `32 KB × 64.8k/s ≈ 2 GB/s`。实测：

**启动期 41,317 次 switch_user / 32.4 s ≈ 1,275 次/秒**（不是 64.8k/s —— 那是 Windows

而且 `bank_invalidate` 在 `bank_ready` 之后是 **O(bank_n)**（只清 live 表里的项），
不是 32 KB memset。启动期 bank_n 很小（fills 只有 244K/32s），实际代价可以忽略。

**结论：switch_user 失效不是那 +20% 的组成部分。** 这条白捡的优化不存在，
但也排除了一个嫌疑人。

（顺带：`on_switch` 与 `switch_user_calls` 两个计数完全相等 = 41,317，
说明每一次地址空间切换都真的触发了一次失效，没有漏也没有多余。）

## 4. ④ 多核 SMC：通过（并挖出测试自己的一个坑）

新增 `tests/test_smc_mp.c`：两个 `HvCpu` 交替跑，写由"另一个 CPU 上下文"发出。

结构性前提（用代码钉住，不靠推断）：
- `mmu.c` 里 `bank` 出现 **0 次** —— 取指路径（`exec_tag` / 块查找）完全不经过 bank；
- bank 只缓存 VA→PA 的 **addend**，不缓存代码内容；
- 翻译作废走 `hv_invalidate_code → page_gen[pg]++`，而 `page_gen` 是**RAM 全局**的
  （不是 per-CPU），所以任何 CPU 下次查块时 gen 不匹配就重翻。

测试结果（BANK=1，交付配置）：

```
cpu0 first run          : x0 = 1 (want 1)
cpu0 data-read done     : x2 = d2800020, bank_n = 0
cpu1 wrote code[0]      : now d2800040 (want d2800040)
cpu0 second run (no rst): x0 = 2 (want 2)
invariants after write  : code[0]=d2800060 code_pages=0(0) page_gen=2(>=2) smc=2
cpu1 after cpu0's write : x0 = 3 (want 3)
smc_mp: 0 failures
```

**这个测试的第一版是"失败"的，而失败原因是测试自己错了**，值得记下来：
`hv_cpu_reset(cpu, m)` 内部固定调 `hv_cpu_reset_index(cpu, m, 0)` —— 两个 CPU 都会
被注册成 `m->cpus[0]`，后者覆盖前者。于是 `protect` 只遍历到一个 CPU、
`whint` 又按 `cpu->index` 索引（两个 CPU 共用同一份），第 5 步就假失败了。
改用 `hv_cpu_reset_index(&c0,&m,0)` / `(&c1,&m,1)` 后全过。
（生产路径 `linuxvirt.c` 用的是带 index 的版本，所以真实 SMP 没这个问题。）

**BANK=0 对照**（同一份测试源码，只换引擎）：

```
cpu0 second run (no rst): x0 = 2 (want 2)
invariants after write  : code[0]=d2800060 code_pages=0(0) page_gen=2(>=2) smc=2
cpu1 after cpu0's write : x0 = 3 (want 3)
smc_mp: 0 failures  (BANK=0 control)
```

**两边逐项一致**（含三条不变量 `code_pages/page_gen/smc` 的数值），所以 bank 没有改变
SMC 的行为 —— 它不是"碰巧通过"，是根本没参与这条路径。

`bank_n = 0` 是预期的：测试 RAM 是 4 KB 页，没有 2 MB 块描述符，bank 本来就不会填。
但结论与"bank 是否填充"无关 —— 因为取指不经过 bank（上面第一条）。

# 第八轮：按 EL 分流的 bank（+23.2% → +8.0%）

## 0. 先确认被否决的那条：编译期查页表分流

「编译期查页表决定用哪个探测模板」不是本项目的方案（我上一轮提的是"探测挪进 refill 分支"），
但把它否决掉是对的，而且四条理由我逐条复核过：

| 否决点 | 复核结果 |
|---|---|
| VA 是运行时值，编译期没有页表视角 | 成立。`ldr x0,[x1]` 的 x1 编译期是空的 |
| 块缓存跨进程共享，查谁的页表取决于运行时 ASID | 成立。块键是 `{va, pa, flags, gen}`，**pa 在里面**——这恰好证明块已经和映射绑死，再叠一层"编译期页表快照"只会和这套绑定打架 |
| 失效频度付不起（TLBI/mmap/fork/COW） | 成立。启动期 `switch_user` 41,317 次、fork 数千次 |
| 拆分是**同步**的（mprotect 单页、MADV_NOHUGEPAGE、migration、COW），比合并危险得多 | **成立，而且是我没考虑过的方向**。我原来只盯着 khugepaged（异步、慢），漏了反方向 |

所以：**固化不变量，不固化易变状态**。这条我接受，并且下面的实现完全按它做。

## 1. 先量前提：EL 分布（这是决定一切的数）

per-EL 块基础设施确认存在：`HV_BLOCK_EL1`(1) / `HV_BLOCK_PAN`(8) 是块键 `flags` 的一部分，
`g_el = !(flags & EL1) ? 0 : (flags & PAN) ? 2 : 1` —— **翻译期就能确定的常量**。

Debian 启动（RAM=2048, CPUS=2）加 `HV_SUM`：

| | fills | 占比 |
|---|---|---|
| EL0 | 605,161 | 11.8% |
| EL1 | 4,517,219 | **88.2%** |
| EL1+PAN | 0 | 0% |
| **bank fills** | el0=**0** / el1=**258,263** | **100% 来自 EL1** |

两个结论：

1. **EL1 占 fill 的大头（88%）** —— "内核态占大头"成立。
2. **EL1 内部 94.3% 是 4 KB**（2 MB 块只占 5.7%）—— 所以 EL1 的探测基本收不回来。
3. **一个我们俩都没预料到的事实：boot 期 bank fills 的 EL0 部分是 0。**
   bank 在启动期的全部价值压在那 5.7% 的 EL1 大页上；EL0 一个都没填。
   （knee 是另一回事 —— 它是 EL0 进程 + THP，bank 在那里才真正工作。）

## 2. 实现（翻译期常量，不查任何运行时状态）

```python
# BANK_EL=1
gate = '(!op.store && el_idx == 0)'      # EL0 块：保留探测
# EL1 / EL1+PAN 块：整段探测不发射
```

`el_idx = g_el` 完全由块 `flags` 推导，翻译这个块的时候就知道，**不查页表、不查 ASID、
不看 THP 状态**。填充侧也一起收：

```c
if (el == 0 && w->block_size >= (1ull << 21) && ...)   /* 只给 EL0 填 bank */
```

| | 基线 | bank（全 EL） | **bank（EL 分流）** |
|---|---|---|---|
| 2 核 中位 | 25.68 | 31.98 | **27.68** |
| 代价 | — | **+23.2%（+6.02 s）** | **+8.0%（+2.04 s）** |

```
base   25.64 27.55 25.63 25.62 25.95    中位 25.64 ± 0.83
EL分流 27.20 28.66 27.84 27.29 27.68    中位 27.68 ± 0.58
```

knee 三档（EL0 路径，应当不变）：

| 工作集 | bank（全 EL） | **bank（EL 分流）** | 偏差 |
|---|---|---|---|
| 64 MB | 44.84 | **44.92** | +0.2% |
| 512 MB | 75.04 | **74.04** | −1.3% |
| 2 GB | 115.79 | **113.89** | −1.6% |

**三档全在 ±2% 内，2 GB 还略好。** 验收通过 → `BANK_EL=1` 成为交付配置。

## 4. 残差 +2.04 s 是什么：不是 refill，是"做了更多工作"

这一格差点写成错的结论。第一次看 `tlb_refills`，el2 比 base 高 6.3%，像是"bank 让 refill 变多"。
但 `guest_insns` 也不同。归一化之后反转了：

| | time | guest_insns | refills/insn | ns/insn |
|---|---|---|---|---|
| base | 25.85 | 8.588 M | 330.0‰ | 3045.5 |
| EL 分流 | 28.72 | 9.317 M | **324.5‰** | **3139.1** |

- **refill 效率反而略好**（324.5 vs 330.0‰）→ "refill 变多"是伪影，它只是工作量变大的伴生。
- 真实代价是 **每 guest 指令 +3.1%**（3139 vs 3045 ns/insn）。

而 el2 的 `guest_insns` **系统性高 4–10%**（6 次运行一致），这是启动的 **tick 反馈**：
每指令慢 3% → 同样的等待时间内 timer 多跳几次 → 内核多跑一些轮询/dhcp/超时路径 →
更多指令 → 更慢。所以 +8% 墙钟 = **+3% 的真实成本被反馈放大**。

那 3% 的物理来源：EL0 块仍在探测（EL0 占 11.8% 的 fill），加上 HvCpu 多出 38 KB/CPU
（bank 32 KB + used 2 KB + live 4 KB）的足迹。

**这部分是静态轴的尽头**：boot 的 EL0 和 knee 的 EL0 在 EL 上无法区分（一个是 4 KB 栈/堆，
一个是 2 MB THP），要再往下砍只能引入运行时判据 —— 而那正是被（正确地）否决的方向。
下一步该走 **EL1 linear map**，但那已经是"EL1 不再需要 bank"之后的另一条路。

## 5. 一个失败的分支（记录以免重犯）

`tlb_fill` 里的 bank 填充**也**按 EL 收掉（el2），相对只收探测的版本（el）只多赚 **0.1 s**
（+8.3% → +8.0%）。说明填充期的 `bank_used/bank_live` bookkeeping 不是税的一部分 ——
boot 期 bank fills 本来就只有 25 万次，可忽略。
**结论：这一层的优化空间比我预期的小一个量级，不要再往这儿投入。**

## 6. 交付配置

```

```

`BANK_EL` 只改 `translate.c`（探测发射）与 `mmu.c`（填充条件），**不动 HvCpu 布局**，
所以 ABI 不变、knee 与自测无需重编（但仍建议同环境重建，见 build_variant.sh 的注释）。

# 第九轮：BANK_SEEN 二态被证伪（40 分钟，省下 1 天）

## 0. 被否决的四条：全部成立

"per-insn 计数 + 运行期 NOP 打补丁"这套（不是我提的方案，但值得逐条记）：

| 否决点 | 复核 |
|---|---|
| per-insn 计数 = 把刚消掉的税加回来 | 成立。我自己就撞过 `imm12` 那道墙（bank 在 `x28+0x401000`，计数桶 +38920 → 38920/8=4865 > 4095，编码溢出到 Rn 位） |
| NOP 补丁要 mprotect + IC IVAU + 处理并发窗口，~20 µs/次 | 成立。A55 无 PoU coherence，必须显式刷 |
| 混合 VA：per-block 的 NOP 会误伤 per-insn 的混合块 | 成立，**而且它同样适用于下面那个"修正版"**（见 §3） |
| 阈值触发不了启动期残差（4KB 块大多只执行 1 次） | **成立，而且这是最关键的一条**：任何"学到才用"的机制都需要第二次机会，一次性块没有第二次 |

## 1. 修正版的设计（信号在慢路径，作用在翻译期）

```c
/* tlb_fill：第一次见到 2MB block → 置位 + 推 page_gen（给"下次翻译"一个机会） */
if (ram->bank_seen && !ram->bank_seen[pg]) {
    ram->bank_seen[pg] = 1;
    __atomic_add_fetch(&ram->page_gen[pg], 1, __ATOMIC_SEQ_CST);
}
/* translate：这一页见过 2MB block 才发射探测 */
gate = el_idx == 0 && e->bram->bank_seen[e->bpg]
```

零 syscall、零 icache 刷新、零并发窗口 —— 比 NOP 补丁便宜两个数量级，这个判断是对的。

## 2. 实测：knee 512 MB 从 74 → **363 ns**

| 变体 | knee 512 MB | bank fills |
|---|---|---|
| 交付版（`BANK_EL=1`） | **74.0–75.9** | 0.59 M |
| **`BANK_SEEN=1`** | **363.1 / 384.4** | **17.6 M** |

**完全退回到无 bank 水平（base 359.7）。** 方案不成立。

## 3. 为什么失败：两个独立的、都足以致命的原因

### 3.1 页号错位：标记记在数据页，翻译期查的是代码页

`bank_seen` 在 `tlb_fill` 里按**数据访问的 PA** 置位；
但翻译期能拿到的 `b->pg` 是 `dispatch.c:150` 里 `nb.pg = pg`，而那个 `pg` 来自
**取指**的物理地址 —— 是**代码页**。

```
数据页的 bank_seen[pg]  ←  fill 时置位
代码页的 b->bpg          ←  翻译时查询
两者永不相等 → 探测永不发射 → bank 白填（fills 17.6 M，命中 0）
```

这就是你的否决三（混合 VA）在"修正版"里的同一个病：一个块**可以访问多个数据页**，
而翻译决策只能看块自己所在的那一页。per-block 的粒度装不下 per-insn 的信息。

### 3.2 即使页号对上，chained 热循环也不会重编译

`page_gen++` 只影响"**下次查找**"。而 knee 的块转移 **88% 是 chained**
（16.7 M 访问只产生 120 K 次 dispatcher entry，其中 105 K 是 chained）——
循环块查过一次表之后就靠链接直接跳，永不回 dispatcher。
所以就算标记打对了，"下次翻译"这个事件也**不会到来**。

这两个原因互相独立，任何一个都足以让方案失效。**第二个更是"学到的知识没有机会被使用"**，
它不是实现问题，是 chained 设计（本身是性能优化）与"延迟决策"之间的结构性冲突。

## 4. 由此得到的结论（比方案本身重要）

> **任何"运行期学习 → 翻译期生效"的机制，都要求块被重新翻译；
> 而热块之所以热，恰恰因为它永不重编译。**

这条和"固化不变量、不固化易变状态"是同一个硬币的两面：
- 固化**不变量**（EL、VA 区段、指令类别）→ 一次决定，永远有效 → 与重编译无关 ✓
- 学习**易变状态**（页表项、THP）→ 决定会过期 → 必须依赖重编译 → 与 chained 冲突 ✗

所以 EL 分流（第八轮）能成立，BANK_SEEN 不能 —— 不是因为实现质量，是因为前者的依据在
翻译期**已经确定**，后者要等一个**可能永远不来的未来**。

## 5. 处置

`BANK_SEEN` 保留在工具链里（`BANK_SEEN=1`），但**不作为交付配置**，默认关闭，
并在此记录实测数据，避免以后有人再走一遍。

**EL0 那 3% 的税到此为止。** 它的正确解法不是让引擎去学，而是让 EL0 的访问不再需要探测
——那就是 linear map 之类的"换机制"，而不是"给现有机制加反馈"。

## 6. 顺带修掉的两个工具缺陷

1. **`build_variant.sh` 不删 `build/translate_patched.c`**：`BANK_SEEN`/`BANK_RD`/`BANK_EL`/
   `RET_MODE`/`HASH` 都是**环境变量**驱动的，改它们不会让该文件的 mtime 变化，make 就复用
   上一个变体的副本 → 症状是"改了开关行为不变"或"头文件对不上直接编不过"。已加进清理列表。
2. **`patch_bank.py` 里 `patch_ram_ncode` / `patch_dispatch_ncode` / `BANK_EL` 填充块
   各出现过两份重复定义**（多次插入累积）。重复定义时**后一份静默覆盖前一份**，
   于是我改第一份不生效、改第二份才生效 —— 这类"改了没反应"极难排查。已去重。
   **教训：给自修改脚本加片段时，必须用 `assert count==1` 卡住重复。**

# 第十轮：EL1 linear map —— 通道建成，但 emit 仍有 bug（未交付）

## 0. 设计取向：按需开启的通道，不是内置优化

linear map 的 VA 区间和偏移**是系统相关的**（Linux `PAGE_OFFSET` vs Windows 内核 VA
布局完全不同），所以引擎不能内置任何具体数值。这一轮做的是**通道**：

> 引擎只提供"如果你告诉我 `[base, base+len)` 恒等于 `host+delta`，
> 我就让这个区间的 EL1 读跳过 TLB 探测"的能力；**由 runner 按需打开**。

三条约束，都落实在代码里：

1. **默认关闭**。`nlinmap == 0` 时**一条指令都不发射**，交付二进制与今天逐字节等价
   （已用 `BANK=1 BANK_RD=1 BANK_EL=1 LINMAP=0` 重建验证：353720 B，knee 74.75 ns 不变）。
2. **不固化易变状态**。区间由配置显式给出，不探、不学、不猜。
   （第九轮 BANK_SEEN 的教训：靠运行期学习的东西都要等重编译，而热块永不重编译。）
3. **失败安全**。VA 不在区间内就落回原探测；命中只产出 addend（= delta），
   与 bank 命中走**同一个合流点**，不引入新的权限或失效语义。

### 责任边界（写进代码注释，因为这是配置者的义务）

引擎**无法**验证区间内映射真的连续 —— 它拿到 delta 就直接加。配置者必须保证
`[base, base+len)` 内每个字节都满足 `host = va + delta` 且**全部已映射**。
否则不崩溃（ram 是 malloc 的一大块，读越界不会立刻 segfault），**但会读到错的内存**。

## 1. 已建成的部分（可复用的地基）

| 件 | 位置 | 状态 |
|---|---|---|
| 配置字段 `linmap[2]/nlinmap` + `HV_LINMAP` 宏 | `HvMachine`（不是 `HvCpu`，避开 imm12 那个坑） | ✅ |
| CLI `--linmap GB,LEN,PA`（最多 2 段） | `main_android.c` | ✅ 已验证打印 |
| delta 推导：`host(pa_base) - guest_base` | 同上，RAM 建好后算 | ✅ |
| 越界/找不到 RAM 的拒绝与截断 | 同上 | ✅ |
| 发射代码（`sub`/`sub`/`tbnz` + literal pool） | `tools/patch_linmap.py` | ⚠️ 见 §2 |
| 与 `BANK` 的补丁顺序兼容（两种尾部形态） | 同上 | ✅ |

**为什么用 `sub + sub + tbnz` 而不是 `cmp + b.hs`**：整个 TLB 探测段是刻意写成
"Uses no flags" 的（源码注释明说），后续指令依赖进入时的 NZCV。`cmp` 会污染它。
实测：用 `cmp` 时 guest 在 **5864 条指令**处确定性崩溃，**无论区间配成什么值**。

## 2. 未解决：emit 仍然崩（这是本轮唯一的失败项）

现象：

hv-linux: fatal signal 11 (SIGSEGV) addr=0x5300...3ff8 [inside JIT]

已排除 / 已修：

| 假设 | 结论 |
|---|---|
| `cmp` 污染 NZCV | **真 bug**，已改 `sub+tbnz` |
| `tbnz` 编码：`63u << 31` 在 uint32 里截断成 `0x80000000`，丢掉 b40 位，实际编成"测试 bit 31" | **真 bug**，已改为常数 `0xb7080000`（fault dump 里 `b700014f` → `b708014f` 可对照） |

1. `put_tlb_slot` 是否会因为前面多了 4 条指令而算出不同的 `tlb` 偏移 —— 它是**位置相关**的

3. literal 在热路径中间发射（`in_cold == 0`）时 `fix[]` 的处理顺序。

## 3. 处置

## 0. 先认一个更严重的错：这半天的测量环境是脏的

## 1. PAGE_OFFSET：用自洽性证明，不再推

上一轮我写"guest pc=0xffff8000... 提示真实布局不是 52-bit"，却没跟下去。现在跟上：

```
halt pc = 0xffff8000800244f0,  RAM pa_base = 0x40000000, RAM = 2560 MB

VA_BITS=48: PAGE_OFFSET = 0xffff800000000000  → pc-offset = 0x800244f0  在 RAM 内 ✓
VA_BITS=52: PAGE_OFFSET = 0xfff8000000000000  → pc-offset = 0x78000800244f0  不在 ✗
```

**结论：运行时是 48 位 VA，PAGE_OFFSET = `0xffff800000000000`。**
（顺带修正：`(UL(-1) << (VA_BITS-1))` 对 52 位给的是 `0xfff8…` 不是 `0xfff0…`。）
`.config` 里的 `CONFIG_ARM64_VA_BITS=52` 与设备上跑的 Image 不符 ——
**版本号/config 不可信，只有自洽性证明可信**。

## 2. 发射断言层（`tools/emit_check.py`）—— 本轮唯一的交付物

自包含，不依赖 capstone（离线设备/CI 都能跑）。5 个断言 + 1 个编码器：

| 断言 | 杀什么 |
|---|---|
| `check_no_flags` | `cmp`/`tst`/S=1 指令污染 NZCV（探测段文档化为 "Uses no flags"） |
| `check_self_op` | `Rd==Rn/Rm` 自反（默认禁止，显式 `allow_self_op` 才放行） |
| `check_offset` | imm12 溢出（`38920/8=4865 > 4095`） |
| `check_logical_imm` | AND/ORR/EOR 立即数的 N:immr:imms 形状合法性 |
| `tbnz()/tbz()` 编码器 + 黄金表 | 位域截断（`63<<31` 在 uint32 里丢 b40） |

**自检结果：6/6 历史 bug 被拦下，0 处误杀**（含 `add x,x,#1` 这种合法的自反操作）。

### 它当场抓到了我自己的一个新 bug

上一轮我说"tbnz 编码修好了，改成 `0xb7080000`"。断言层一跑：

```
FAIL tbnz x15,#63 -> 0xb7f8000f (期望 0xb708000f)
```

正确的 ARM ARM 布局是 **bit31=b5, bits30:25=011011, bit24=op(1=tbnz), bits23:19=b40**，
基址是 **`0x37000000`**，不是 `0xb7000000`（后者把 b5 写死成 1）。
所以 `tbnz #63` = `0xB7F80000`，而我上一轮的 `0xb7080000` 其实是 **#33**。
——**"修了一个 bug"和"修对了"是两件事，只有断言层能区分。**

## 3. linmap：进展与仍差一步

修完上面两处（`tbnz` 基址、临时寄存器），实测：

| | tlb_refills | fetch_walks | guest_insns | knee |
|---|---|---|---|---|
| 不给 `--linmap` | 593,041 | 580 | 461,587 | **71.7 / 72.7** |
| 给 `--linmap`（48 位窗口） | **226** | 24 → 后飙到 18 亿 | **3,239** 就 halted | 无输出 |

**refills 从 59 万掉到 226 —— linmap 的命中路径确实在工作了**（前一版是完全没命中）。
但 guest 只跑 3239 条就 `halted=3`，说明 **delta 在窗口的一部分上不成立**。

### 又踩了一次 `addr==临时寄存器`（换了个寄存器又踩）

把临时寄存器从 `T` 换成 `x7` 之后仍崩。原因：`x7` **本身就在 `pick()` 的候选表里**
（`candidates[] = {6, 7, 15, 9, ...}`）。当 `addr` 被分到 7 时，`sub U, addr, 7`
又退化成 `x-x=0` → off 恒 0 → 永远"命中" → 拿 delta 当 addend。
症状：`fetch_walks` 飙到 **18 亿**（guest 跑飞）。
修法：只从 `{6,7,15}` 里挑一个**不在 `{addr,T,U}` 中**的作为临时寄存器。

### 现在剩的问题：窗口太宽

`[0xffff800000000000, +2.5GB)` 覆盖了整个线性映射，但**内核镜像的虚拟映射**
不一定满足 `va − PAGE_OFFSET == pa − 0x40000000`（KASLR / 独立映射）。
错误 delta 立刻把内核数据写坏 → 3 千条指令内就死。

下一轮该做的**不是再猜**，而是：
1. 把窗口收窄到 1 页，逐页试（或用 fill 采样先画出"哪段 VA 满足该等式"）；
2. 或者干脆在 `tlb_fill` 里**校验**：若 `ram->host + (pa - ram->pa) - va != window.delta`，
   打印一次并拒绝该窗口（这比事后调试便宜得多）。

**配置不变**：`BANK=1 BANK_RD=1 BANK_EL=1`，不含 LINMAP。

## 5. 三条可复用的纪律（都是这轮真金白银换来的）

1. **测量前先 `top` 看 %CPU**，不要只 `ps | grep` 自己的名字。
   `w_test_exc` 这种带壳进程 `pkill -x` 杀不到，会静默烧核几小时。
2. **"改了没生效"和"改了但改错"要分开验证**。`translate_patched.c` 不删会复用旧变体；
   `@PLACEHOLDER@` 替换顺序反了会塞进未替换文本。两者症状都是"行为不变"。
3. **手写指令常数必须有黄金表**。这轮 `tbnz #63` 我连续写错两次（一次丢 b40、
   一次基址少 b5），两次都"看起来修好了"。断言层一跑就现原形。
