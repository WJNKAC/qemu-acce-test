# 三态判读规则（所有网络读数的翻译表）

> 这份表是**读数翻译的唯一依据**。任何 `refused` / `ok` / `timeout` 的
> 出现，都按这里解释，不按直觉解释。

## 一、三态定义

| 观测 | 内核返回 | 含义 | 判读 |
|---|---|---|---|
| `ok` | 三次握手完成 | 服务在监听，应用层可达 | **端口可达** |
| `refused` | `ECONNREFUSED`（收到 RST） | 包抵达对端、对端拒绝 | **网络通**（最强证据） |
| `timeout` | `ETIMEDOUT`（无任何回应） | 包没到 / 回来没到 | **唯一可疑信号** |

### 为什么 `refused` 比 `ok` 更能证明"通"

发出 RST 需要完整的 TCP/IP 栈工作：收到 SYN → 查监听表 → 无监听 →
构造 RST → 路由回来。**任一环节断了都不会有 RST，只会 timeout。**

所以：
- `ok` 证明"路径通 **且** 有服务"
- `refused` 证明"**路径通**"（且能反证对端栈活着）
- `timeout` 证明"路径不通（或对端完全不存在）"

**`ok` 少于 `refused` 不代表网络变差** —— 只代表端口上没服务。

## 二、按目的端口拆开读

同一个 `refused`，端口不同语义不同：

| 端口 | 谁在听 | `refused` 的含义 |
|---|---|---|
| `10.0.2.2:22` | slirp 网关（**故意不监听**） | 网关可达，且没有 SSH 服务 → **正常**，这是"通"的阳性证据 |
| `10.0.2.3:53` (TCP) | slirp 内建 DNS（**只做 UDP**） | DNS 主机可达，但不收 TCP → **正常** |
| `10.0.2.2:10080` | host 侧 `nc -l` 监听 | `refused` = **监听者不在** → 是 host 侧的问题，不是网络问题 |

**规则：读到 `refused` 时必须看端口，再决定算"通"还是算"host 侧未就绪"。**

`10080` 的 `refused` 尤其要小心 —— 它不反映 guest↔slirp 数据面，
只反映"我那个 nc 监听没起来"。判读时单独标注，不并入网络健康度。

## 三、curl 与三态的关系

`NETPROBE-CURL code=200` 是**完整路径**（guest → slirp → host loopback）的证据，
强度高于任何 `refused`。

| curl | TCP 三态 | 判读 |
|---|---|---|
| 200 | 任意 | **完整路径通**（curl 优先） |
| 000 | `refused` 出现在 10080 | host 监听没起，非网络问题 |
| 000 | 全部 `timeout` | 真不通 |
| 000 | 探针异常 > 0 | 探针坏了，本行作废 |

**互相矛盾时的优先级：探针异常 > curl > 三态。** 前面那个否决后面那个。

## 四、禁止的写法

| 反例 | 为什么错 |
|---|---|
| `ok=1/0` 二态 | 把 `refused` 判成失败 → 把"通"读成"不通" |
| `grep 'Connection refused' && 判失败` | 同上，语义反了 |
| 只看 `refused` 总数不看端口 | 10080 的 `refused` 是 host 侧问题 |
| 用 `timeout` 之外的任何东西判"不通" | 只有 `timeout` 可疑 |
