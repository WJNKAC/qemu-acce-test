# 三态判读规则（所有网络读数的翻译表）

> 这份表是**读数翻译的唯一依据**。任何 `refused` / `ok` / `timeout` 的
> 出现，都按这里解释，不按直觉解释。

## 一、三态定义

| 观测 | 内核返回 | 含义 | 判读 |
|---|---|---|---|
| `ok` | 三次握手完成 | 服务在监听，应用层可达 | **端口可达** |
| `refused` | `ECONNREFUSED`（收到 RST） | 包抵达对端、对端拒绝 | **网络通**（最强证据） |
| `timeout` | `ETIMEDOUT`（无任何回应） | 包没到 / 回来没到 | **唯一可疑信号** |

### 为什么 `refused` 比 `ok` 更能证明"通"

发出 RST 需要完整的 TCP/IP 栈工作：收到 SYN → 查监听表 → 无监听 →
构造 RST → 路由回来。**任一环节断了都不会有 RST，只会 timeout。**

所以：
- `ok` 证明"路径通 **且** 有服务"
- `refused` 证明"**路径通**"（且能反证对端栈活着）
- `timeout` 证明"路径不通（或对端完全不存在）"

**`ok` 少于 `refused` 不代表网络变差** —— 只代表端口上没服务。

## 二、按目的端口拆开读

同一个 `refused`，端口不同语义不同：

| 端口 | 谁在听 | `refused` 的含义 |
|---|---|---|
| `10.0.2.2:22` | slirp 网关（**故意不监听**） | 网关可达，且没有 SSH 服务 → **正常**，这是"通"的阳性证据 |
| `10.0.2.3:53` (TCP) | **没有谁在听**（`get_dns_addr()` 恒失败） | **从来不是 `refused`** —— 实测是 `err:ENETUNREACH`（13.54）。本行曾写作"DNS 主机可达，但不收 TCP → 正常"，**该结论从未被实测支持**，已作废 |
| `10.0.2.2:10080` | host 侧 `nc -l` 监听 | `refused` = **监听者不在** → 是 host 侧的问题，不是网络问题 |

**规则：读到 `refused` 时必须看端口，再决定算"通"还是算"host 侧未就绪"。**
**补充（13.54）：虚拟 DNS 地址 `10.0.2.3` 的任何端口都不可达**，
且是 `get_dns_addr()` 取不到上游导致的 `EPERM` —— 不要把它读成"端口语义"。

`10080` 的 `refused` 尤其要小心 —— 它不反映 guest↔slirp 数据面，
只反映"我那个 nc 监听没起来"。判读时单独标注，不并入网络健康度。

## 三、curl 与三态的关系

`NETPROBE-CURL code=200` 是**完整路径**（guest → slirp → host loopback）的证据，
强度高于任何 `refused`。

| curl | TCP 三态 | 判读 |
|---|---|---|
| 200 | 任意 | **完整路径通**（curl 优先） |
| 000 | `refused` 出现在 10080 | host 监听没起，非网络问题 |
| 000 | 全部 `timeout` | 真不通 |
| 000 | 探针异常 > 0 | 探针坏了，本行作废 |

**互相矛盾时的优先级：探针异常 > curl > 三态。** 前面那个否决后面那个。

## 四、禁止的写法

| 反例 | 为什么错 |
|---|---|
| `ok=1/0` 二态 | 把 `refused` 判成失败 → 把"通"读成"不通" |
| `grep 'Connection refused' && 判失败` | 同上，语义反了 |
| 只看 `refused` 总数不看端口 | 10080 的 `refused` 是 host 侧问题 |
| 用 `timeout` 之外的任何东西判"不通" | 只有 `timeout` 可疑 |

## 七、UDP 不算三态，它算五态（13.54 补）

上面那张表是 **TCP 专用**的。UDP 没有握手、没有 RST，`refused` 这个词在 UDP 上
根本不存在。硬把 TCP 的词汇套上去，会得到一批"看起来对、其实没有信息"的读数。

| 读数 | 怎么来的 | 判读 |
|---|---|---|
| `answer:an=N` | 收到应答且 N>0 | **通** |
| `rcode=K:an=0` | 收到应答但 rcode≠0 | **通**，是上游拒绝解析（NXDOMAIN 等），不是网络问题 |
| `timeout` | 应用侧 `recv()` 超时 | **证据最弱的一档**，见下 |
| `err:<ERRNO>` | `connect()` 过的 socket 拿到 errno | 包被处理了，且结果明确 |
| `answered` | `IP_RECVERR` 路径拿到应答 | 通 |

**关键：UDP 的 `timeout` 不等于 TCP 的 `timeout`。**

TCP 的 `timeout` 说明"没收到任何回应"——SYN 发出去了，没有 SYN-ACK 也没有 RST，
这在本机链路层是可信的。

UDP 的 `timeout` 只说明**应用没拿到东西**，它至少对应两种截然不同的世界：

1. 包真的被丢了（网络不通 / 对端不存在）
2. 包被回了 ICMP，但内核没把它交给这个 socket

第 2 种在实测中真的发生过：同一个 `10.0.2.3:53`，普通 `recv()` 是 `timeout`，
而加了 `IP_RECVERR` 就能直接拿到 `ENETUNREACH`（13.54）。
**如果只看 `timeout`，这个"确定发生的故障"会被读成"说不清"。**

**规则：凡是 UDP 探针报 `timeout`，先问一句"内核收没收到 ICMP"。**
问法是 `setsockopt(SOL_IP, IP_RECVERR, 1)` + `connect()` + `recvmsg(MSG_ERRQUEUE)`。
拿不到任何东西，才是真空洞。

### 常见误判

| 反例 | 为什么错 |
|---|---|
| 用 `refused` 描述 UDP | UDP 没有 RST，这个词在 UDP 上没有意义 |
| 把 UDP `timeout` 直接记成"网络不通" | 可能只是 ICMP 没交给应用 |
| 用 TCP 连 53 端口来"验 DNS 通不通" | DNS 主用 UDP；TCP 那一路失败说明的是别的事（13.54：说明地址翻译就失败了） |

## 八、读数在哪里（13.56 补）

长跑（reboot 循环、soak）的读数**只认设备侧的 serial 日志**，不认 host 侧 stdout。

实测：6 轮那次跑到第 4 轮（t=595 s），主机的 `adb shell` 管道断了，host 侧
输出冻结在 `--- round 4 ---`，而后台任务一直显示"正在运行"。
设备上一查：`BEGIN=6 END=6`，6 轮早就跑完了，QEMU 进程也已退出。

**不是 QEMU 挂了，是 adb 那条管道断了** —— 两者在 host 侧看起来一模一样。

规则：

| 做法 | 为什么不行 |
|---|---|
| 采信脚本最后打印的汇总 | 管道断了就永远等不到；等到了也可能是半截 |
| 用 host 侧文件大小/时间判断进度 | 断连后文件不再增长，会被读成"卡死" |
| **按 `st-<tag>.serial.log` 重算判据** | ✅ 唯一可靠的来源 |

所以：**跑完先连上设备，按日志把判据重算一遍，再采信任何汇总。**
重算的判据必须和脚本里的一致，否则就成了两套标准。

## 九、"还在跑"与"卡住了"同形：退出条件自己会坏（13.63 补）

后台长跑的两种失败，现象完全一样 —— 任务列表里一直显示"运行中"：

| 实际情况 | 表现 |
|---|---|
| 任务还在正常进行 | 有输出、有进度 |
| 进程卡在一个没人能回答的提示上 | **无输出**，但进程活着 |
| 监控循环的退出条件写错了 | 有输出（每轮打一行），但**永远不会退出** |

第三种最阴：它在打日志，所以看起来"在正常工作"。

### 实测两例

**(1) `patch` 卡 17 小时**

```
1833322  bash -c ... patch -p1 --forward --silent < local-edits.patch ...
1833408    └─ patch -p1 --forward --silent     stat=S+  wchan=wait_woken
           fd/0 -> .../local-edits.patch (deleted)
```

`patch` 的 stdin 已经重定向到补丁文件，但**它问问题时是直接开 `/dev/tty`**，
不理 stdin。`--forward` 遇到"已经打过的补丁"会问
`Reversed (or previously applied) patch detected!  Assume -R? [n]`——
那个终端属于一个早就结束的会话，于是永远等。

判据：`stat` 带 `+`（前台进程组）、`wchan=wait_woken`、**输出文件 0 字节**。

**(2) 监控循环 2 小时 52 分不退出**

```sh
S=$(adb shell '...; ps ... | grep -c "[s]oak.sh"' | tr -d '\r' | tr '\n' ' ')
case "$S" in *" 0"*) break ;; esac     # ← 模式要求"空格+0"
```

实际值是 `S="0 "`（0 在开头，前面没有空格），所以**永不匹配**。
它每 5 分钟照常打一行 `10:41 [0 ]`，看起来完全正常。

### 规则

1. **凡是"等某个条件就退出"的循环，必须有一个独立的墙钟上限**，
   不能只靠条件本身。条件写错 = 无限循环。
2. **判"卡住"看三样**：输出文件是否还在增长、`wchan`、`fd/0` 指向哪里。
   只看"进程还在"区分不了。
3. **交互式工具一律加非交互开关**：`patch --batch` / `-t`、
   `apt-get -y`、`ssh -o BatchMode=yes`。不给它开口子的机会。
