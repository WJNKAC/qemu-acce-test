## 二、结构性结论（本次最重要的认知产出）

问题不在"缺功能"，在**所有权**。详见 `recon/henge-seam-structure.md`。

### 决定性证据 1：ARM 是唯一不在投递函数里清 `CPU_INTERRUPT_HARD` 的架构

| 架构/后端 | `cpu_reset_interrupt(HARD)` 次数 |
|---|---|
| SPARC | 1（`int32_helper.c:98`） |
| LoongArch | 1（`cpu.c:72`） |
| HPPA | 1（`int_helper.c:35`） |
| i386 / KVM | 1（`kvm.c:5958`） |
| i386 / WHPX | 2 |
| i386 / HVF | 1（`x86hvf.c:412`） |
| **ARM** | **0** |

ARM 的 `HARD` 唯一清零点 = `arm_cpu_set_irq(level=0)`，即 **GIC 拉低线**那一刻
（`target/arm/cpu.c:834-857`）。投递路径不清它。

→ ARM 设计隐含前提：**GIC 与投递者能同步操作同一个 `CPUState`**。
TCG 满足（同线程）；KVM 不需要（内核持有，用户态零副本）；
**henge 嫁接不满足**（GIC 在 QEMU、投递在引擎）。

### 决定性证据 2：AppleVM 根本没有 QEMU

| 指标 | 数值 |
|---|---|
| 补丁中 `CPU_INTERRUPT_HARD` | **0 次** |
| `devices/` 改动 | **3282 行 / 15 文件** |
| `core/` 改动 | **100 行** |
| `host/` 改动 | 87 行 |

AppleVM 的引擎 = 完整机器（CPU+MMU+GIC+PCI+virtio+xhci+ACPI+fb），中断单栈闭环，
所以结构性不存在本接缝。它 97% 的改动在设备层 —— 这解释了"给 henge 加能力"的
两种对立路线：加设备（上游）vs 加适配层（本工程）。

### 所有权矩阵

| 资源 | TCG | KVM/ARM | henge 嫁接（本工程） | henge 独立（AppleVM） |
|---|---|---|---|---|
| GIC | QEMU | 内核 | **QEMU** | 引擎 |
| 投递 | QEMU | 内核 | **引擎** | 引擎 |
| 中断电平 | 1 份 | 用户态 **0 份** | 曾有 **2 份**（已改为 1 份） | 1 份 |
| 睡眠 | QEMU | 内核 | 引擎 park + QEMU halt 两套 | 引擎 |

## 三、已实施的代码改动（一期，全部已编译）

### 设计原则：读穿透 = MTTCG 同款

QEMU 的 `CPUState.interrupt_request` 是线电平的**唯一所有者**，引擎降级为
"每块边界轮询的读者"。这不是妥协：MTTCG 里 vCPU 线程读 `interrupt_request`、
iothread 写（`qatomic_or`），本来就是跨线程读穿透。

|---|---|---|

### 踩过的坑（务必记住）

`put_ool(OOL_EXIT)` 会调 `put_branch_exit()`，后者**检查前一条指令**
（`e->hot[site_at] != 0x36000000`）判断能否被链式跳转接管。
删掉原来的 `CBNZ` 后它会去 patch 错的指令 → **JIT 生成代码段 SIGSEGV**
（`fault addr 0x4259`，anonymous 映射）。
修法：保留一个恒真条件分支
```c
put(e, 0xd2800027u);  /* movz x7, #1 */
put(e, CBNZ_X(7));
put_ool(e, (Ool){.kind = OOL_EXIT, .pc = pc + 4});
```

### 当前残留问题（内核 idle 阶段）

```
CPU 0/1      = 500/500 ticks/5s   → 双核 100%
A(line-high) = 2^29               → WFI 立即返回 5 亿次
slept        = 950 冻结            → 一次真睡都没有
bailout      = 20
henge_irq    = 1/0 1/0，I=1，pc ffff800080f3bec8
```

### 与改造前的关键区别

改造前：线是**假的**高（跨栈陈旧副本），根因是所有权。
现在：线是**真的**高（从 QEMU GIC 实读），根因转移到**为什么降不下来**。

一个值得注意的数字：`slept` 冻结在 **950**，而 `p1b`（`HV_WFI_HOST=0` 对照组，
改造前行为）在同一阶段也是 **950**。两版睡眠次数完全一致，说明：
- 睡眠侧没有回归
- 这个活锁是**改造前就存在的**，读穿透既没治好也没加重它
- 早期引导的活锁（`A` 疯涨）才是读穿透治好的那个

→ 结论：**存在两个独立故障**。
  - 故障 A（早期引导）：陈旧电平副本 → 已由读穿透消除
  - 故障 B（内核 idle）：线真高但不降 → EOI/投递语义，尚未定位


已排除：
- ✅ `sysreg_external = 1`（`henge-accel.c:886`），ICC 读写确实交给 QEMU
- ✅ 读/写两侧 ICC 都走 `HV_SYSREG_EXTERNAL`（`engine/core/sysreg.c:205` 与 write 侧同款判断）
- ✅ `hv_check_interrupts` 每轮 WFI 都经过（`dispatch.c` 的 `case HV_EXIT_WFI` 在 `for(;;)` 内，`break` 后回到顶部即检查点）
- ✅ `irq_line_get` 钩子已安装（`henge_engine_register_cpu` → `hv_engine_set_irq_hook`）

待验证（按优先级）：
1. **EOI 是否真的把线拉低** —— 在 `henge_service_sysreg()` 里对 ICC_EOIR1 写入前后打印
   `cs->interrupt_request & HARD`，确认 QEMU GIC 的 writefn 执行后线是否归零
2. **`I=1` 时投递是否被正确拒绝、`I=0` 时是否立刻投递** —— 需要 PC 轨迹而非采样
3. **line 高但 guest 不 ack**：是否该中断 target 的是另一个 redistributor

所以：**回归窗口 = 08:57 → 10:04，即读穿透改造**；且只在 `smp>1` 暴露。

## 为什么

`HV_WFI_LOG=1` 抓到：

```
henge: wfi spin bailout cpu0 pc=ffff800008c5e9cc daif=c0 irq=1 fiq=0 el=1
```

`daif=0xc0`：guest 在 `cpu_do_idle()` 里关中断执行 `wfi`（ARM64 的固定写法）。
读穿透读到的是**真实电平**——此时 GIC 确实为这个 CPU 拉高了线。于是 WFI 立即返回，
guest 走 `msr daifclr` 再取中断；但线并没有在 EOI 后降下来，下一次 idle 又是同样一幕，
每秒约 7k 次，双核永远起不完。

改造前的"拷贝线"只在 5 个点刷新，落到 WFI 时多半是陈旧的 0，于是 CPU 真的睡了。
**它能启动，靠的是陈旧，不是正确。**

抓到的 GIC 访问是 1056 次 `ICC_IAR1` + 1056 次 `ICC_EOIR1`，成对——guest 的 ack/EOI 路径是通的。
所以"线不降"另有原因（待查），读穿透只是把它从隐藏变成致命。

# 第二轮（14:50）：GIC 边沿追踪 —— "线卡住"的假设被推翻

给 `gicv3_cpuif_update()` 加了 `HENGE_GIC_TRACE=1` 的边沿日志（CPU、irq/fiq 前后值、
INTID、组、优先级），跑 60 秒 Debian 12 / `smp=2`：

```
henge-gic: cpu1 irq 0->1 fiq 0->0 intid=27 grp=2 prio=160
henge-gic: cpu1 irq 1->0 fiq 0->0 intid=27 grp=2 prio=255
...                       ← 成对出现，线在正常地起落
```

INTID 直方图：

| INTID | 次数 | 是什么 |
|---|---|---|
| 27 | 45991 | vtimer PPI |
| 1 | 6497 | SGI（IPI） |
| 8193 / 8194 | 3039 / 2383 | virtio-blk |
| 0 | 2640 | — |

**结论修正**：线**没有**卡在高位，它在 0→1→0 地正常翻转。之前
"EOI 之后线仍为高"的推断是错的——那是从 `HV_WFI_LOG` 的采样点看出来的错觉。

同时计时器是健康的：`CNTV_CVAL` 写入的 `delta` 从启动期 ~600k ticks
收敛到 ~249k ticks（62.5 MHz 下 4 ms = 250 Hz），全部是 `future`。
引擎的 CNTVCT 与 QEMU 的 virtual clock 没有跑偏。

所以读穿透失败的真实形状是：**诚实电平 + `cpu_do_idle` 的关中断 WFI**，
让 WFI 的返回频率从 250/s 变成 ~7k/s；问题在"谁在反复唤醒"，不在"线没降"。
下一步：在诚实电平下给 `wait_for_interrupt()` 的每条返回路径打点
（已有 `HV_WFI_LOG`，扩成 per-path 计数 + 每秒汇总），把 7k/s 归到具体路径。

```
WFI_SLEEP pc=…c5e9cc daif=c0 line=0
DECIDE    pc=…c5e9cc daif=c0 line=1 aux=0   ← 醒，线高但仍屏蔽
DECIDE    pc=…c5e9ec daif=0 line=1 aux=1   ← 开中断后立刻投递
IAR aux=27 → EOIR
```
计数器：`wfi=94 sleep=4986 delivered=6669 iar=6669 eoir=6669` —— 交付、IAR、EOIR 三者相等，
睡的次数远大于醒，正是健康形态。

B5（卡死）：

```
WFI_HIGH  pc=…c5e9cc daif=c0 line=1
DECIDE    pc=…c5e9cc daif=c0 line=1 aux=0   ← 同一 pc，没有前进
WFI_HIGH  pc=…c5e9cc daif=c0 line=1
...（35 秒内 2740 万次）
```
计数器：`wfi=27405088 sleep=952 delivered=1007 iar=1007 eoir=1007`。
**guest 卡在 `cpu_do_idle` 的 WFI 上原地重跑，永远到不了下一条 `msr daifclr`。**

## 结论（四分叉落点）

- **不是 A**（投递判决 bug）：B4/B6 的 delivered 与 IAR 严格 1:1；
- **不是 B**（hook 读错核）：per-CPU 断言一次都没触发（`seam cpu` 计数 0）；
- **不是 C**（spurious 风暴）：IAR 全是真 INTID（27/1），没有 1023；
- **不是 D**（primary/secondary 互等）：卡死发生在单核自己身上；
- **真正的位置**：`translate.c` 在 `MSR DAIF` 上把"读 lines_ptr 的早退"改成"恒真退出"，
  使 WFI 处的 pc 不再前进。这是把"少一次退出"的优化换成了"每次开/关中断都回宿主"，
  而回宿主路径在 WFI 上没能把 pc 带过去。

**读穿透本身成立**：B4（latch）和 B6（电平）都能启动，差别只在读哪一份。

## 最终采用的配置（B6，已验证）

1. `henge_irq_line_get()` 读 **`env->irq_line_state`（物理电平）**——一个所有者；
2. 引擎的投递判决、WFI 判据、`irq_check` 全部走 `hv_irq_line()` 读穿透；
3. **`translate.c` 保留早退版**（JIT 里读 `lines_ptr` 的那条快路径）。这条快路径读的是
   `HvPerCpu.irq_line`，仍由 `henge_irq_push()` 在"重入前 / kick / MMIO 后"刷新——
   于是形成清晰的分工：**JIT 读廉价副本，C 侧判决读真实电平**；
4. `HV_IRQTRACE=1` 的链式打点保留（默认关闭），GIC 边沿日志 `HENGE_GIC_TRACE` 保留。

实测：`smp=1` 26.6 s、`smp=2` ~31 s、`smp=4` 36.9 s 到 systemd 首批 target；
串口 522–544 行，与 TCG 同样的 boot 形状。

## 待办

- 查清 B5 的确切机制（"恒真退出"为何让 WFI 的 pc 不前进），再决定要不要重新引入那次优化；
- `HV_IRQTRACE` 目前只在风暴/每 16k 事件时 dump，若要做长期看护，加一个 HMP 命令按需 dump。

## -kernel 诊断（桌面）

Alpine `Image` 头（xxd）：

```
0x08 text_offset = 0        0x10 image_size = 0x03160000
0x38 magic = "ARM\x64"      0x18 flags = 0x0a（4K 页/小端）
```

`hw/arm/boot.c: load_aarch64_image()` 的规则：text_offset < BOOTLOADER_MAX_SIZE 时加 2 MiB，
所以内核被装到 **0x40200000**，而 **0x40000000 是 QEMU 写的 aarch64 引导桩**
（它的职责是把 DTB 地址放进 x0 再跳到内核）。

→ **H1（入口地址错）排除**：0x40000000 是引导桩的合法入口。
trace 里 `pc=0x40000000 x0=0` 说明桩没有把 x0 变成 DTB，随后 "复位到 0" 符合
"异常时 VBAR 仍为 0 → 取向量到 0" 的闭合链。
剩下 H2（桩执行了但寄存器/内存视图不对）与 H3（桩没执行，引擎看到的是空 RAM）。
裁决仪器：引擎侧异常 trace（ESR/EL/FAR/VBAR/new_pc）+ 桩首指令处的一次性 dump。

GPT 扫描 `/data/local/tmp/deb13-target.img`：

```

#2 ext4 lba=585728  30517 MB
```

ESP 的 FAT 引导扇区全零，且前 64 MB 里 `EFI` / `BOOTAA64` / `grubaa64` / `debian` 一个都找不到。

## `-kernel`：H1/H2 排除，病灶是二级核

加上 `earlycon=pl011,0x9000000` 后串口立刻有输出（70 行），最后一行为：

```
[ 0.047366] smp: Bringing up secondary CPUs ...
```

`smp=1` 时能一路跑到 init（`rdinit=/bin/sh` 退出后 panic，属预期，276 行）。
`trace=psci` 显示：

```
PSCI HVC fn=0xc4000003 -> 0x0        ← CPU_ON 成功
```

`HV_EXC_TRACE` 显示 CPU1 被正确 re-sync 到入口：

```
henge-boot: cpu1 pc=4236d408 x0=0 x1=0 pstate=00000013
```

但内核仍然停在 "Bringing up secondary CPUs"。

结论：
- **H1（入口地址错）排除**——0x40000000 是 QEMU 的引导桩，内核在 0x40200000；
- **H2（寄存器不全）排除**——x0/pstate 都对，CPU1 的入口也是内核给的 0x4236d408；
- 真正的问题：**DT 直启下二级核启动后没有完成握手**（ACPI/UEFI 路径下同样走 PSCI CPU_ON 却是好的）。

下一步仪器：在 CPU1 落到 0x4236d408 之后做一次性 block 追踪（打印头 N 个块与异常），
与 UEFI 路径下二级核的行为对照，找出"直启 vs ACPI"的差异点。

# 第八轮（18:30）：翻译 churn 拆解 —— 它不是 CPU 的账

`-accel henge,stats=30`，同一镜像，两个相位：

| 指标 | 101 s（活动） | 340 s（真 idle） |
|---|---|---|
| translated | 8666/s | **12/s** |
| again（va/va+pa） | 33% / 32% | 54% / 55% |
| 翻译占时间 | **3%** | **0%** |
| chained | 9066/s | 13/s |
| tlb flush | 9164/s | 275/s |
| exc / irq | 2234 / 373 | 60 / 48 |
| wfi | 345/s | 221/s |
| blocks held | 374849（101 MB） | 377728（101 MB） |
| full flush | 1 | 1 |

结论：

1. **churn 不构成 CPU 成本**：翻译只占 0–3% 的时间，idle 时每秒只有 12 次翻译；
2. 没有容量压力：全程只有 1 次 full flush，101 MB 稳定；
3. `again` 33–54% 说明"重译过的 VA"占一半，但绝对量太小，不是问题；
4. 所以 idle 的 CPU 账不在翻译，而在 WFI/park 路径（221 次醒/秒 + 60 次异常/秒）。

## 测量口径更正

上一轮我报的"CPU 0 37% / CPU 1 22%"是**解析 bug**（把 10 s 采样点的序号当秒数）。
同一窗口用 /proc/<pid>/stat 与逐线程求和重新测（300–350 s）：

```
proc  ticks: 15812 → 16709 (+897/50s) = 17.9% 单核
thread sum : 14469 → 15280 (+811/50s) = 16.2% 单核
```

即 5–6 分钟时约 **18%**；soak 在 8–25 分钟测得 11.5%，说明它还在缓慢收敛。
以后 idle CPU 一律用"proc ticks 差值 + 窗口秒数"，并同时记 threads 作交叉校验。

# 第九轮（19:00）：`-kernel` 病因 = GICv2 的 IPI 投递，不是入口也不是 EL

## 三针打完

1. **pstate 0x13 是假线索**：`pstate_read` = `0x400003c5` → mode=5（EL1h）、el=1、daif=0xf。
   `uncached_cpsr` 的 0x13 只是 QEMU 内部存储形态。**分叉 1 排除。**
2. **CPU1 没有卡在 bring-up**：从 0x4236d408 起逐块执行（secondary startup），
   最终落在 `cpu_do_idle`（0xffff8000814dcc88），约 2000 块/秒。
3. **CPU0 也在 cpu_do_idle**（同一地址、同一 why=2）——两边都进了 idle，
   说明 CPU0 的 `kernel_init` 在等一个永远不到的完成量，IPI/SGI 没有送达。

## 决定性对照

```
-M virt              (默认 GICv2)  → 停在 "smp: Bringing up secondary CPUs"
-M virt,gic-version=3              → 293 行，跑到 rdinit=/bin/sh 退出后 panic（= 已到用户态）
```

**所以 `-kernel` 的 bug 是 GICv2 下的 SGI/IPI 投递**；GICv3 路径（Debian 一直用的那条）没问题。
这也解释了为什么 UEFI/ACPI 能起双核、DT 直启不能：两者默认的 GIC 版本不同。

## 顺带发现

`rdinit=/bin/sh` 下 shell 立即 EOF 退出（panic），即使用 TCP 串口从启动就连着也一样；
说明 DT 直启时 init 的 stdin 没有接到 tty（earlycon 有输出、tty 控制台未接管）。
交互式 9p 测试因此改走 ISO 安装器（P1），不再依赖 `-kernel` 的 shell。

## 下一步

  目标 CPU 的 `env->irq_line_state` 是否被拉起；这是 -kernel 对齐 TCG 默认配置的最后一块。

# 第十一轮（20:20）：GICv2 三针结果 —— 发送侧正常，病灶是"屏蔽态 WFI 快返回活锁"

## 针 3（hop 0 补课）：SGIR 确实写了

`HENGE_SGIR_TRACE=1`（GICD_SGIR = 0x8000f00，MMIO 出口）：

```
henge-sgir: #1 val=00010001 len=4 cpu=1
henge-sgir: #2 val=00010001 len=4 cpu=1
```

0x00010001 → SGI irq=1、target mask=0x1（CPU0）。**发送侧没问题**，CPU1 走到了 `complete()`。

## 针 1：热循环 PC = cpu_do_idle（不是 WFE 锁环）

`HV_BOOT_TRACE` 每 10 万块采样，挂住 10 s 后两核都停在：

```
henge-bt: cpu0 #1100000 pc=ffff8000814dcc88 flags=7 el=1 why=2
henge-bt: cpu1 #900000  pc=ffff8000814dcc88 flags=7 el=1 why=2
```

0xffff8000814dcc88 = `cpu_do_idle` 的 WFI。**WFE 自旋锁候选不成立**（PC 不在锁环）。

## GICv2 侧：线算出来了，但只在早段送达

`HENGE_GICV2_TRACE=1`：

```
henge-gicv2: update cpu=0 best=27 prio=160 pmask=240 runprio=256 level=1
```

timer PPI 27 优先级足够、线算成 1；`HENGE_IRQ_LINE_TRACE=1` 统计 10 s：
**total=3632, level=1 只有 37 次**（都在早段），之后 `arm_cpu_set_irq` 只收到 level=0。

## 针 2 + IRQTRACE：屏蔽态 WFI 活锁


# 第十二轮（20:55）：仪器钉死后的 GICv2 真相 —— 定时器健康，SGI 1 从未成为 pending

## 两个仪器伪影，已修

| 伪影 | 证据 | 修法 |

```

```

`daif=c0` 说明 WFI 时 I 是屏蔽的（cpu_do_idle 的正常形态）。
**"引擎把 WFI 续行重置回块首"假设撤销。**

## 新的病根：SGI 1 写了，但 GIC 侧从未把它算成 pending

# 第十八轮（08:10）：判决点 —— SGIR 后线**起来过**，294 µs 后又被放下

2. 某次 `GICD_*` 写触发重算；
3. 另一次 gic_update 在别的事件里把 level 归零。

## 下一针（有界窗口）

## 结构性注脚（写回 translate.c 边界）

**"退出启发"这个被允许的用途本身就是 bug 的机制载体**——

# 第十九轮（14:30）：全量记录（不设窗口）——SGI 被取走了，IRQ 进过向量 15 次

## 读码三件

1. **timer 归属**：`m->tick` 不为空。`henge_tick_delta24()` 读的是 QEMU 的
   `env->cp15.c14_timer[GTIMER_VIRT]`；引擎自己的 `cntv_cval/cntv_ctl` 按注释
   "written once at reset and never again / stale forever"——客机写经 `sysreg_external`
   路由到 cpreg（`gt_cval_write`/`gt_recalc_timer`）。
2. **seam 路由**：CNTV/CNTP 的写在引擎 `sysreg.c` 的 case 之前就被 `sysreg_external`
   送走，所以引擎侧计数器零是设计使然，不是断链。
3. **`gic_update` 打印条件** `(best_irq != 1023 || irq_level)`：`best=1 & level=0` **会打印**，
   所以 989874 的静默落线只能是 `best=1023 & level=0`（pending 被清 = ACK）。用户的
   "屏蔽假象" 分支排除。

## 全量低速率日志（10 s，不设窗口）

```
IAR/EOIR 45 行：
  14 × IAR 3ff (1023 spurious) cpu0
  13 × IAR 1b (27) + 13 × EOIR 1b   → 13 次 tick
   1 × IAR 401 + 1 × EOIR 401       → 0x401 = CPUID 1 | INTID 1 = **SGI 1 被 CPU0 取走**
vec: cpu0 15 次，全部落在 offset 0x280 = **IRQ from EL1h**
SGIR 只有 irq=1（两次）
```

## 结论

- **SGI 1 确实被客机取走并 EOI**（IAR/EOIR 0x401），异常也进了 IRQ 向量（15 次）。
  所以"中断进不去"这条线排除。
- 卡在 "Bringing up secondary CPUs" 的原因**不在中断投递**，而在投递之后的完成/唤醒语义：
  - 客机只发了 SGI 1（call-function），**没有看到 SGI 0（reschedule）**；
  - arm64 的 `complete()` 唤醒走 resched IPI（SGI 0）；如果它没发/没到，
    CPU0 的等待任务不会被唤醒，5 s 兜底又依赖 tick——两条路同时死。

# 第二十一轮（19:55）：冻结探针裁决 —— 线高、引擎掩码、投递窗口缺席

探针落在 `henge_irq_line_get`（引擎每个块边界必经过）与 `hv_check_interrupts` 的未投递分支：

```
henge-decide: cpu0 pc=ffff8000814dcc88 daif=c0 l0=1 l1=0 el=1 I=1 F=1
henge-exitdump: cpu0 line=2 I=0 pc=ffff8000800244ec
```

- 权威线 = 2（HARD 高）；
- 引擎自己的 daif = **0xc0**（I/F 全掩码）——decide 不投递是**正确**的；
- QEMU 侧 `env->uncached_cpsr` 的 I=0 是**陈旧读数**（寄存器只在 seam 同步），
  这是本项目第三个"两视图不一致"的实例（copy、PSTATE、现在的 QEMU env）。

结论：
- **stuck-active 不成立**（不是 GIC 把线掩蔽住），T1/T2 两分支都不适用；
- 病灶是**投递窗口缺席**：客机在 `daifclr` 之后的未屏蔽窗口里走的是链式块，
  没有到达块边界检查；等它回到边界时又已经 `daifset`（0xc0）。
- 这与修法 C1（链链接轮询）+ C2（WFI 出引擎）完全对应；O1/O2 的 sticky 位是
  让"线变化"跨过链式块被看到的那一环。


- 它读的是 **copy**（`HvPerCpu.irq_line/fiq_line`），不是权威电平；
- C4 退役 push site 0/2 后，copy 只由 O1 的 `hv_engine_note_irq` 和 kick 维护；
- 而我们新写的 `hv_engine_note_irq` **无论 irq/fiq 都写 `irq_line`，从不写 `fiq_line`**
  ——一个正确性 bug（FIQ 事件覆盖 IRQ copy，FIQ copy 永远陈旧）；
- 更重要的是：fast_resume 是**绕过 dispatcher 的续跑路径**，它的中断门若读到陈旧 copy，
  就会带着 pending 中断续跑，直到下一次真正进 dispatcher——这就是"C1 有界汇合"的洞的
  具体位置（不是链节 thunk，thunk 每链都轮询 exit_req）。

## 下一针（一个小 build）

1. `hv_engine_note_irq(cpu, irq, level)` 增 irq 参数，分别写 irq_line/fiq_line；
2. `fast_resume` 的门改为读权威 `hv_irq_line(cpu, 0/1)`（与 hv_check_interrupts 同源），
   或至少同时校验 exit_req——把"有界汇合"钉在唯一真值上；
3. 加 word→next-exit→IAR 延迟仪与 gap 内 PC 环（上一轮预注册），验证洞是否就是 fast_resume。

# 第三十二轮（16:20）：两点告警链命中 —— IPI 在目标核 pending 超过 5 ms，目标 running、HARD=1

## 告警数据（UEFI v3，115 次命中）

判读（按预注册表）：

| 字段 | 值 | 含义 |
|---|---|---|
| pending | hppi=0（SGI 0） | **中断仍 pending，没被取走** |

## 结论

**IPI 在目标核 pending ≥5 ms，目标在跑、可抢占、HARD 已置，却没有被取走。**
三种可能：

1. 目标在 **IRQ 屏蔽的临界区**（DAIF.I=1）里跑得久——引擎正确地不取，等它开中断；
2. 目标在引擎内**没有到达块边界**（长块/单块循环）——汇合点缺席；

- PC 紧簇（同一地址）+ I=1 → 临界区/自旋死锁；
- PC 多样 + I=0 → 汇合点缺席（块边界没到）；
- PC 多样 + I=1 → 长临界区（等它自己结束）。

## 客机代码 dump（在告警时刻，CPU1）

```

code[ffff800008c7e2e0] = 72003c3f   ands   wzr, w1, #0x...
```

`daif=c0`（I/F 全屏蔽）、`can_preempt=0`（running priority=160，被自己/别人占着）、

CPU1 在**带中断屏蔽的锁自旋**（LDAXR + b.ne 回跳）里，锁被 CPU0 持有；

## 下一步

1. 确认锁字地址（x19）与 CPU0 持有的锁是否同一（引擎可 dump x19 的 va+pa）；
2. 若是同一把锁 → 客机的 BPF JIT + kick_all_cpus_sync 竞态被我们的调度时序放大；
   修法方向：让 IPI/唤醒在目标进入屏蔽区前到达（或在屏蔽区内也能被"看到"），
   即回到"事件界"——IRQ 屏蔽时的 IPI 应能让目标在 unmask 后立刻取，而不是永远等。
3. 若是不同锁 → 另一个 guest 死锁，需要更细的锁归属。

# 第四十一轮（23:15）：第四笔学费 + 免费读码（deadline 传播正确）

## 学费 #4（对半入账）

- **park 时长 ≠ 唤醒延迟**：4.7 ms avg、Σ33 s/核 是**上界**，不是税额；
  税 = wake − event 到达，两个端点从未同时打戳；
- **上界 ≠ 判决**；**门槛条件必须命名 metric，不得只指仪器**（“唤醒 avg ms 级”没钉住 metric 名字）；
- 旧句“唤醒税定案”改写为“上界成立（33 s/核 parked）、税额未测”。

## 免费读码：main-loop 的 poll timeout 取 timerlist deadline

`util/main-loop.c:590`：
```c
timeout_ns = qemu_soonest_timeout(timeout_ns,
                                  timerlistgroup_deadline_ns(&main_loop_tlg));
```
→ **deadline 传播正确**，“固定 poll 间隔”假设**证伪**；
“迟到火”假说先折半：若 fire 迟到，机制只能来自 **main-loop 忙**（设备/IO/BQL），
不是 timeout 算错。

## 推论更新

- 4.7 ms 的 park 很可能大部分是**合法睡眠到 CVAL deadline**（2–5 ms 桶 ≈ 250 Hz tick 周期），

- 统一模型（事件出生节拍）仍待五戳链裁决：deadline → fire → kick → wake → decide → IAR；
- 中间点选项的定性仍是**产品选择**（deadline 门控本已原生），除非五戳链抓到 main-loop 忙的证据。

# 第四十二轮（07:30）：四戳链读数 —— wake_late ≈ 110 µs，95% 的 park 由事件终结

## 判决（三指标命名）

| 指标 | 读数 | 裁决 |
|---|---|---|
| **wake_late**（事件置位→running） | **~110 µs**（<0.5ms 占 95%+） | kick→wake 路径快，**无税** |
| **timeout_ended** | 3–5%（162–180 次） | 少量超时终结，非主体 |
| **park 时长** | 4.4–4.7 ms，长 tail 也由事件终结 | **合法睡眠**（客机自己的 CVAL 周期） |

- 4.7 ms 的 park = 客机选择睡多久（它的事件没到之前都在睡）；
- 醒来时 95%+ 是事件终结、且只花 110 µs 进入 running——**上游投递不慢**；
- 结论：**44 s 的 wall 差不是"唤醒税"**，而是基线风暴把客机的睡眠人为切短
  （24k/s 的 WFI 快返回让客机不断重检查、更早推进），用 CPU 换的 wall。

## 中间点选项（按预注册死活条款）

fire_late ≈ 0（deadline 传播正确、wake_late 110 µs）→ **timer 轮询版按现规格死掉**；
若未来要缩短 wall，唯一杠杆是"主动缩短客机睡眠"（= 风暴），即用 CPU 买 wall——
这是产品决策，不是 bug fix。

# 第四十四轮（16:15）：立项书退回 —— IAR 56 µs 是重尾样本，不是单价

## 学费 #4 第三实例：单价 ≠ 分布

| 读数 | 值 | 身份 |
|---|---|---|
| claim | 0.85 µs | 稳定 |
| scan（32 个 SGI/PPI） | 1.36 µs | 稳定 |
| cpuif update（qemu_set_irq→O1→cpu_interrupt） | 9.7 µs（波动到 58） | 重尾 |
| **稳定构成合计** | **~12 µs** | GIC 内部真实构成 |
| 旧“IAR 单价” | 56–58 µs | **单次重尾样本** |

结论：**56 µs 是 max 侧样本，不是均值**；若真实均值 12–15 µs，
seam 溢价总账从 ~5 s 缩到 **~1–1.5 s**（外加 BQL 争用段，未单列）。
立项书第一页的收益上限从“五秒级”降到“一秒级”；快窗动机保留，但 ROI 必须先摆上桌。

## KVM 对照入册（参照，不是依据）

KVM 衔接窄（ioctl/eventfd/共享页）是因为 **GIC 与 vCPU 同栈**（内核 vGIC）：
- vCPU 运行 = KVM_RUN + kvm_run 共享页；
- 中断 = KVM_CREATE_IRQCHIP（内核 vGIC）+ KVM_IRQFD/KVM_IRQ_LINE；
- 设备快速路径 = ioeventfd；WFI = 内核阻塞 + halt_poll；
- ICC sysreg 在内核处理，不 exit。

对照表当 **架构参照**；收益必须自己算（上面重算过）。

## 架构案骨架（窗口用，先于代码）

1. **范围边界**：per-CPU ICC（ICC 接口 + redistributor cpuif 侧）进引擎；
   distributor 留 QEMU。vtimer 是同类（CVAL 22 µs 也是 seam 价），与 ICC 共用
   “per-CPU sysreg 快窗”机制——但 vtimer fire 带 main-loop deadline 接口，
   范围决策点：第一步含不含 vtimer 寄存器访问（fire 留 QEMU、CVAL 写跨栈 arm）。
2. **不变量移交清单**（最重）：
   - 单真值 / C1 有界汇合 / C2 睡眠正确性的主人换栈；
   - **census 关账绑定当前架构**：“线写入者全部 BQL 下”是 parked ⇒ 无 pending 的论证支柱；
     ICC 搬引擎后线由引擎喂 latch、跨线程无锁，BQL 串行化论证失效，需新同步序
     （引擎写 latch + 唤醒的配对）。
3. **一致性协议**：GICD↔引擎共享状态清单（SPI pending/route/affinity）+ 变迁通知方向
   = 新的事件界；检查点先于代码。
4. **验证**：状态所有权搬家没有 codegen diff——用 **IAR/EOI 序列 trace diff**（henge-win 旧仪器）
   做行为等价，叠全矩阵 + 门槛五件。

## 序列

1. 本 build：fire 戳 + armed-deadline Δ + 唤醒原因细分 + **IAR 直方图化**（收口批与立项同一 build）；
2. 三跑：UEFI（gap 类直方图定 CNTVCT）+ v2（decide:take）+ RT（最后缺员）；
3. 三终局裁决 → 证书落笔 + 产品决定一行（决定架构优先级）；
4. 架构窗：按重算数字立项；若 CNTVCT 类占 gap 大头，**内联 CNTVCT 几小时定向修先行**。

## 记账

- 学费 #4 第三实例：单价 ≠ 分布（park avg 4.7 → IAR 56 → 同一物种）；
  判据表加一行：**价格模型用直方图，单样本不进立项书**；

## IAR 分布直方图（turn 109，收口批）

```

hist(<2/5/10/20/40/80/160/>=160us) = 293/15948/9263/7019/4002/104/99/4489
```

# 第四十八轮（18:05）：证书签字

## take = 1.000 的评注（效力边界）

- 验证的是 **decide→deliver 无丢失**；ready 且未屏蔽则交付本是语义要求，1.000 是预期值；

- spurious:delivery ≈ 1:1 是客机双读签名（处理后再读撞 spurious），benign，留作行为指纹。

## TCG smp2 = 239 s 的评注

- 补跑修正读法：smp4 惩罚是**通用 boot 成本**（TCG +134 s、henge +16 s）；

## 第五十二轮（09:25）：算术对账 —— settle=0 与 bb-persistent 不互斥，机制是入口 tap 领先窗

### 算术矛盾的解：两个观测点采样**不同时刻**

- "方向单一 = 语义差异" **撤回**：入口 tap 架构下窗口结构性单向；
- "3 例不是排序窗" **撤回**：线边沿是 mid-service 观测点，不是 settle；

- 把两侧都换成裸 `ldr`（volatile asm，绕过一切编译器缓存）后结论不变：
  写者裸读=1，读者裸读=0（周期性 10 次，地址恒定）；
- 单进程、同一虚拟地址、裸读，一侧 1 一侧 0——内存模型层近乎不可能；
  怀疑第三类：写侧的 1 在**同一地址**上被后续某次写覆盖为 0，而覆盖者不经过
  我们观测的 update（例如另一线程/另一映射），或该地址所在页在某一侧被重新映射；
- 下一步（按阶梯 tier 3）：gdb 硬件观察点 `watch -l *(int*)0xb400...`（ASLR 下需
  在 gdb 里取地址），Termux 尚无 gdb，需 `pkg install gdb`（约 50MB）后执行；
  这是唯一能区分"谁改了它"的手段。

## 第一百轮（03:00）：身份病破案——`hv_engine_note_irq` 覆盖权威线副本

- 真因（第七个"重复真相"案例）：accel 的 O1 线钩子在每次 QEMU `arm_cpu_set_irq`
  边沿调用 `hv_engine_note_irq()`，后者把 QEMU 的线电平写进 `pc_state->irq_line`。
  权威模式下 QEMU GIC 已退役，它的"0 边沿"把引擎 GIC 刚置的 1 压回 0——
  于是写者（GIC update）1、读者（kicker/注入）0，裸读也一样，且与布局/实例无关；
- 修法：`hv_engine_note_irq` 在 `g_auth_g` 存在时只置 exit_req，**不写线副本**；
- 修后：smp1 boot 从 0.15s 前进到 **0.907s**（serial 165），新的 panic 是
  `stack-protector: Kernel stack is corrupted in: __invoke_ps...`（PSCI 调用路径的栈损坏）；
- 判读：身份病关闭；剩余是 PSCI 栈/状态链（新的、更靠后的层），与 IABT 同源候选。

## 第一百零一轮（03:15）：新 panic——`__invoke_psci_fn_hvc` 的栈金丝雀损坏

- 现场：CPU0 PID 0 `swapper/0`，0.9s；`stack-protector: Kernel stack is corrupted
  in: __invoke_psci_fn_hvc+0x70/0x70`；回溯里出现 `psci_system_suspend_enter`、
  `__ktime_get_real_seconds`（suspend/idle 路径）；
- 判读：guest 在 idle/suspend 的 PSCI 调用（HVC）返回时，包装器帧的金丝雀被踩——
  嫌疑在引擎的 HVC 异常入口对 guest 栈的处理（异常帧写入的 SP/SPSR 恢复），
  或 PSCI_CPU_SUSPEND 恢复语义；
- 与 IABT 同源候选：都是"引擎在 guest 栈/寄存器上的写"；
- 下一步：查引擎 HVC 外部调用路径的异常帧（take_exception for HVC/PSCI）是否写栈、
  用哪个 SP（EL1 vs EL0），并对照 QEMU 的 arm_handle_psci_call 前后 env.sp 的期望。

## 第一百零二轮（03:30）：HVC 外部路径不写 guest 栈——嫌疑转向 suspend 路径

- 读码：`hv_exception_insn` 的 HVC/SMC 外部分支只设 exit_reason/pc，**不写 guest 栈**；
  translate 对 EL1 的 HVC 也是"像调用一样"继续（不产生 guest 异常帧）；
- 因此 `__invoke_psci_fn_hvc` 的金丝雀损坏不是该路径直接写栈；
- 回溯出现 `psci_system_suspend_enter`——嫌疑在 suspend/idle 的 PSCI CPU_SUSPEND
  处理（QEMU 的 arm_handle_psci_call 对 SUSPEND 的返回语义/恢复），或 guest 的
  协程栈被换出后恢复不完整；
- 下一步：带 HENGE_AUTH_TRACE 复跑，抓 panic 前的 PSCI 序列（尤其 0xc4000001
  CPU_SUSPEND）与返回；再决定是引擎侧恢复语义还是 guest 的 suspend 状态机。

## 第一百零三轮（03:45）：进展但**不稳定**——两类 panic 交替（0.11s idle-kill / 0.9s 栈金丝雀）

- 同配置两跑：
  - j2：0.907s，`stack-protector ... __invoke_psci_fn_hvc`；
  - j3：0.111s，`Attempted to kill the idle task`，无 PSCI trace；
- 说明修掉 note_irq 覆盖后，boot 能到较深，但仍有**早期竞态**（0.1s 级）与**晚期
  suspend 栈问题**（0.9s 级）两族；
- 下一步：先压早期族——0.1s 的 idle-kill 发生在 kernel init 早期，与 tick/唤醒相关；
  在 note_irq 修复后的新基线上重跑 N 次统计两族的比例，再逐个修。

## 第一百零四轮（04:00）：4 跑统计（1 深 / 3 早）+ 早期 panic 仍是同一 hvc 存储异常

- 4 跑：0.867s ×1；0.059/0.066/0.069s ×3——**早期族主导**；
- 早期 panic 现场（0.066s）与晚期同形：
  ```
  x0=-1  x1=0xc4000012(SYSTEM_RESET2)  x4=0x02093fa0  stp x0,x1,[x4] 故障
  ```
  fn 出现在 x1 而 x0 是上一次返回值——**参数错位一位**的形态；
- 该路径是 kernel 的 panic/restart（SYSTEM_RESET2）+ smccc 包装器写 res；
  res 指针 0x2093fa0 是物理样地址，说明调用者的栈/寄存器已被踩；
- 下一步：反汇编 kernel 的 SYSTEM_RESET2 调用点（符号 psci_system_reset2 /
  machine_restart），核对 hvc 前的寄存器布局，判断是 guest 自身路径还是引擎的
  寄存器/栈搬运错位。

## 第一百零五轮（04:15）：反汇编对账——kernel 设置正确，panic 现场寄存器被移位

- `psci_sys_reset+0x5c`（SYSTEM_RESET2 分支，0xffff8000810a7528）：
  ```
  mov x0,#0x12; mov x1,#0; movk x0,#0xc400,lsl16   → x0=0xc4000012, x1=0
  blr x4
  ```
  → kernel **设置正确**；
- 但 panic dump：`x0=-1, x1=0xc4000012`——**整体移位一位**；
  wrapper `__arm_smccc_hvc` 的 `ldr x4,[sp]` 从 guest 栈取 res 指针，
  dump 里 x4=0x02093fa0（物理样垃圾）→ 存储故障；
- 结论：panic 发生前 guest 的寄存器/栈已被移位/污染（与"进 panic 前状态已踩"
  一致），不是 hvc 路径本身写坏；
- 引擎侧 save/load 的 SP 处理（spsel 双 bank）读码看是正确的；
- 下一步：找移位/污染的上游——两族 panic（0.06s idle-kill、0.9s 金丝雀）同源于
  "guest 状态在某个引擎写点被移位"，优先查引擎的异常入口/恢复序列与
  env 往返（spsel/EL 切换时）。

## 第一百零六轮（04:30）：原始 oops 定位——guest 访问 0x2093fa0（未映射物理/截断指针）

- 早期族的第一现场：`Unable to handle kernel paging request at virtual address
  0000000002093fa0`（EC=0x96000044，data abort translation fault）；
- 0x2093fa0 不在 RAM（0x40000000–0x80000000）内，也不是内核线性映射 VA——
  像**被截断/被污染的指针**（与 res 指针同值）；
- panic 的移位寄存器是下游；上游是"guest 某处拿到了坏指针 0x2093fa0"；
- 下一步：找 0x2093fa0 的来源——近期 guest 从引擎读取的 sysreg/MMIO 值里是否有
  该地址（截断的 kernel VA 低位），用 HENGE_TRACE=sysreg/mmio 抓早期访问序列。

## 第一百零七轮（04:45）：MMIO 轨迹无 0x2093fa0——来源不在早期 MMIO

- `-accel henge,trace=mmio` 早期轨迹：全是 UART（0x9000000/0x9000018），
  值里没有 0x2093fa0；
- 本跑 serial=84（又提前停——波动仍在）；
- 下一步：改抓 `trace=sysreg`（ID/系统寄存器读取），看 guest 早期是否从某个
  sysreg 拿到含该地址的值；同时继续记录两族 panic 的分布。

## 第一百零八轮（05:00）：坏指针来源锁定——`__invoke_psci_fn_hvc` 的 `mrs x4, sp_el0`

- 反汇编 `__invoke_psci_fn_hvc`（0xffff8000810a7400）：
  ```
  mrs  x4, sp_el0
  ldr  x5, [x4, #1184]     ← 栈金丝雀读（[sp_el0+canary_off]）
  str  x5, [sp, #56]
  add  x4, sp, #0x18       ← res = sp+0x18
  stp  x4, xzr, [sp]       ← 存 res 指针
  bl   __arm_smccc_hvc
  ...
  canary check: ldr x3,[sp,#56]; ldr x2,[sp_el0,#1184]; cmp; b.ne __stack_chk_fail
  ```
- 原始 oops `paging request at 0x2093fa0` 正对应 `ldr x5,[x4,#1184]` 的 x4 坏值——
  **引擎的 `sp_el0` 是坏的**（不是栈帧，是 SP_EL0 寄存器）；
- 两个 panic 由此统一：sp_el0 坏 → 金丝雀读/检失败（stack-protector panic）；
  同一寄存器影响 res 指针路径（x4 从 [sp] 取到旧值/垃圾）；
- 下一步：抓引擎在 wrapper 处的 `cpu->sp_el0 / cpu->spsel / cpu->el`，
  并核对 `MSR SP_EL0`（translate.c:1685）在 EL1/spsel 下的写路径是否被某条
  seam 往返（save/load 或 hv_sp_switch）覆盖。

## 第一百零九轮（05:15）：sp_el0 在早期变为垃圾——原始 oops = [sp_el0+1184] 的 canary 读

- HVC 状态打印：早期 VERSION/FEATURES 调用时 `sp0=0xffff800082af74c0`（有效）、
  sp=有效栈、x0=fn 正确；第 8 次调用（panic 路径）x0=-1、x1=fn（下游污染）；
- 原始 oops 地址随跑变化（0x2093fa0 / 0x2065700），但都 ≈ `sp_el0+1184`：
  即 `__invoke_psci_fn_hvc` 的 canary 读用了**坏的 sp_el0**；
- 结论：引擎的 `sp_el0` 在 0.05s 前后被某条路径写坏（上下文切换的 MSR SP_EL0、
  异常入口/ERET 的 bank 交换、或 seam 往返的 sp_el[0]）；
- 下一步：在异常入口（hv_take_exception）、ERET（hv_pstate_set）、seam 往返
  （save/load）后各打 sp_el0/sp/spsel/el，定位变坏的那一步。

## 第一百一十轮（05:30）：sp 轨迹——早期物理 SP（0x43354000）后转有效虚拟 SP

- sp-trace（异常入口/switch）：第一次异常 sp=0x43354000（物理，MMU 之前的早期 boot），
  sp0/sp1 均 0；随后 sp=0xffff8000...（有效）、sp0=0xffff800082af74c0（有效）、sp1 有效；
- 即 bank 交换在早期之后是自洽的；坏 sp_el0（canary 读）出现在更晚的某个点，
  本轮 trace 未覆盖到（40 行上限，主要停在 boot 早期）；
- 下一步：把 trace 改为"只在 sp_el0 越界（非 0xffff8000_... 也非 0x4335...）时打印"
  或只在 smccc wrapper 附近打印，抓变坏瞬间；并检查早期物理 SP 阶段是否有
  EL0/EL1 bank 误交换（第一次异常前 el=1/spsel=1 已成立）。

## 第一百一十一轮（05:45）：sp 采样仍未抓到变坏点（有效值：0xffff0000034b0000 等）

- 每 200 次采样：sp=0xffff80008000bcc0、sp0=0xffff0000034b0000（fixmap/EFI VA，有效）、
  sp1=有效——采样点都自洽；boot 仍早停（serial 163）；
- 坏 sp_el0 的瞬间没落在采样点；改为"只在越界时打印"（判据：非 0、非 0xffff0000_…
  也非 0xffff8000_… 即异常），一次跑就能抓到；
- 下一步：实现越界过滤打印，并同时打印调用上下文（异常入口/ERET/seam 三处各一个 tag）。

## 第一百一十二轮（06:00）：sp_el0 全程有效（fixmap 值）——晚期金丝雀是 wrapper 帧/SP 位移

- sp0 变更日志：0xffff0000034b0000 / 0xffff0000034b1100 / 0xffff0000034c1100 交替
  （fixmap 的每核栈），sp1 有效——**sp_el0 没有变坏**；
- 本跑 0.903s，晚期 panic：`stack-protector: ... __invoke_psci_fn_hvc+0x70`；
- 于是晚期金丝雀损坏的机制改为：wrapper 的帧（`sub sp,#0x50` 后 canary 在 [sp,#56]）
  在 hvc 往返（seam 的 save/load + QEMU psci）后**SP 被移位或帧被写**；
  sp_el0 无辜（前一轮把 0x2093fa0 归给 sp_el0 的推断需收回——那个地址是 canary 读
  的故障地址，但 sp_el0 本身在采样里一直有效；真正被踩的是帧内 canary）；
- 下一步：在 seam 服务前后打印 engine 的 sp（不是 sp_el0），看 PSCI 往返是否移位；
  尤其 CPU_SUSPEND（0xc4000001）路径。

## 第一百一十三轮（06:15）：PSCI seam 的 SP 往返干净

- psci-sp 轨迹：pre sp=0xffff800082ae3c80 → post envsp1=同值（sp0/sp1 也保持）；
  ret 与 PSCI 语义一致（VERSION=0x10001、FEATURES=2 等）；
- 即 **seam 的 save/load 没有移位 SP**——晚期金丝雀不是 seam 移位；
- 早期 panic 仍在（0.0597s，paging request 0x21a7f10，同样 ≈ sp_el0+1184）；
- 下一步：查 wrapper 的 canary 槽 [sp,#56] 在 hvc 前后的写入者——把引擎的
  翻译/存储路径在该栈地址上做写监视（或对比 hvc 前后该槽的值，打印引擎侧内存读）。

## 第一百一十四轮（06:30）：sp_el0 = arm64 的 `current`——观测值 0xffff0000_034b0000 可疑

- arm64 上 **SP_EL0 保存 `current` 任务指针**；wrapper 的 canary 读 `[sp_el0+1184]`
  = `current->stack_canary`；
- 引擎的 MSR SP_EL0 处理两条路（translate 快路径 store HV_CPU_SP_EL0、sysreg 慢路径
  `cpu->sp_el0=v`）都在，且 trace 显示 sp0 确实在变（0xffff0000034b0000 /
  0xffff0000034b1100 / 0xffff0000034c1100）；
- 但 0xffff0000_034b0000 在 48-bit VA 布局下**不是内核规范地址**（bit47=0 → 用户空间）；
  若内核 VA 布局是 48-bit，这个值不可能是合法的 `current`；
- 下一步：确认内核 VA 位宽（48/52）与该值合法性；若不合法，查引擎在哪个点把
  current 写成了 0xffff0000_...（MSR SP_EL0 的值来源）。

## 第一百一十五轮（06:45）：MSR SP_EL0 两条路径都在（快路径/慢路径/helper 兜底）

- translate 快路径：`SR(3,0,4,1,0)` 在 `el1 && spx` 时 store HV_CPU_SP_EL0；
  不满足时返回 0 → 走 `HV_OP_MSR` helper；
- sysreg 慢路径：`if (!cpu->spsel) return -1`（UNDEF），否则 `cpu->sp_el0 = v`；
- 即 MSR SP_EL0 的处理语义完整；"sp_el0 停在早期物理值"的假设需要**在 oops
  时刻直接读数**来证实/证伪（当前只有采样值）；
- 下一步：在引擎的故障路径（hv_take_exception 的 sync 分支）打印 sp_el0/当前 pc，
  与 oops 地址对照（oops VA - 1184 应等于当时的 sp_el0）。

## 第一百一十六轮（07:00）：决定性读数——sp_el0 有效；坏的是 [sp] 里的 res 指针

```
sync-exc: pc=ffff8000800244f4 far=1e77010 esr=96000044
          sp0=ffff800082af74c0（有效） sp=ffff800082ae3c90 spsel=1 el=1
```

- 故障指令 = `__arm_smccc_hvc+0xc` 的 `stp x0,x1,[x4]`（0x244f4）；
- `far=0x1e77010` = x4 = **从 [sp] 读出的 res 指针**（垃圾）；
- **sp_el0 有效** → 前两轮对 sp_el0/current 的怀疑收回；
- 外层 wrapper 在 hvc 前 `stp x4,xzr,[sp]` 写入的是 `sp+0x18`（合法栈地址），
  hvc 返回后 `ldr x4,[sp]` 却读到 0x1e77010——说明**该栈槽在 hvc 期间被覆盖**；
- 候选：seam 服务期间有 host 侧写 guest 内存；或该 store 未落到预期槽
  （引擎的 ADD/存储路径）；下一步在该槽（0xffff800082ae3c90）上做写监视
  （引擎已有 m->watch_va 机制，可直接设置）。

## 第一百一十七轮（07:15）：抓到了——wrapper 的 `sub sp,#0x50` 未生效（SP 算术 bug）

- watch 日志抓到了覆盖 res 槽的写者：
  ```
  watch: write to ffff800082ae3c90 = 1fcd800 (8-byte) by pc ffff800080097434 x30 ffff800080098744
  ```
  即内核函数 0x80097434 向**它自己的 [sp]=0x...c90** 写局部量 0x1fcd800；
- 而 smccc wrapper 的 [sp] 也是 0x...c90（trap 时的 sp）——说明 wrapper 的
  **`sub sp,sp,#0x50` 没有生效**：它的帧与调用者的帧重叠，res 槽被调用者的局部量覆盖；
- 这解释了两个 panic 族：res 指针读到调用者的局部值（0x1fcd800/0x1e77010/0x2093fa0），
  canary 槽也被踩；
- 下一步：审计引擎对 `ADD/SUB (immediate) Rd=SP` 的翻译（put_sp_add 一类），
  特别是 16 字节对齐形式与 writeback；这是最后一个环节。

## 第一百一十八轮（07:30）：SP 算术本身正确；嫌疑在 helper thunk 的 SP 保存/恢复

- `put_add_imm` 对 `sub sp,sp,#0x50`（d=n=31、imm=0x50）发出的是
  `sub sp,sp,#0x50`（d=31 即 SP）——**指令编码正确**；
- 引擎约定"块运行期间 guest SP = host SP"（translate.c:570）；
- `put_helper` 只保存 x30、加载 thunk、ADR info、BLR thunk，**不显式保存/恢复 SP**；
  thunk（HV_CPU_HELPER_THUNK 汇编）负责 SP 的保存/切换/恢复；
- 现象（trap 的 cpu->sp = 调用者 sp）= thunk 保存的 SP 不含 wrapper 的 sub，
  或块退出时 cpu->sp 同步点不对；
- 下一步：读 thunk 汇编（helper thunk）的 SP 处理：入口是否保存 guest SP、
  出口是否恢复；以及 HVC 外部退出路径（exit_reason 设置后）是否在正确点同步 cpu->sp。

## 第一百一十九轮（07:45）：thunk 的 SP 保存/恢复是对的——sub 在别处丢失

- `hv_helper_entry`（enter_elf.S:180）：
  ```
  mov x2, sp; str x2, [x28, #CPU_SP]     ← 保存 guest SP（helper 入口）
  ldr x2, [x28, #CPU_HOST_SP]; mov sp, x2
  ...
  ldr x0, [x28, #CPU_SP]; mov sp, x0     ← 恢复
  ```
  即 helper 边界的 SP 往返正确；refill 路径也保存 `mov x15,sp; str x15,[x28,#CPU_SP]`；
- 但 watch 显示 wrapper 的 `stp x4,xzr,[sp]` 落在**调用者的 sp（c90）**，而不是
  wrapper 的 `sub #0x50` 之后（c40）——sub 在 wrapper 自己的块内丢失；
- 下一步：在块边界（exit/dispatch）打印 host sp 与 cpu->sp 的差，定位 sub 之后
  哪次边界同步把它覆盖回旧值（候选：chained exit、is_stolen 的 SP 拷贝、
  put_exit 不保存 SP 而由 dispatcher 事后覆盖）。

## 第一百二十轮（08:00）：hv_exit/hv_helper_entry 都正确保存 SP；丢失发生在 wrapper 块内

- `hv_exit`（enter_elf.S:158）：`mov x0,sp; str x0,[x28,#CPU_SP]` —— 正确；
- `hv_helper_entry`（:180）：保存/恢复 `CPU_SP` —— 正确；
- psci-sp 轨迹的 pre 值 = trap 时的 cpu->sp（c90，已经是旧值）→ **sub 的丢失在
  进入 seam 之前**，即 wrapper 块执行期间；
- 下一步：在 dispatcher 的 hv_enter（块入口）与退出点打印 host sp vs CPU_SP，
  限定在 wrapper 的 pc 范围（0x810a7400-0x810a7470），看块入口是否带着旧 SP
  （即上一条链的 CPU_SP 没更新），一次跑即可定位。

## 第一百二十一轮（08:15）：块入口/出口 SP 探针就位，但未触发（范围/时机待核）

- 在 dispatch.c 的 `hv_enter(cpu, b->code)` 两侧加 `blk-enter/blk-exit` 探针
  （限定 wrapper pc 0x810a7400-0x810a7480）；
- 跑后无输出（serial=107，早停）——要么早停发生在 wrapper 之前，要么进入时的
  cpu->pc 不在范围内（block 的 va 与 cpu->pc 的差异），要么 wrapper 的块被链式
  跳转进入（不经过该调用点）；
- 下一步：确认探针是否在二进制里（strings）、并把范围放宽到 0x810a7000-0x810a9000，
  同时在 hv_check_interrupts 的 sync 路径已抓到 wrapper（0x244f4）作为对照。

## 第一百二十二轮（08:30）：wrapper 是**链式进入**（不经 dispatcher 的 hv_enter）

- 探针确认在二进制里（strings=1）；范围放宽到 0x810a7000-0x810a7700 后**仍不触发**；
- 同跑 sync-exc 仍是 `pc=ffff8000800244f4 far=25be3d0 sp=...ae3c90`——内层 wrapper
  的块确实执行了；
- 结论：外层 wrapper（0x810a7400）经**间接分支缓存/链**进入，绕过 dispatcher 的
  hv_enter 探针；其 `sub sp,#0x50` 的丢失点在链式路径上（块前导/链目标/CPU_SP 同步）；
- 下一步：把探针移到链目标（b->code 的入口）或 hv_enter 汇编本身，并在链式
  转移前后打印 CPU_SP，定位 sub 丢失；这是最后一段。

## 第一百二十三轮（08:45）：关链后仍不经过 hv_enter——外层 wrapper 走 IJC thunk

- HENGE_NO_CHAIN=1 + trace：panic 同类（paging 0x42919f0）；探针仍 0 次；
- 即外层 wrapper（0x810a7400）即使关链也是经 **hv_ijc_thunk**（间接分支缓存）
  进入目标块，不经过 dispatcher 的 hv_enter；
- 结论：SP 丢失点在 IJC 目标块的入口/前导或 CPU_SP 同步，而非 dispatcher 路径；
- 下一步：在 IJC thunk 的跳转处（或目标块入口）打印 CPU_SP 与 host sp，
  这是最后一段；walk 顺序：hv_ijc_thunk → 目标块前导 → sub → 第一次 CPU_SP 同步。

## 第一百二十四轮（09:00）：块无前导（live 寄存器）；sub 与 helper 入口的 SP 矛盾待 asm 级验证

- 读码：块**没有前导**（translate.c:2119 "No prologue: hv_enter, chained exits and
  the indirect-branch cache all..."）——guest 状态在 host 寄存器里跨块保持，
  guest SP 就是 host SP；
- 因此 `sub sp,#0x50` 是 host SP 的原生减法，应当直接生效；
- 但 helper 入口保存的 CPU_SP（= 异常打印的 sp）仍是 **c90**（sub 前的值）——
  与"无前导、原生 sub"矛盾；
- 下一步（asm 级）：在 hv_helper_entry 的 `mov x2,sp` 前与块内 sub 后各取一次
  host sp（例如用 mprotect/断点或直接加一条临时 str 打印到固定槽），
  确认 sub 是否真的改了 host SP；若没改，检查 translate 对该 ADD/SUB(imm,SP)
  的发射路径（put_add_imm 的 "never SP" 契约是否被违反）。
