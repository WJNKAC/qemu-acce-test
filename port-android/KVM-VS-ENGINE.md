# KVM vs 直通翻译器 vs TCG —— 四方对比

这台设备（OPPO PDYT20 / OP4E21，Android 12）**有 root，也有可用的 `/dev/kvm`**，
于是第一次能把四条执行路径放在同一台机器、同一个客户机镜像上对比：

| 路径 | 是什么 | 需要什么 |
|---|---|---|
| **原生** | 设备上直接跑 | — |
| **KVM** | QEMU + `-accel kvm`（硬件虚拟化，EL2） | root + `/dev/kvm` + 内核能在 EL2 上 |
| **加速器** | `hv-linux`（本项目的 ARM64→ARM64 直通翻译器） | 只要用户态 |
| **TCG** | QEMU + `-accel tcg`（纯软件翻译，同 ISA） | 只要用户态 |

## 这台设备的实测条件

| | |
|---|---|
| 型号 | OPPO PDYT20（device 名 OP4E21），Android 12 / SDK 31 |
| SoC | 联发科（PMIC mt6358），8 核 = **6× Cortex-A55 (0xd05) + 2× Cortex-A76 (0xd0b)** |
| 内核 | **4.14.186**，用户自编（`kuan-jsbsbxjxh66-compile`，编译机 `laptop@82MS`） |
| 页大小 | 4096 |
| 大核 | cpu6 / cpu7（`taskset c0`） |
| 频率 | 硬件上限 **2.0 GHz**（依赖加法链标定 1.996 GHz）。见下方更正 |
| `/dev/kvm` | `crw------- virtmanager root u:object_r:kvm_device:s0` |
| QEMU | Termux `qemu-system-aarch64-headless` 11.1.3（Android/aarch64 原生构建） |

> **更正（频率）**：这里原先写"大核被内核限在 1.274 GHz，所以绝对值比上一台慢 1.73 倍"。
> **那是错的。** `scaling_max_freq` 我先读到 1274000，后来重读变成 2000000，
> 而用"依赖加法链"标定（10 亿次 add，A76 关键路径 1 周期）得到 **1.996 GHz**。
> 那个 1274 是某个 power hint 打开时的瞬时值。
>
> 真实情况：硬件上限 2.0 GHz，`performance` 下实测 2.0 GHz。所以**不存在 1.73 倍的频率差**。
> 教训：频率必须实测标定，不能读一次 sysfs 当常数。

所有测量都：`taskset c0` 绑大核、`performance` governor 锁频、每次前后清场、
重复取中位数。

## 0. 先确认 KVM 是真的能用

`/dev/kvm` 这个设备节点在 Android 上是 ueventd 按配置**静态创建**的
（给 cuttlefish 用的），**不代表 KVM 真的初始化成功**。arm64 上 KVM 要求内核
跑在 EL2，而多数手机 bootloader 在 EL1 交接。而且这台机器的 `dmesg` 里
**一条 KVM 记录都没有**，没法靠日志判断。

所以写了个最小探针（`port-android/work/kvmprobe.c`），直接 ioctl 问内核：

| 探针 | 结果 |
|---|---|
| `open(/dev/kvm)` | ok |
| `KVM_GET_API_VERSION` | **12** |
| `KVM_CREATE_VM` | ok |
| `KVM_CREATE_VCPU` | ok |
| `KVM_GET_VCPU_MMAP_SIZE` | 8192 |
| `KVM_ARM_PREFERRED_TARGET` | ❌ **EINVAL** |
| `KVM_ARM_VCPU_INIT(target=0)` | ❌ EINVAL |
| **`KVM_ARM_VCPU_INIT(target=5)`** | ✅ **OK** |
| `KVM_CREATE_IRQCHIP` | ENODEV（arm64 上正常，VGIC 走 `KVM_CREATE_DEVICE`） |

**`PREFERRED_TARGET` 失败是这台内核的真问题**：4.14 的 `kvm_target_cpu()`
只把 MIDR 映射到 A53/A57，遇到 Cortex-A55/A76 返回 -EINVAL，于是"首选目标"
查询失败。逐值扫 0..12，只有 `KVM_ARM_TARGET_GENERIC_V8 = 5` 能过。

QEMU 自己会处理这个（`-cpu host` 会退到 generic v8），**自己写 VMM 的人会卡在这里**，
而且报错只有一句 `Invalid argument`，很容易被误判成"KVM 不可用"。

结论：**这台设备的 KVM 是真的**，QEMU 能建 vCPU、能收到 GICv3 ITS 的真实中断
（启动日志里 `ITS-PCI-MSIX-0000:00:01.0 virtio0-output.0` 计数在涨）。

## 1. 微基准（四方）

单位 ns/iter，越小越快；`real` 是每轮 ms。客户机里跑的是**同一个静态 aarch64 二进制**
(`bench3`)，只是执行方式不同。`-cpu host`（KVM）/ `-cpu cortex-a72`（TCG）。

| 负载 | 原生 | **KVM** | **加速器** | **TCG** | KVM/原生 | 加速器/原生 | TCG/原生 |
|---|---|---|---|---|---|---|---|
| `alu` 纯寄存器 | 10.35 | **10.29** | **10.33** | 18.15 | **0.99** | **1.00** | 1.75 |
| `mem` 访存 | 8.19 | **8.19** | 15.34 | 28.45 | **1.00** | 1.87 | 3.47 |
| `call` 4 亿次 noinline 调用 | 4.72 | **4.73** | 8.73 | 66.83 | **1.00** | 1.85 | **14.2** |
| `branch` 数据相关分支 | 3.69 | **3.71** | 5.55 | 14.92 | **1.01** | 1.50 | 4.04 |
| `real` qsort+指针追逐+哈希 | 3.473 ms | **3.496 ms** | 17.07 ms | 106.6 ms | **1.01** | 4.92 | **30.7** |

几何平均：

| | 相对原生 | 相对 TCG |
|---|---|---|
| **KVM** | **1.002×（就是原生）** | 6.4× 快 |
| **加速器** | **1.91×（52% 原生）** | **3.35× 快** |
| TCG | 6.40×（16% 原生） | — |

### 三个要点

1. **KVM 就是原生**。五项全部落在 0.99–1.01，`mem` 和 `call` 甚至一模一样。
   这不是测不准 —— 硬件虚拟化本来就只有 stage-2 页表和异常退出这点开销，
   纯计算路径上确实是零。`call` 的 1.00 尤其说明问题：**`ret` 这种间接跳转
   在硬件虚拟化下不需要任何软件介入**，而在 TCG 下是 14.2 倍。

2. **加速器在 1.0–4.9 之间，跟 KVM 的差距就是"没有 EL2"的代价**。
   `alu` 1.00（一模一样，直通翻译的极限就是这里）、`mem` 1.87（软件 TLB 查表）、
   `call` 1.85（间接跳转缓存 vs 硬件 BTB）、`real` 4.92（真实程序形态下的综合）。

3. **TCG 的最差项恰好是 `call`（14.2×）和 `real`（30.7×）** —— 和上一台设备的
   结论完全一致。原因见 BOOT-VS-TCG.md：`ret` 要退出 TB 回主循环哈希查表。

## 2. 块转移开销实验（四方）

同一份工作指令流（2^28 条），只改"每个基本块里塞多少工作指令"：

| 每块指令数 | 原生 | **KVM** | **加速器** | **TCG** | KVM/原生 | 加速器/原生 | TCG/原生 |
|---|---|---|---|---|---|---|---|
| 3（`u1`） | 0.7865 | 0.7881 | 2.3756 | 9.2151 | **1.002** | 3.02 | **11.72** |
| 10（`u8`） | 0.7865 | 0.7887 | 0.7924 | 1.2751 | **1.003** | **1.008** | 1.62 |
| 34（`u32`） | 0.7865 | 0.7881 | 0.7923 | 0.9337 | **1.002** | **1.007** | 1.19 |

拟合 `c(U) = a + (2a+b)/U`（`a` = 每条指令成本，`b` = 每次块转移成本）：

| | a（每条指令） | b（每次块转移） | 折算 |
|---|---|---|---|
| 原生 | 0.7865 ns | ≈0（分支预测吃掉） | — |
| **KVM** | 0.7879 ns | **≈0** | 硬件直接跳 |
| **加速器** | 0.7923 ns | **≈0** | 块链一条 `B` |
| **TCG** | 0.8199 ns | **2.0018 ns** | **≈2.44 条指令当量** |

**这张表是整份文档的核心。** 它把三方完全分开了：

- **KVM 的 b = 0**：块转移是 CPU 的事，guest 里一条 `b` 就是宿主一条 `b`。
- **加速器的 b = 0**：这是块链干的事 —— 块与块之间发一条 `B` 直接跳过去，
  不回派发器。所以它在 `u8`/`u32` 上跟 KVM **差 0.5%**，跟原生**差 0.7%**。
- **TCG 的 b = 2.0 ns ≈ 2.44 条指令**：每跳一次块就要付两条半指令的钱。
  真实内核代码平均 5 条指令一块，所以每 5 条指令付 2.4 条 —— 这就是它的结构性劣势。

> 上一台设备测出 TCG 的 b ≈ 1.08 ns（2.4 周期 @2.2GHz）。这台机器折算下来
> 也是 **2.44 条指令当量**，两台设备上的"指令当量"几乎相同 —— 说明这个数字
> 是 TCG 的设计常数，不是某个设备的特性。

至于加速器为什么在 `u1` 上 3.02×：3 条指令的块里，块进出占的比重最大，
而引擎的块链接有"首次进入要建链"的一次性成本（`dispatcher` 进入 vs `B` 直跳）。

## 3. 开机速度

同一个 Debian 12（bookworm arm64，NVMe 根，systemd 252，283 包）。
2 vCPU / 2048 MB。宿主墙钟包住整条调用，减去空 adb 调用基线。

### 指标一：启动路径本身（`fastboot=1`，挂上根就关机）

| | KVM | 加速器 | TCG |
|---|---|---|---|
| 3 次 | 1622 / 1632 / 1632 | 2162 / 2179 / 2065 | 9033 / 9266 / 8978 |
| **中位数** | **1632 ms** | **2162 ms** | **9033 ms** |

| 比值 | |
|---|---|
| 加速器 / KVM | **1.32×** |
| TCG / KVM | 5.53× |
| **TCG / 加速器** | **4.18×** |

### 指标二：到 systemd 完全就绪（`hvrun=boot`）

| | KVM | 加速器 | TCG |
|---|---|---|---|
| 3 次（墙钟） | 3939 / 4061 / 4130 ms | 17075 / 17024 / 17059 ms | 127038 / 125549 / 126546 ms |
| guest 自报 uptime | 3.29 / 3.35 / 3.45 s | 16.39 / 16.33 / 16.36 s | 125.31 / 123.71 / 124.77 s |
| **中位数** | **4061 ms** | **17059 ms** | **126546 ms（126.5 s）** |

| 比值 | fastboot | 完整启动 |
|---|---|---|
| 加速器 / KVM | 1.32× | **4.20×** |
| TCG / KVM | 5.53× | 31.2× |
| **TCG / 加速器** | **4.18×** | **7.42×** |

三列的三次测量各自都很稳（加速器 0.3%、TCG 1.2% 波动），宿主墙钟和 guest
自报 uptime 只差 0.7–1.2 s（固定启动开销），两边对得上。

### 更正：之前那个"≥34×"是错的

上一台设备（vivo V2156FA）上我曾测出"TCG 完整启动 12–15 分钟仍未就绪，
加速器 25.5 秒，≥34×"。**那个数字不成立**，原因现在很清楚：

当时 TCG 的第 2 次尝试卡在 `boot-efi.mount` 依赖失败 → 掉进 `sulogin`
**维护模式等待输入**。`sulogin` 永远等不到人敲键盘，所以"永远不就绪"——
这不是性能问题，是配置问题伪装成的超时。第 1、3 次用的 virtio-blk/NVMe
设备名对不上，很可能同样掉进了 sulogin。

这台设备上我把孤儿进程问题修掉之后，TCG 完整启动**稳稳 126 秒就跑完了**。
所以真实的"完整启动 vs 纯启动"放大倍数是：

| | 加速器 | TCG |
|---|---|---|
| 完整启动 / fastboot | 7.9× | 14.0× |

TCG 确实比加速器多放大一倍（因为它对 fork/exec/间接跳转收费更重），
但**是 7.4 倍，不是 34 倍**。

> **踩过的坑（写下来免得别人再踩）**：第一轮测出 17.1 / 22.5 / 28.4 s 单调上升，
> 第二轮（加长冷却）反而 60.5 / 35.3 / 31.2 s。看起来像热降频，其实是
> **TCG 那次的孤儿进程在偷 CPU**：宿主侧 `timeout` 只杀了 adb 客户端，
> 设备上的 `qemu-system-aarch64` 继续跑了 28 分钟 CPU 时间、吃满 1.2 个核。
> 修法：超时改到**设备侧**（`su -c 'timeout N ...'`），并且每次测量前后 `pkill` 清场。
> 修完之后三次立刻收敛到 0.3% 波动。
> 另外 `timeout` **不认环境变量前缀**（会把 `LD_LIBRARY_PATH=...` 当程序名），
> 必须写成 `timeout N env VAR=... cmd`。

## 4. 怎么读这些数字

### 4.1 KVM 在这台设备上是"真原生"，但它不是随便就能有

- 需要 bootloader 把内核交在 **EL2**（多数零售机不是）
- 需要内核编了 KVM，而且 `kvm_target_cpu()` 认识这颗核
  （这台 4.14 就**不认识** A55/A76，得靠 `GENERIC_V8` 兜）
- 需要 `/dev/kvm` 对进程可读（这里是 `crw------- virtmanager`，必须 root）

这台机器三条都是用户自己解决的 —— 自己编了内核。**这正是本项目的立论点**：
直通翻译器的价值不在"跑赢 KVM"，而在**没有 KVM 也能跑到 52% 原生**。

### 4.2 加速器 vs KVM 的差距在哪里

| 差距来源 | 微基准证据 | 加速器/KVM |
|---|---|---|
| 纯计算 + 块转移 | `u8` / `u32` | **1.008×（几乎无差）** |
| 软件 TLB（访存） | `mem` | 1.87× |
| 间接跳转（`ret`/`br`） | `call` | 1.85× |
| 真实混合负载 | `real` | 4.92× |
| 冷启动路径 | fastboot | 1.32× |
| 完整 systemd 启动 | full boot | 4.20× |

**注意 fastboot 只有 1.32×，而完整启动 4.20×。** 差 3 倍，说明内核启动路径
以访存和顺序代码为主（正好落在 `mem` 1.87 和 `call` 1.85 之间），
而 systemd 是海量 fork/exec + 文件操作 + 超时轮询，落在 `real` 那 4.92× 上。

### 4.3 TCG 的放大：从 4.2 倍到 7.4 倍

| TCG / 加速器 | 倍数 |
|---|---|
| `fastboot`（内核 + 挂根） | 4.18× |
| 完整启动（到 systemd 就绪） | **7.42×** |
| 微基准 `real` | 6.25× |
| 微基准 `call` | 7.66× |

完整启动比纯启动多一倍放大，且和 `real`(6.25×) / `call`(7.66×) 两个微基准
**完全吻合** —— 说明这不是什么"启动特例"，就是那两类负载在启动路径里的占比变高了：

- 内核启动：访存 + 顺序代码为主（对应 `mem` 1.85× / `alu` 1.76×）
- systemd：海量 fork/exec、每次 exec 换地址空间、大量 `ret` 与定时器中断
  （对应 `call` 7.66× / `real` 6.25×）

**微基准能预测真实启动**，这是这套测量方法最值得信任的一点：
四条路径在同一台设备上量出来的 `fastboot`/`full` 比值，
和微基准给出的区间一致，不是靠猜。

## 5. 复现

```bash
cd output

# 0. 取 QEMU（KVM / TCG 两条对照路都需要它做设备模型）
./scripts/fetch-qemu-sys.sh

# 1. 确认 KVM 真的能用（不要相信 /dev/kvm 存在就等于可用）
adb push ../port-android/work/kvmprobe /data/local/tmp/
adb shell 'su -c "/data/local/tmp/kvmprobe"'

# 2. 微基准四方
./scripts/run-bench-kvm.sh              # alu/mem/call/branch/real
./scripts/run-bench-kvm.sh loops        # 块转移开销
ONLY="alu call" ./scripts/run-bench-kvm.sh

# 3. 开机
./scripts/fetch-debian.sh               # 首次：推 1 GB 磁盘镜像
./scripts/run-boot-kvm.sh fastboot      # 约 1.5 分钟
./scripts/run-boot-kvm.sh full          # 约 7 分钟（TCG 单次要 2 分钟）
COLS="kvm engine" ./scripts/run-boot-kvm.sh full    # 跳过 TCG 可省 6 分钟
```

## 6. 一句话总结

> **KVM 在这台设备上是原生速度（1.002×）；直通翻译器是 52% 原生（比 TCG 快 3.35 倍）；
> TCG 是 16% 原生。**
> 开机：KVM 1.6 s / 加速器 2.2 s / TCG 9.0 s（到挂根），
> 4.1 s / 17.1 s / 126.5 s（到 systemd 就绪）。
> 直通翻译器的意义不是追平 KVM —— 而是**在 99% 拿不到 EL2 的 Android 设备上，
> 把"软件翻译"这件事做到只剩访存和间接跳转两项成本，
> 块转移成本已经压到和 KVM 一样是 0。**
