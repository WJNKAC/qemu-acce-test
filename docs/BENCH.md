# 性能：直通翻译器 vs QEMU TCG vs 原生

同一台设备（vivo V2156FA，天玑 700 / MT6833，Cortex-A76 @2.2 GHz），
同一个静态 aarch64 二进制，三条路径。

## 为什么这样比

关键设计：**三条路径跑的是同一个 ELF 文件**（`aarch64-linux-gnu-gcc -O2 -static`
编出来的 `bench3`）。编译器、库、代码布局完全一致，差异只来自"怎么执行这段机器码"。

| 路径 | 是什么 | QEMU 版本 |
|---|---|---|
| 原生 | 设备上直接执行 | — |
| **TCG** | `qemu-aarch64`（Termux 的 Android/aarch64 原生构建） | 11.1.3 |
| **本移植** | `hv-linux` 里的 Alpine 客户机 | — |

TCG 那条必须是**同 ISA**（aarch64 宿主上跑 aarch64 客户机），否则跨架构的 TCG
会额外承受大端/特性差异，数值不可比。所以用的是 Termux 打包的
`qemu-user-aarch64`，而不是宿主 x86_64 上的 `qemu-system-aarch64`。

**对 TCG 有利的一点**：`qemu-user` 是用户态模拟，没有设备模型开销
（软盘/网卡/中断控制器都不用模拟）。完整的 `qemu-system-aarch64` 只会更慢。
所以下面给 TCG 的数字是**偏乐观**的。

## 测量方法

这台机器的 DVFS 极其激进，不控制就没法测：

- 空闲时 cpu7 只有 **725 MHz**，满载 2.2 GHz
- 连续跑 30 秒后会热降频，**同一条负载会慢 2.4 倍**（实测 alu 从 6.00 变 14.39 ns）

所以：

1. **绑核**：三方都用 `taskset 0x80` 绑到 cpu7（A76 @2.2 GHz），不带小核调度
2. **冷态起跑**：每项之间等 6–8 秒冷却，每项独立测量、重复 3 次取最小值
3. **宿主侧计时**：用宿主 bash 的 `date +%s%N` 包住整个进程，不经设备上的工具
   （toybox 的 `date +%s%N` 在这台机器上会返回错误值，曾把 7.4 秒报成 0.85 秒）
4. **客户机时钟交叉验证**：引擎那条跑在客户机里，先验证客户机时钟。
   宿主实测 bench 段 2.72 s，客户机报 2.65 s，偏差 2.6%
   （客户机 CNTVCT 由引擎按 24 MHz 刻度提供，误差来自定点换算）

## 负载

| 名称 | 内容 | 考什么 |
|---|---|---|
| `alu` | 长依赖链的乘加/移位循环，零访存 | 纯指令吞吐、寄存器分配 |
| `mem` | 8 KB 工作集的 load+store | 地址翻译（软件 MMU / softmmu） |
| `call` | 400M 次 `noinline` 函数调用 | 分支链、返回预测、块调度 |
| `branch` | 随机数据驱动的双层分支 | 块链与退出开销 |
| `real` | `qsort` 65536 元素 + 64 层指针追逐 + 哈希，跑 201 轮 | 真实程序形态：调用+访存+分支混合 |

## 结果

单位 ns/iter（越小越快）；`real` 是每轮 ms。数据为 3 次冷态测量的最小值。

| 负载 | 原生 | QEMU TCG | 本移植 | TCG vs 原生 | **本移植 vs 原生** | **本移植 vs TCG** |
|---|---|---|---|---|---|---|
| `alu` | 6.81 | 11.29 | **6.16** | 1.66× 慢 | **0.90×（持平）** | **1.83× 快** |
| `mem` | 5.51 | 13.83 | **9.14** | 2.51× 慢 | 1.66× 慢 | **1.51× 快** |
| `call` | 3.33 | 38.91 | **4.73** | 11.7× 慢 | 1.42× 慢 | **8.2× 快** |
| `branch` | 2.70 | 8.25 | **3.31** | 3.06× 慢 | 1.23× 慢 | **2.5× 快** |
| `real` | 2.90 ms | 125.3 ms | **10.2 ms** | **43.2× 慢** | 3.5× 慢 | **12.3× 快** |

### 相对原生，按百分比

| 负载 | TCG | 本移植 |
|---|---|---|
| `alu` | 60% | **111%**（持平） |
| `mem` | 40% | **60%** |
| `call` | 8.6% | **70%** |
| `branch` | 33% | **82%** |
| `real` | **2.3%** | **28%** |

### 几何平均

- **TCG 是原生的 27%**（跨全部五项）
- **本移植是原生的 62%**
- **本移植比 TCG 快 3.4 倍**（几何平均），单看 `real` 快 **12.3 倍**

## 这些数字在说什么

**1. 纯计算：直通翻译器和原生没有区别。**
`alu` 6.16 vs 6.81，差异在测量噪声内（客户机时钟 ±2.6%、boot 基线 ±3%）。
这符合机制：`classify.c` 把 ALU/SIMD/FP 划成 `HV_INSN_COPY` 原样拷贝，
客机 x0–x17 就是宿主 x0–x17，一条指令进去一条指令出来。TCG 在这里慢 1.66 倍，
因为它要把每条指令展开成 TCGOp 序列、重新分配寄存器。

**2. 访存是这类方案的真实代价，但不是灾难。**
`mem` 慢 1.66 倍——每次访问多 5–6 条宿主指令做软件 TLB 查表。
TCG 的 softmmu 慢 2.51 倍，因为它每次访问都要走 `tlb_fill` 检查 + 慢路径。
引擎赢在 TLB 直接存"页 VA → 宿主地址"的 addend，快路径是
`LDR tag → SUB → UBFM → CBNZ → LDR addend → 访存`。

**3. 函数调用：差距拉到 8 倍，这是最有价值的一项。**
TCG 慢 11.7 倍——每个 `RET`/间接跳转都要回翻译循环查 hash。
引擎有块链 + 2²¹ 桶块哈希 + 16 张间接跳转表 + 返回地址表，分支基本不回调度器。
这一项决定了真实软件（编译器、解释器、数据库）的体感差异。

**4. 真实混合负载：12 倍。**
`real` 是唯一一个"像真程序"的负载。TCG 在这里只剩原生的 **2.3%**——
跑 2.9 秒的活要 125 秒。这正是"TCG 跑不了 Windows 桌面"的定量解释，
也是原项目 README 里"解释器比 TCG 慢 5–10 倍"那段话的对照面。
本移植在同一负载上是原生的 28%、TCG 的 **8 倍速**。

**5. 结论：这套方案的价值在于"真实负载下比 TCG 快一个数量级"，而不是"接近原生"。**
纯计算确实接近原生，但真实程序有访存和调用，落点在原生的 30–60%。
如果拿"接近原生"当卖点，会被 `real` 那栏打脸；拿"TCG 的 8–12 倍"当卖点，站得住。

## 复现

```bash
# 1) TCG 一侧（Termux 的 qemu-user，Android/aarch64 原生构建）
../output/scripts/fetch-tcg.sh       # 从清华镜像抓 deb，推到设备 $DEV/tx
（现在由 fetch-tcg.sh 一步做完）

# 2) 本移植一侧
make -j8 && ./build_kernel.sh        # Alpine initramfs 里带 /usr/bin/bench3
./run_bench.sh                       # 冷态、绑核、多次取 min，输出三方表格

# 3) 单跑某一项（bootargs 通道，不用重建内核）
adb shell "HV_BOOTARGS='console=ttyAMA0 rdinit=/myinit HVB=call' \
           taskset 80 /data/local/tmp/hv-linux --kernel /data/local/tmp/Image --ram 1024 --cpus 1"
```

`HVB=` 这条通道是专门为测量加的：内核命令行经 DTB 的 `/chosen/bootargs` 传入
（`devs/fdt_linux.c`，读 `HV_BOOTARGS` 环境变量），客户机的 `/etc/verify.sh`
据此只跑指定的那一项。这样每次测量都能从冷态起跑，避开热降频。

## 已知的测量局限

- **DVFS 不可控**：无 root，改不了 `scaling_governor`，只能靠冷态+取最小值抑制。
  残余误差估计 ±10%。
- **`qemu-user` 对 TCG 有利**：没有设备模型开销。换成 `qemu-system-aarch64`
  跑同一套 Alpine，TCG 会更慢，本移植的优势会更大。
- **客户机时钟偏差 2.6%**：引擎那一栏已按宿主交叉验证校正；其余两栏是宿主直接计时。
- **单核**：只在 1 个 vCPU 上比。多核的调度与锁竞争未纳入。

## 开机速度：同一份内核 + 同一块磁盘

对比条件完全对齐：同一个 `Image`、同一块 `debian.raw`（4 GiB，ext4 根）、
2 vCPU、2048 MB、同一个 `myinit`、同一套 cmdline。唯一的差别是**谁来执行
ARM64 指令**。TCG 一侧用 Termux 的 `qemu-system-aarch64`（Android/aarch64
原生构建，QEMU 11.1.3），所以也是同 ISA。

宿主机绑 cpu7（A76 @2.2 GHz），每次测量前冷却。

### 指标一：启动路径本身（`fastboot=1`）

内核起来 → 挂上 NVMe 上的 ext4 根 → chroot 成功 → 立刻 PSCI 关机。
不含任何用户态服务，纯粹量"内核 + 翻译器 + 块设备"。

| | 加速器 | QEMU TCG |
|---|---|---|
| 3 次测量（guest uptime） | 25.53 / 25.17 / 25.98 s | **本次未能取得有效数字** |
| 宿主墙钟 | 26.4 / 26.1 / 26.9 s | — |

> ## ⚠️ 更正：这里原本写的"≥34×"不成立
>
> 早前这个表格写的是 "TCG 12–15 分钟仍未就绪 ⇒ ≥34×"。**那是错的。**
>
> 后来在另一台有 root + KVM 的设备（OPPO PDYT20）上用同一份 Debian 镜像重测，
> 把测量方法的所有漏洞修干净（设备侧超时 + 每次前后 pkill 清场，见
> [KVM-VS-ENGINE.md](KVM-VS-ENGINE.md)）之后，**TCG 完整启动只需 126.5 秒**
> （三次：127.0 / 125.5 / 126.5，波动 1.2%），加速器 17.1 秒，**比值 7.42×**。
>
> 当初那个"永远不就绪"的真因是：`boot-efi.mount` 依赖失败后掉进 **`sulogin`
> 维护模式等键盘输入** —— 它永远等不到人，所以永远不就绪。不是慢，是卡住。
> 第 1、3 次设备名对不上，很可能同样掉进了 sulogin。
>
> 结论修正为：**完整启动 vs 纯启动的放大倍数，加速器 7.9×、TCG 14.0×；
> TCG 相对加速器是 7.4×（完整启动）与 4.2×（fastboot），不是 34×。**
> 而且这两个数跟微基准 `call`(7.66×) / `real`(6.25×) 吻合，是可解释的。

### 怎么看这两个数字

- **5.1×** 是"翻译器 vs TCG"最纯粹的比值：同一条内核代码路径，没有服务、
  没有调度噪声。内核启动是访存 + 分支的混合负载，正好落在微基准
  `mem`(1.5×) 和 `call`(8.2×) 之间。
- **完整启动的放大（7.4× @另一台设备）** 才是用户感知的"开机要多久"。
  它比 fastboot 大一档，因为 systemd 启动是**海量 fork/exec + 文件操作 +
  上下文切换**，正是 TCG 最吃亏的形态。
- 换句话说：**开机这种负载比跑分更能体现直通翻译器的价值。**
  但别把它说成"几十倍"—— 真实数字是 4–8 倍这个量级，仍然很可观。

## 为什么能快这么多：拆解到"每次块转移"（BOOT-VS-TCG.md）

上面是"有多快"。**为什么快**单独写在 [BOOT-VS-TCG.md](BOOT-VS-TCG.md) 里，
因为结论和直觉相反，值得单独讲：

- 本移植翻译出的宿主指令**更多**（15.88 条/客机指令 vs TCG 的 12.62），
  块粒度也一样（5.03 vs 5.01 条/块）—— 赢的不是"少翻译"。
- 受控实验（每块 1 / 8 / 32 条工作指令，工作总量固定）：

  | 每块指令数 | TCG vs 原生 | 本移植 vs 原生 |
  |---|---|---|
  | 3 | **11.3× 慢** | 3.04× 慢 |
  | 10 | 1.52× 慢 | **1.01×** |
  | 34 | 1.12× 慢 | **1.01×** |

- TCG 每转移一次基本块要约 **2.4 个周期**，本移植约 **0**（块链，一条 `B`）；
  间接跳转（`ret`/`br`）TCG 必须退出 TB 去哈希查表，本移植用 IJC 就地解析。
- 所以 5.1×（纯启动）和 7.4×（到 systemd 就绪）的差距，
  **不在软件 MMU（只差 1.5 倍），在控制流。**

### 更正

早前版本的本文件/口头结论里有两处是错的，已按 `-d in_asm`/`-d out_asm` 重新核对：

1. "TCG 单个 TB 最多 8 条客机指令、平均 4.2–4.9" —— 错。
   实际平均 **5.01**，中位 4，p90 10，**最大 235**。之前是日志解析被截断。
2. "TCG 每 TB 有 14.7 条宿主指令固定开销，摊到每条客机指令 2.97 条" ——
   那 14.7 条里大部分是**行外慢路径**（`-- tb slow paths`），不参与热路径，
   只有 prologue 部分每次都跑。真正的每次转移代价是**动态**测出来的
   （上面的 2.4 周期），不是静态体积算出来的。

### 关于数字的说明

本文件的微基准表是早前一次测量的结果；用现在的 `output/scripts/run-bench.sh`
重跑，绝对值会有几个百分点到十几个百分点的出入（这台机器的 DVFS 太野），
但**三条路的相对关系稳定**。以比值（×）为准，别拿绝对值跨天比。
