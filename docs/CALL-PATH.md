# `call` 的成本到底在哪 —— 影子栈能不能救

结论先说：**影子栈这个方案，引擎里已经有了，而且它已经不是瓶颈。**
我把"返回地址处理"这条路径用三种方式拆开实测，客户机里**一点都动不了**。
真正吃掉 `call` 的是那 17 条宿主指令本身，不是预测失败，也不是查表。

---

## 1. 先确认：引擎里已经有一个"影子栈"

`core/translate.c` 的 `put_call` / `put_return` 维护一张
**返回地址表**（`HV_CPU_RET_TAB`，`HV_RET_BITS = 13` → 每张表 8192 槽 × 16 字节，
共 `HV_IJC_TABLES = 16` 张）：

| | 内容 |
|---|---|
| 索引 | `(guest_ret_va >> 2) & 0x1fff` |
| `+0` | `tag = salt ^ guest_ret_va` |
| `+8` | `H` = 调用之后那条指令对应的**宿主**代码地址 |

- 客机 `bl` → 宿主 `bl L`（拿到 H 塞进表），然后把 `x30` 改成客机返回地址
- 客机 `ret` → 查表 → 命中则 `ret x6` 直接跳到 H；未命中落到 IJC

这就是影子栈在功能上要做的全部事情。**唯一的差别是它用"按返回地址哈希的表"
而不是"按调用深度压栈的栈"**，源码注释里给了理由：

> A table and not a stack, so calls and returns don't wait for each other:
> a stack's top has to go through memory from each to the next.

也就是说，栈版本会让每次 call 和 ret 都串在同一个地址上（store→load 转发链），
表版本让不同深度的条目落在不同槽位。**这个选择是有意的，不是遗漏。**

## 2. 那它到底贡献了多少？A/B 关掉它

`HV_NO_RAS=1` 让所有 `ret` 都走间接跳转缓存（等于"没有影子栈"）：

| | 有返回地址表 | `HV_NO_RAS=1` |
|---|---|---|
| `bench_calls` 第 1 次 | 2.416 ms | 2.408 ms |
| 第 2 次 | 2.618 ms | 2.662 ms |

**差异在噪声内（±5%）。** 关掉它也不变慢 —— 说明这张表的热路径成本已经很低，
而且**"返回预测失败"根本不是成本项**（否则关掉它会大幅变慢）。

## 3. 再进一步：换三种返回指令，看宿主 RSB 有没有被用上

引擎发的是 `ret x6`（**寄存器间接**）。ARM 的返回地址栈（RSB）通常只预测
以链接寄存器 `x30` 为目标的 `ret`。如果 `ret x6` 拿不到 RSB 预测，
每次返回就是一次间接跳转失败（10–15 周期），那才是大钱。

用 `tools/patch_translate.py` 生成三个变体（原树只读，改的是生成副本）：

| RET_MODE | 生成的返回序列 |
|---|---|
| 0（基线） | `ret x6` |
| 1 | `mov x30, x6` + `ret`（走 x30，力争 RSB） |
| 2 | `br x6`（明确不走 RSB，反向对照） |

### 宿主侧微基准（test_bench，fib 递归，各 3 次）

| 变体 | 3 次 | 中位数 | 波动 |
|---|---|---|---|
| 0 `ret x6` | 2.582 / 2.464 / 2.564 | 2.564 | 4.6% |
| **1 `mov x30,x6; ret`** | **2.402 / 2.404 / 2.428** | **2.404** | **1.1%** |
| 2 `br x6` | 2.595 / 2.528 / 2.556 | 2.556 | 2.6% |

看起来变体 1 快 6%，而且**波动从 4.6% 收紧到 1.1%** —— 很像"命中 RSB、变成可预测"。

### 客户机里（真正的目标，`bench3 call`，各 5 次）

| 变体 | 5 次 | 
|---|---|
| 0 | 5.55 / 5.57 / 5.06 / 5.58 / 5.57 |
| 1 | 5.59 / 5.56 / 5.08 / 5.58 / 5.58 |

**一模一样**（两个档位 5.06/5.57 是 DVFS，两变体落在同一档）。`real`、`branch` 同样无差。

**结论：宿主侧那 6% 是代码对齐的运气，不是 RSB。** 这个变体不值得留；
而且它有一个正确性隐患（见第 5 节），更不能上。

## 4. 那 1.85× 到底花在哪：就是指令条数

把 `fib` 的 JIT 代码 dump 出来逐条数（`tools/analyze_jit_dump.py`）：

| 客机 | 宿主 | 放大 | 内容 |
|---|---|---|---|
| `movz x0,#24` + `bl` | **9 条** | — | `bl L`、`b site`、`add`(表基址)、`str`(存 H)、`ldr`(装客机 LR)、`ldr`(salt)、`eor`、`str`(存 tag)、`b target` |
| `ret` | **10 条** | **10.0×** | `ubfx`、`add`、`add`、`ldp`、`ldr`(salt)、`eor`、`eor`、`cbnz`、`ret x6`、`nop` |

一次 call+ret = 客机 2 条 → 宿主 **19 条**，其中维护性开销约 **17 条**。

对得上的算术：

- `bench3 call`：原生 4.72 ns，加速器 8.73 ns，差 **4.01 ns**
- 实测主频 **2.0 GHz**（依赖加法链标定，见 MEASURE.md）→ 4.01 ns ≈ **8 个周期**
- 17 条宿主指令在 4 宽发机上 ≈ **4.25 个周期**

**只解释了一半**（8 vs 4.25）。剩下约 3.75 周期不在指令发射上。这仍然是
"指令条数为主因"的量级，但不能说"完全对上"—— 之前用 1.274 GHz 算出的
"5.1 周期，误差在解释范围内"是基于错误的频率读数，已更正。

这解释了为什么三个变体都没用：它们改的是"这 17 条指令长什么样"，
但一条都没少。

## 5. 顺便记一个坑：`mov x30,x6; ret` 是错的

引擎的不变式是「**宿主寄存器 == 客机寄存器**」（链式进入下一个块时不重载）。
`ret` 时 `x30` 持有**客机**返回地址（表就是拿它做索引的）。
`mov x30, x6` 会把它换成宿主地址 H，于是目标块看到的 `x30` 是个宿主地址。

`fib` 恰好没事（返回后立刻 `bl` 覆盖 x30，或者由 `ldp x29,x30` 从栈恢复）。
但按 AAPCS，`x30` 在调用后是 caller-saved，理论上不该被依赖 ——
可一旦有代码在返回后**存储**或**透传** x30，就会把宿主地址泄进客机内存。

所以这个变体即使测出增益也不能上。任何"返回走 x30"的方案都必须同时解决
客机 x30 的保存/恢复，代价会吃掉全部收益。

## 6. 真正值得试的方向：返回点特化（ret → 字面量 `b`）

既然成本是指令条数，唯一的出路是**把 10 条变成 1 条**：

> 如果一个块的 `ret` 总是返回到同一个地方（叶子函数、非递归、单调用点），
> 就为这个「调用点 × 被调块」克隆一份被调块，把里面的 `ret` 直接改成
> `b H`（字面量跳转）。

- **收益**：一次 call+ret 从 19 条降到约 10 条，`call` 有望从 1.85× 压到 ~1.4×
- **正确性**：不依赖 host x30，不破坏宿主/客机寄存器不变式
- **代价**：代码体积（按调用点克隆）；递归/多调用点函数退化为现有路径
- **判据**：`bench_calls`（fib，递归）应该**没有**收益 —— 它正好是反例；
  要证明收益得用「单调用点 + 叶子被调」的负载，也就是 `bench3 call`

这是下一步该做的事，而且它和影子栈是互斥的路线：影子栈优化"查表命中率"，
返回点特化直接**消灭查表**。

## 7. 顺带：`mem` 才是现在更大的一块

同一次四方对比里，`mem` 是 1.87× 而 `call` 是 1.85×，`real` 4.92×。
`real` 里 qsort + 指针追逐以访存为主。每次客机访存是 5–6 条宿主指令的
软件 TLB 查表 —— 和 `call` 同一个量级的问题，但发生在**每一次 load/store**，
而 `call` 只发生在调用点。所以如果要排优先级，**访存路径的指令数**比返回路径更值钱。

## 复现

```bash
cd port-android
# 三个返回变体（原树只读，只改生成的副本）
for m in 0 1 2; do rm -f build/translate.o build/translate_patched.c; make RET_MODE=$m; done
# 关掉返回地址表做 A/B
taskset c0 test_bench          # 对比 HV_NO_RAS=1
# dump 出 JIT 代码逐条数
HV_DUMP=/tmp/dump.bin test_bench bench_calls && python3 tools/analyze_jit_dump.py /tmp/dump.bin
```
